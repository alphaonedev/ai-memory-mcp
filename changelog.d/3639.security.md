**`memory_notify` / `ai-memory notify` / `POST /api/v1/notify` never overwrite
an inbox message again (#3639).**

A second delivery to the same recipient with the same title merged into the
first row through the `(title, namespace)` upsert: the earlier body was
destroyed, the row kept the FIRST sender's `agent_id` (so the new body was
presented as written by the first sender), a read row stayed "read", both
senders received the same row id (an existence oracle on another agent's
inbox), and the wake plane re-woke the recipient for the same id. Both
backends.

- Every delivery is a NEW row. The stored title is minted from the fresh row
  id — `<subject> [<first 8 chars of the id>]` (`inbox_stored_title`) — so two
  deliveries can never share the key, and every notify funnel (MCP, CLI,
  HTTP, the sqlite and postgres SAL adapters) inserts with the
  refuse-on-conflict arm: a collision is a visible error, never a merge.
- The caller's title is kept verbatim as `metadata.subject`; inbox rows and
  the notify receipt carry both `title` (stored, unique) and `subject`.
- A fresh delivery is always unread; the wake names the new row.
