**Carrier-branch freshness gate and carrier ruleset (#6143, partial; the defect stays open until #6182).** `chain/**` and `rehearsal/**` pull-request bases carry no rule requiring status checks or an up-to-date head, and GitHub does not re-run `pull_request` workflows when the base moves, so a green gate could be merged on a stale head. Two new `c8-precheck.yml` jobs, both advisory until the carrier ruleset requires them: `Carrier-base freshness gate (#6143)` (`scripts/check_carrier_base_fresh.py`) reports RED for a merge ref not built on the live carrier-base tip and prints the `gh pr update-branch` remedy; `Carrier-ruleset live verifier (#6143)` (`scripts/check_carrier_ruleset_live.py`, read-only) compares the live rulesets with the committed payload `docs/ci/carrier-ruleset.json` (strict, `do_not_enforce_on_create`, no bypass actors, contexts pinned to the GitHub Actions app) and the new declaration `scripts/qc-allowlists/required-contexts-carrier.txt`, so a removed or weakened carrier rule is detected once the ruleset is applied (#6182, one `gh api -X POST` command documented in `docs/ci/CARRIER-BRANCH-GATES.md`). The verifier's `applied`/`pending-apply` state is coupled to promoting its own context (release and carrier declarations, payload, not-required ledger), it names only tracking issue #6182, it treats only an actual empty `bypass_actors` list as verified, and it treats an empty `gh` body as unreadable. A `--pre-apply` mode refuses the ruleset POST/PUT while any unfrozen carrier tip (today `chain/promo6-ssh` and `rehearsal/audit-wip-ssh`) lacks the two jobs, and the verifier job is granted `issues: read` explicitly. Both run the PR's own copy under `pull_request` (#6140). Pinned by `tests/carrier_base_fresh_gate_6143.rs`.
