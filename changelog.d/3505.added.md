`ai-memory wake-hub` sessions may now subscribe to the namespaces an agent
PROVABLY reads, not only to their own inbox.

Since #3468 the delegation verifier admitted exactly one topic per session —
`#_inbox/<agent-id>` — so a wake about a shared team namespace had nowhere to
land. It now also admits `#<namespace>` for any namespace the CURRENT identity
snapshot proves that principal reads.

The proof is derived out of band by `ai-memory identity hub-cache`, from the
SAME predicate the store applies for namespace read scope: the #1921 team /
unit / org subtree the agent's id sits in, with #3348 substrate namespaces
excluded. There is no second copy of that predicate —
`crate::visibility::namespace_read_scope_admits` is the one definition, reused
by the sqlite and postgres exporters alike. The expanded set is carried in the
public snapshot, so the hub matches it EXACTLY and still opens no database at
verify time; a prefix rule at the hub would silently re-widen every scope the
exporter narrowed.

Revocation is the load-bearing half. Every session's LIVE subscription set —
the hello topics and anything a later `subscribe` frame added — is re-verified
on the existing one-second revalidation, so dropping a namespace from the next
snapshot drops the already-open subscription with no reconnect and no
cooperation from the client. Before this, a topic added by a `subscribe` frame
was never re-checked at all and could outlive the proof that admitted it. The
session survives the narrowing: losing a namespace costs subscriptions, never
the agent's own inbox.

The per-agent set is bounded by `MAX_READABLE_NAMESPACES` (tied to
`MAX_TOPICS_PER_SESSION`). Over the ceiling the exporter refuses to publish and
the hub refuses to load — never a truncation, because which namespaces survived
one would depend on ordering. A snapshot naming a substrate namespace is
refused at load, and the verifier refuses such a topic independently, so a
buggy or compromised exporter still cannot hand over another agent's inbox.

`ALLOWLIST_FILE_VERSION` is unchanged at `2`, deliberately: the field is
additive, so a newer hub reading an older snapshot defaults the set to empty
and admits own-inbox only (never "everything"), while an older hub reading a
newer snapshot already refuses the file whole through `deny_unknown_fields`.
Bumping would have made a newer hub refuse every older snapshot instead, so
upgrading the hub before the exporter would take the fleet down.

`identity hub-cache` reports the total granted set in its published JSON
(`readable_namespaces`, `max_readable_namespaces_per_agent`), so a widening is
visible without opening the 0600 file.

Not included: nothing in the substrate publishes a topic-addressed wake yet —
the #3469 sink emits direct wakes only — so a namespace topic is subscribable
and is fed by another authenticated session. Emitting a topic wake from the
substrate is a separate change to the producer, tracked as a follow-up.
