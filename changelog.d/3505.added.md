`ai-memory wake-hub` sessions may now subscribe to — and send wakes to — the
namespaces an agent PROVABLY reads, not only to their own inbox.

Since #3468 the delegation verifier admitted exactly one topic per session —
`#_inbox/<agent-id>` — so a wake about a shared team namespace had nowhere to
land. It now also admits `#<namespace>` when the CURRENT identity snapshot
proves that principal reads it.

The proof is the store's own #1921 read scope, derived out of band by
`ai-memory identity hub-cache` from the agent's OWN ID: its team / unit / org
ancestors, carried in the public snapshot as PREFIXES. The hub then admits a
namespace when `crate::visibility::namespace_subtree_contains` — the store's
own subtree containment test, shared with `crate::storage::matches_subtree` —
places it inside one carried prefix AND it is not a #3348 substrate namespace.
Both halves are the shared predicate, so nothing re-widens: `acme/eng` admits
`acme/eng/x` and never `acme/engineering`. The hub still opens no database at
verify time, and the sqlite and postgres exporters call one definition.

Carrying prefixes rather than an expanded namespace list is an availability
property, not a convenience: an expanded list is a function of the CORPUS, so
it grows as namespaces are created, an org-level agent eventually exceeds any
per-agent ceiling, and an export that refuses publishes NOTHING — after which
the snapshot ages out and the hub refuses EVERY hello. The prefix set is a
function of the agent's id, so it is fixed-size forever and the 30-second
refresher issues no corpus-wide namespace scan on either backend.

Topic-addressed SENDS take the same proof. A `wake` whose `to` is
`#<namespace>` is gated by the identical check a `subscribe` takes, so a
session may address exactly the topics it could itself subscribe to; an
out-of-scope send is refused `403 forbidden` and fans out to nobody. Without
that gate the widening would have been one-sided — before this change nobody
could subscribe to a namespace topic, so an ungated send reached nobody, and
the moment one became subscribable any authenticated peer in any tenant could
have published fabricated hints to every subscriber of a team namespace and
forced catch-up reads fleet-wide while paying only its own token bucket.
`forbidden` refuses one frame and keeps the session, so a mis-addressed wake
never becomes a reconnect storm. The reserved `wake-hub-producer` (#3469) is a
flat id with no ancestor, so it carries an empty set by design and cannot
publish to a namespace topic at all; its direct own-inbox wakes are unchanged.

Revocation is the load-bearing half. Every session's LIVE subscription set —
the hello topics and anything a later `subscribe` frame added — is re-verified
on the existing one-second revalidation, so narrowing the next snapshot drops
the already-open subscription with no reconnect and no cooperation from the
client. Before this, a topic added by a `subscribe` frame was never re-checked
at all and could outlive the proof that admitted it. The session survives the
narrowing: losing a scope costs subscriptions, never the agent's own inbox.

The per-agent set is bounded by `MAX_READABLE_PREFIXES`, which is DEFINED as
`crate::visibility::NAMESPACE_READ_SCOPE_DEPTH` so the hub's ceiling and the
derivation are one number and cannot drift. The exporter cannot produce an
oversize set, so a file carrying one is evidence it is not what it claims to be
and the hub refuses it whole — never a truncation, because which prefixes
survived would depend on ordering. A snapshot naming a substrate prefix is
refused at load, and the verifier refuses such a topic independently, so a
buggy or compromised exporter still cannot hand over another agent's inbox.

`ALLOWLIST_FILE_VERSION` is unchanged at `2`, deliberately: the field is
additive, so a newer hub reading an older snapshot defaults the set to empty
and admits own-inbox only (never "everything"), while an older hub reading a
newer snapshot already refuses the file whole through `deny_unknown_fields`.
Bumping would have made a newer hub refuse every older snapshot instead, so
upgrading the hub before the exporter would take the fleet down.

`identity hub-cache` reports the total granted set in its published JSON
(`readable_prefixes`, `max_readable_prefixes_per_agent`), so a widening is
visible without opening the 0600 file.

Not included: nothing in the substrate publishes a topic-addressed wake yet —
the #3469 sink emits direct wakes only — so a namespace topic is fed by another
authenticated session that proves the namespace. Emitting a topic wake from the
substrate is a separate change to the producer, and the send gate makes that
boundary explicit: it would require deliberately granting the reserved producer
principal a namespace scope. Tracked as a follow-up.
