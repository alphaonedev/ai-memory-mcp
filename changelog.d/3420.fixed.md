An update can no longer leave a stale attestation on a rewritten row.
`PUT /api/v1/memories/{id}` (and its MCP `memory_update` / CLI `update` twins)
can rewrite `title`, `content` and `namespace` — all of them inside the signed
`SignableWrite` envelope — while #3015 preserves `metadata.attest_level` and
`metadata.write_signature` across the patch, so the row persisted
`attest_level="agent_attested"` beside a signature that can never again be
re-derived from it: unverifiable by construction, yet believed by
`row_is_agent_attested`, by the federation relay under
`AI_MEMORY_FED_REQUIRE_WRITE_SIG=1`, and by the attestation census. Every
update funnel on both backends now applies one shared entitlement decision
(`identity::attest::entitled_update_attestation`): while the signed envelope is
intact the stored attestation is preserved verbatim (the #3015 contract,
unchanged); when any envelope field is rewritten — including the fresh
`created_at` an append-and-archive supersede mints — the row drops to
`claimed` with the signature removed and a WARN naming the transition; and an
update, which has no signature channel, can never mint an attestation from
caller-supplied metadata. Re-attesting a rewritten row means re-storing it
through a signed write funnel.
