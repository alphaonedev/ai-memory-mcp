Test suites no longer mint keypairs in the operator's real key store. The
X25519 key-directory resolver forked on `#[cfg(test)]` — a sandbox that is
true only while compiling the crate's own unit tests. Integration tests link
the already-built rlib, compiled without `cfg(test)`, so they took the
production arm and wrote per-agent keypairs into `~/.config/ai-memory/keys`;
43 fixture keypairs (`agent-bad-2383.x25519`, `pg-commit-b-wrong.x25519`,
`test-agent-228-tamper.x25519`, …) accumulated there while the unit suite
looked hermetic. The fork is gone: one resolver for every build, and tests arm
the sandbox explicitly through `identity::keypair::install_test_key_dir_sandbox`
— a single mechanism that works on both sides of the crate boundary and that
verifies at arm time that the pin took effect, rather than trusting it. A new
guard binary keeps it closed: it refuses any test source that can resolve the
default key directory without arming the sandbox, refuses the reintroduction of
the `cfg(test)` fork, and proves behaviourally that a minted keypair lands in
the sandbox with the operator's key directory untouched.

The two test-only helpers live behind a new `test-support` cargo feature that production builds never enable, so neither exists in the shipped API: arming the sandbox permanently pins `AI_MEMORY_KEY_DIR` at a tempdir, and a production caller would strand every key minted afterwards in a directory the OS reclaims at exit. Integration tests reach it through a self dev-dependency — the mechanism that does cross the crate boundary, which is the whole lesson of this issue.
