**`memory_capture_turn` resolves the caller like every other tool (#3393).**

The MCP dispatcher handed `memory_capture_turn` the RAW `initialize.clientInfo.name`
as its caller, so the captured row (and its `signed_events` attribution) was stamped
with an unvalidated, un-prefixed, client-chosen string — ignoring `AI_MEMORY_AGENT_ID`,
unreadable by the identity that wrote it, and making the #1413 `metadata.agent_id`
agreement check compare two client-chosen strings. A caller passed as `None` was
stamped with a sentinel no identity can read back.

- The tool now takes the #3549 authority principal (`AI_MEMORY_AGENT_ID` first; the
  handshake name only through the canonical durable `ai:<client>@<hostname>` derivation,
  sanitised and validated), exactly like `memory_store`. A caller string that is not a
  valid agent id is REFUSED (`INVALID_INPUT … set AI_MEMORY_AGENT_ID`), never stamped;
  an absent caller resolves through the same ladder.
- The envelope carries the `agent_id` the row was attributed to, so the caller can see
  what was stamped instead of trusting it.
- The dispatch-level audit actor (`resolve_mcp_agent_id`) uses the same derivation for
  its client fallback instead of `ai:<raw name>`, so a control character in a client
  name never reaches the SIEM actor field.

Tests (fail on the previous head): `capture_turn::handler_tests::*_3393` (env wins,
prefixed fallback, invalid caller refused, agreement against the resolved id, sentinel
gone), `mcp::tests::resolve_mcp_agent_id_never_stamps_raw_client_name_3393`, and
`tests/capture_turn_identity_3393.rs` over MCP stdio. `memory_capture_turn` is an MCP
stdio (sqlite) tool; the HTTP `POST /api/v1/capture_turn` twin already resolved its
caller through the HTTP authority and is unchanged.
