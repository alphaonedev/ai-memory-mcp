**`schema_version` is documented as the advisory shape marker it is, not as a parser selector (#4241).** `docs/CONFIG_SCHEMA.md` said "None/1 = legacy flat parse; >=2 = sectioned parse" and that `>= 2` "selects the sectioned parse path", implying two version-selected parsers. There is one: `AppConfig::from_toml_contents` runs the deprecation and unknown-key validation and then a single `toml::from_str` (`src/config.rs:8605`) for every marker value; the inspected version predicate (`src/config.rs:8664`) selects only the mixed-legacy-field drift WARN, and `AppConfig::resolve_llm` (`src/config.rs:9450`) resolves sectioned `[llm]` values without consulting the marker. Both carriers now describe the marker, and a note records that the loader accepts known flat and sectioned fields through the same parser, that resolver precedence applies regardless of the marker, and that the marker proves nothing about future-schema support — the field is `Option<u32>` (`src/config.rs:3533`), so omission is not a stored `1`. The field table's Default column now reads `None` (omitted) rather than `1`, matching that same evidence — `schema_version` is `Option<u32>` with no serde default and no `unwrap_or(1)`, so an omitted marker is stored as `None` and merely DENOTES the legacy shape.
