### Fixed

- **[test-isolation] `daemon_runtime::tests::test_bootstrap_serve_*` could
  fail with the SQLCipher-passphrase refusal because the `cfg(test)`
  passphrase slot is a process-global that the seeding tests bounded but never
  excluded readers from**
  ([#3539](https://github.com/alphaonedev/ai-memory-mcp/issues/3539)).
  Test-isolation and gate-script change only; no product behaviour changes and
  the fail-closed at-rest boot gate is untouched (it is the VICTIM here, not
  the defect). `storage::connection::refuse_at_rest_requested_without_sqlcipher()`
  runs on EVERY sqlite open and refuses when `passphrase_requested()` is true —
  which consults BOTH `AI_MEMORY_DB_PASSPHRASE` AND the process-private
  passphrase slot seeded by the `--db-passphrase-file` channel. Under
  `cfg(test)` that slot is a process-global `RwLock<Option<String>>`, and the
  old `DbPassphraseGuard` only RESET it on enter and on drop. A reset bounds a
  seed to one test body; it excludes nobody. So when either of the two seeding
  tests overlapped `test_bootstrap_serve_keyword_tier_no_embedder` — which took
  no lock at all and opens sqlite through `bootstrap_serve` — the boot took the
  sqlcipher refusal (`Check (macos-fed,sqlite)`, 2026-09-08). Same class as
  [#3517](https://github.com/alphaonedev/ai-memory-mcp/issues/3517) /
  [#3523](https://github.com/alphaonedev/ai-memory-mcp/issues/3523): a
  process-global written under a lock the READERS do not take. The self-hosted
  runner environment was surveyed read-only and carries no passphrase, so no
  operator environment was involved.
  - There is now ONE window for the whole channel,
    `test_support::PassphraseEnvIsolation`: it takes the crate-canonical env
    mutex (`config::test_env_lock()`, the single mutex #3523 unified) AND
    clears `AI_MEMORY_DB_PASSPHRASE` for its lifetime, restoring the prior
    value on drop — including on an unwinding panic. Field order is drop
    order, so the variable is restored BEFORE the mutex is released and no
    other test can observe the cleared value.
  - Seeders cannot bypass it in Rust at all:
    `DbPassphraseGuard::enter` now takes `&PassphraseEnvIsolation`, so seeding
    the slot without holding the shared mutex is not expressible rather than
    merely discouraged. Both seeding tests were converted, and the two
    hand-rolled `remove_var(ENV_DB_PASSPHRASE)` calls in the
    `--db-passphrase-file` test are gone — the window clears and restores the
    variable for them.
  - All eleven `bootstrap_serve` lib tests enter the same window through
    `test_support::no_passphrase_guard()`, which additionally ASSERTS the slot
    is empty. That assertion is sound rather than flaky precisely because the
    seeders hold the same mutex, so a future bypass fails loudly instead of
    flaking. Where a test also needs the caller-identity lock the window is
    taken FIRST, preserving the crate's single lock order.
  - `scripts/check-test-env-lock.sh` gains **arm (f)**, the grep-level twin of
    the type-level rule, over `src/**` (the one lib test binary whose threads
    share the slot). For each `#[test]`-attributed fn body — reusing arm (c)'s
    fn-scoped detector verbatim — it fails on a `set_db_passphrase(` call, a
    `set_var`/`remove_var`/`EnvGuard::capture` of the passphrase variable, or a
    `bootstrap_serve(` boot that holds none of `PassphraseEnvIsolation`,
    `no_passphrase_guard` or `env_lock`. On the tip it reports all eleven naked
    `bootstrap_serve` call sites; `--self-test` plants both violating shapes and
    a correctly-funnelled fixture that must be spared. The arm's documented
    residual (a lib test opening plain sqlite by some other route) is stated
    with the code rather than overclaimed.
  - CI hygiene, explicitly NOT the fix: the self-hosted `check` legs now blank
    `AI_MEMORY_DB_PASSPHRASE` / `AI_MEMORY_DB_PASSPHRASE_FILE` for the job
    before the test step, so a future operator environment on any self-hosted
    runner cannot reach a suite. It is scoped to the named variables rather
    than all `AI_MEMORY_*` because the enterprise-fed leg exports
    `AI_MEMORY_TEST_POSTGRES_URL` through the same channel and a blanket scrub
    would silently send that leg back to the shared database;
    `AI_MEMORY_NO_CONFIG` is kept deliberately.
