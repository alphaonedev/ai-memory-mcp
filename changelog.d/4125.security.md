The wake-hub `seq_high_watermark` is now PER RECIPIENT. It carried the producer's host-wide wake sequence, so the gap between two of one recipient's watermarks counted every other recipient's notifies: a cross-tenant activity-volume side channel, the same channel #4071 (still open, not fixed here) tracks for the inbox SSE stream, which still emits the host-wide `seq`. Each `agent_notified` wake now carries a `recipient_seq` assigned at PUBLISH time (a per-recipient counter next to the host-wide one, taken under the same short lock as the broadcast send, bounded in BYTES (`wake_hub::limits::RECIPIENT_SEQ_BUDGET_BYTES`, 8 MiB; at the budget the least-recently-woken recipient is evicted per entry)), and the wake sink forwards it verbatim, never renumbering it. The self-heal contract is unchanged: a gap in the recipient's own sequence, including one caused by a lagging broadcast receiver, still means one catch-up inbox read, and the <=60 s backstop poll is untouched. Counters start from a wall-clock base, so a producer restart or an eviction from the counter table moves a recipient's number forward (at worst one wake is labelled `gap`, which costs no extra read; only an evicted recipient ever sees such a jump, a documented residual: an observer that floods the table to full with its own ids and keeps its own idle id as a canary learns, per probe, whether any other recipient was woken in a window it chooses and, by varying the flood, a threshold on the number of DISTINCT other recipients woken; it learns no identity, sender, content or per-recipient volume; each probe costs about one table turnover, at least ~26k notifies (128-byte ids), up to ~43k with the shortest ids, each to a distinct recipient and each leaving a durable inbox row; the per-agent daily quota does NOT bound it, locally (the quota is per sender per recipient inbox namespace and the flood targets distinct recipients, #4359) or over federation (applied wakes are charged storage bytes only, #1544/#1156; #4354 is the narrower federation instance of #4359); an observer with k hub identities reads a count rather than one bit) and never backwards across a real gap. A recipient id over 128 bytes is not tracked (it cannot be delivered and would only evict real recipients), the hash table is pre-sized at twice its entry ceiling so churn never grows it, and the client clamps `AI_MEMORY_WAKE_MISSED` to 65,536 because across a rebase the watermark difference is a clock delta, not a count: only `missed > 0` (reason `gap`) is reliable. The wire format is unchanged (same `u64` field) (#4125).
