### Fixed

- **[manageability][fail-open] A wake-hub `subscribe` carried no
  acknowledgement, so a peer's wake sent in the subscribe window was
  unobservably lost**
  ([#3532](https://github.com/alphaonedev/ai-memory-mcp/issues/3532), follow-up
  to [#3505](https://github.com/alphaonedev/ai-memory-mcp/issues/3505)).
  An accepted `subscribe` was answered with NOTHING. A client could not know
  when its namespace subscription went live, and a peer's topic wake addressed
  inside that window fanned out to nobody. The inbox row is the durable truth
  and the `<=60 s` backstop still found it, so the cost was LATENCY and never
  loss — but it was UNOBSERVABLE latency, which is the property a fleet cannot
  manage, and it is the race the #3505 suite had to work around with a
  ping/pong round-trip after every subscribe (deterministic on Linux, hidden on
  macOS).
  - **The hub now ACKNOWLEDGES an applied subscription change**, and the
    acknowledgement is a promise about the router rather than about the frame:
    the topics are added to (or removed from) the routing table FIRST and the
    ack is minted only after that returned. Because one connection's frames are
    read, handled and written in order, a client that has OBSERVED the ack
    knows the route already existed — so any topic wake a peer addresses after
    that point is routed against a table containing this session.
    `unsubscribe` is acknowledged the same way, with the dual guarantee, which
    retires the second documented ping workaround.
  - **The ack is an ECHO of the request's own kind and bytes, not a new wire
    number** — `subscribe` -> `subscribe`, `unsubscribe` -> `unsubscribe`,
    stamped `from` the hub. That is what makes it genuinely additive: the frame
    parser REFUSES an unknown kind byte (`Kind::from_u8`, and the Python SDK
    reader raises on one), so a hub that started emitting a new `subscribed`
    kind would have ENDED the session of every client written before it instead
    of being ignored by one. Kinds 5/6 are already in every reader's table and
    every client ignores a kind it has no opinion about. `hello` is already
    bidirectional, so a direction-disambiguated kind is the protocol's existing
    idiom, and the topic-list payload is the request's own bytes — so an ack
    cannot carry a body, an identity claim or an authority the client did not
    itself send. The wake-only posture (#3466) is unchanged, and no wire
    version, kind number or reserved byte moved.
  - **Acknowledged means APPLIED.** A refused `subscribe` — out of scope, or
    past `MAX_TOPICS_PER_SESSION` — is answered with its `error` and never with
    an ack, so there is no frame that says "listening" for a topic the hub did
    not take. Topics asserted in the `hello` were already acknowledged by the
    `welcome`, which is registered before it is sent; this extends the same
    guarantee to a subscription taken later in the session.
  - **Clients**: `wake_client::Session::send_subscribe` / `send_unsubscribe`
    only WRITE, and liveness is `next_event()` yielding
    `SessionEvent::Subscribed` — keeping the ack in the one ordered event
    stream is what lets a wake that arrives before it be delivered rather than
    swallowed. The Python SDK takes `topics=` and emits
    `WakeReason.SUBSCRIBED`; the TypeScript SDK takes `topics` and emits a
    `subscribed` signal with `subscribedTopics`. All three IGNORE an
    acknowledgement they cannot parse rather than dropping the session: the
    subscription stays unacknowledged, so a caller waiting on liveness keeps
    waiting instead of being told a lie.
  - **Tests**: `tests/wake_hub_subscribe_ack_3532.rs` pins the ordering
    STRUCTURALLY (the hub's own routing table already names the subscriber at
    the instant the ack is observed — an implementation that acknowledged first
    and registered afterwards fails it), behaviourally (a peer wake sent
    strictly after the ack is delivered, with no sleep, ping or retry anywhere
    in the suite), and fail-open (an old-style client that never reads the ack
    still receives its wakes). The four racy `#3505` call sites and the
    `#3468` own-inbox subscribe now order on the ack instead of a ping, and
    `denied_a_subscription_over_the_session_cap_changes_nothing` became a
    frame-for-frame assertion instead of a 200 ms "did anything arrive?" probe
    that scored an empty stream as acceptance.
