An `escalate` agent-action rule now queues a signed-approval pending on every SQLite write funnel that evaluates the governance pre-write hook while holding a write transaction (restore, caller-scoped restore, consolidate, merge_inbound, and any funnel called inside a caller-owned write transaction such as the store-level update). The hook consults on its own connection, so its pending INSERT used to wait out `busy_timeout` behind the caller's writer lock and fail `SQLITE_BUSY`: the escalated write was refused without being queued for approval, and the lock was held for the whole timeout. The signed-approval router now defers the queue write to the write transaction the calling thread holds on that database, which writes it on its own connection the moment the transaction ends; governance evaluation still happens inside the lock. No module-size ceiling is raised: the deferral lives in `src/storage/escalation_deferral.rs` and the red-first cells in a child test module (#4116).

Per the 5-agent vote (D, amended), the caller is never told a pending id that was not written. A funnel that owns its write transaction (restore, caller-scoped restore, consolidate, merge_inbound, and the `in_write_txn` owners that own their transaction) settles the deferred queue write before it returns the refusal, and reports the real outcome: `pending_id=<id>` (the row exists) or `escalation NOT queued: <err>`. When the transaction belongs to an outer caller, the refusal instead reads `escalation deferred: pending_id=<id> will be queued when the enclosing transaction ends; if memory_pending_approve <id> returns not-found, the queue write failed - re-submit`. The SAL update (`SqliteStore::update`) opens its own outer #3957 `WriteTxn` and the governed write joins that transaction; since #4376 the method settles that transaction itself and returns the real outcome too. A leaked or unsettled escalation frame is reported at ERROR: through `tracing` (plus a debug assertion) when detected on the next open or an unknown settle, and as an `ERROR #4116: ...` line written directly to stderr when the thread exits (the `tracing` fmt layer's thread-local buffer can already be destroyed then, and logging through it would abort the process).
