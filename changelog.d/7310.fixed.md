**zip-extract guard catches build-time generated modules (#7310).** A `mod name;` whose file is not where cargo looks fails. The base is resolved per load from the logical path (symlinks are not resolved; the realpath only keys the seen-set and the escape check), as rustc does: a crate root, a `mod.rs` or a file loaded through `#[path]` looks for `name.rs` / `name/mod.rs` beside itself, any plain `mod x;` load of a file looks under `<stem>/`; a file loaded both ways (`mod a;` plus `#[path = "a.rs"]`) must satisfy both bases. A `#[path]` inside an inline `mod y { .. }` resolves under `y/`. A `#[path]` loads at any `cfg_attr(.., cfg_attr(.., path = ..))` depth, and a `path =` key inside a cfg predicate loads nothing. Only an unconditional `#[path]` exempts a `mod`; a `cfg_attr(.., path = ..)` module is not exempt. Every existing `name.rs` / `name/mod.rs` candidate of a `mod x;` is queued and scanned, including outside `src/`. A `mod` declared inside a `macro_rules!` body (including `mod $name;`) fails, because it resolves where the macro is invoked. Every target `src_path` in `cargo metadata` (inline-table, array and auto-discovered forms included, for the root and each local package) is a crate root, is scanned, and fails when it has no file on disk (only a build step could create it). A local package with no `targets` in the metadata is a tool error (rc 2), as is a cargo call that runs longer than 600 s. A manifest-declared path or build script with no file fails. Build scripts are scanned with their string bodies kept (comments still masked).
