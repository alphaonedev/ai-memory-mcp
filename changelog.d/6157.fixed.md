**MCP `initialize` negotiates `protocolVersion` (#6157).** The handshake used
to answer a hard-coded `2024-11-05` and never read the client's requested
revision. `src/mcp/jsonrpc.rs` now carries `SUPPORTED_PROTOCOL_REVISIONS`
(newest first, currently `["2024-11-05"]`) and `negotiate_protocol_revision`:
a supported `params.protocolVersion` is echoed back; an unsupported, missing
or non-string value is answered with the newest supported revision (the
spec's downgrade) and a stderr `MCP initialize downgrade` diagnostic. The
list stays truthful: `2025-03-26` is not listed because it makes JSON-RPC
batch receipt a MUST and the stdio loop answers a batch array with `-32700`.
`tests/mcp_protocol_revision_ssot_6157.rs` pins every `protocolVersion` use
in the whole repository (source, tests, docs, scripts, client shims,
cookbooks, benches; build output, `node_modules`, `vendor` and scratch
directories excluded) to the supported list, does not follow symlinks, and
fails on any file it cannot read or that is not UTF-8. The first-party client
shims, the host-adapter fake-server fixture, the recursive-learning cookbooks
and `benches/harness_bench.rs` now request `2024-11-05`. The downgrade
diagnostic echoes at most 64 escaped characters of the client value and its
own stderr write is non-panicking (`let _ = writeln!`); the remaining
`eprintln!` sites in the stdio loop are tracked in #6191. The former public
`ai_memory::mcp::jsonrpc::PROTOCOL_REVISION` remains as a `#[deprecated]`
alias of `NEWEST_PROTOCOL_REVISION`. No wire shape change: the field already
existed.
