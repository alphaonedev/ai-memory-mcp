**A failed audit write no longer glues the next record onto a fragment (#4211).** The flat audit trail wrote each record with `writeln!`, which issues the record and its newline as separate writes. A disk that filled mid-record left a fragment with no newline, and the next successful record was appended straight onto it: that record was counted as written but could never be parsed, and `audit verify` stopped with `Parse` there, so every later event went unverified and the loss never surfaced as a gap. Each record and its newline now go out as ONE buffer through ONE write, under an exclusive lock on the trail file that every ai-memory writer takes. When a write fails part-way, the bytes it left are truncated away, but only when they are provably that write's own, so the trail is exactly as before and the lost event is an ordinary, acknowledgeable gap; if only the newline was missing, the line is finished and the event is not lost. When the leftover cannot be removed (the append-only OS flag, the macOS default under `append_only_hint`, refuses truncation), the next record starts a new line and `verify` reports the leftover as a new `TornRecord` failure kind (JSON: `"kind":"TornRecord"`, additive `torn_lines`): never clean and not acknowledgeable, but the chain is checked across it, so later records stay verified and the gap is still reported. An unparseable line the chain does not pass around is still `Parse`. Decided by a 5-agent vote.
