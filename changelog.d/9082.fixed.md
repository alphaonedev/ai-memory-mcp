**Federation pull serves every row, whatever its own `updated_at` (#9082).** `/sync/since` filtered by the row's own `updated_at`, a value the writing peer chose. A row relayed to a node with an old timestamp, or committed by a slower PostgreSQL writer after a faster one, sorted below a puller's cursor and was never pulled, with no error. Schema v102 adds `memories.sync_seq`, a number the SERVING node assigns from a one-row counter (held to commit on PostgreSQL) on insert and on a real change of a replicated column; existing rows are backfilled in `(updated_at, id)` order. A puller now sends `after_seq` and walks that sequence: the server filters by `sync_seq` only and answers with `next_seq` (the highest sequence it examined) and `seq_epoch`; the puller keeps its cursor per peer in the new `sync_pull_seq` table and restarts at 0 when the peer's epoch changes (a restore or re-init regenerates it). A malformed sequence answer applies nothing and moves no cursor. A node built before v102 answers without `next_seq` and is pulled on the timestamp path as before. Known limits: hard deletes are not carried on either path, and a puller built before v102 keeps the timestamp hole.
