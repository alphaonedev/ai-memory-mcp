**Several processes writing the same forensic audit log no longer fork its chain (#4304).** Each process read the chain tail once at start and chained every later row from its own in-memory head, so a row written by any other process in between (a CLI command while `serve` or `mcp` ran, or two commands at once) was skipped: the next row named a stale predecessor and `verify` reported a chain break with no tampering behind it. Every forensic append now takes an exclusive lock on `forensic.lock` in the forensic directory, compares the daily file with what this process last left there (path, device, inode, length, modification time), re-reads the tail when anything changed, and forms, signs and writes the row while still holding the lock. `serve` and `mcp` now sign on the background writer thread rather than the request thread, because the predecessor is only known under the lock. A daily file that is the same file but shorter than this process left it was truncated, not appended to, so the next row still continues this process's own head and the removed rows show as a break, as before. A row is in the chain only once it is on disk: a failed write no longer advances this process's head, so the next row continues the file. That also means a row lost to a failed write is no longer marked by a chain break; it is still counted in `ai_memory_forensic_sink_unavailable_total` and reported on stderr. The lock file is created owner-only (0600), and an append waits at most 1 s for it: `flock` needs only read access, so a holder that never lets go must not stall every audited write. If the lock file cannot be opened, or is still held after that second, the append still re-reads the tail for every row and goes ahead, counted in the new `ai_memory_forensic_lock_unavailable_total` and logged once as a warning; two unlocked appenders can still interleave in that state. If an append needs to re-read the tail and cannot, the row is not written (chaining it from a guess would fork the chain) and the failure is counted in `ai_memory_forensic_sink_unavailable_total`. An in-place rewrite that keeps the file's length and lands within the file system's timestamp granularity of this process's last write is not detected as a change; that is tampering, which `verify` reports. The one-write row append from part 1 of #4304 is unchanged.
