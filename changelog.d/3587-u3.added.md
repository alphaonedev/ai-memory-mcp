**#3587 U3 — curator stale-ruling sweep.**

The curator now runs a stale-ruling pass right after `run_size_gc_pass` and
BEFORE the no-LLM early return, and on demand via the new
`ai-memory curator --stale-rulings` one-shot. A ruling is a memory tagged
`ruling` or carrying `metadata.ruling_key` (`field_names::RULING_KEY`); it is
stale when it is live (not archived), older than `[curator].stale_ruling_days`
(default 14, named const `DEFAULT_STALE_RULING_DAYS`), and carries no
supersede / verify marker (`superseded_id`, `superseded_by`, `verified_at`).
For keyed rows only the LATEST `(namespace, ruling_key)` is reported; older
same-key rows are already-superseded history.

The pass is a pure SELECT on both backends — it NEVER writes to a ruling row,
so a ruling's `version` / `updated_at` are unchanged and the
`archived_memories` delta is 0 (pinned by `_pg` twins of every acceptance
test).

When `[curator].notify_agent_id` is set the pass sends at most ONE
`Tier::Short` digest per stale-id-set hash through `handle_notify_as_sender`,
using the curator's OWN resolved id as the sender (`notify_agent_id` is a
recipient only, validated against the reserved-id set at boot). Dedup is the
stale-id-set sha256 plus a hard floor — the named const
`STALE_RULING_NOTIFY_FLOOR_SECS = 86_400` — stored in a single `_curator/state`
row, so a stable stale set pings once a day rather than once a cycle
(anti-storm precedent #3345). An unset recipient, or `--dry-run`, detects and
reports only. `CuratorReport` gains `stale_rulings_found`,
`stale_rulings_notified`, a capped `stale_ruling_ids` list (persisted to
`_curator/reports`) and the full `stale_ruling_ids_all` (in-memory / `--json`
only).

Both new knobs are CONFIG-FILE-ONLY — there is deliberately no `AI_MEMORY_*`
override. `--stale-rulings` joins the `conflicts_with_all` sets of `--once`,
`--daemon`, `--prune-reports`, `--reflect` and `--rollback`.
