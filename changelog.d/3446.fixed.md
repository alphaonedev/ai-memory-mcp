### Fixed

- **[data-integrity][federation] The `cid` pre-image committed `created_at` as
  raw TEXT, so re-minting an address from a stored row disagreed across
  backends**
  ([#3446](https://github.com/alphaonedev/ai-memory-mcp/issues/3446)).
  `identity::cid::canonical_cid_preimage` joins `created_at` in as TEXT, and the
  two backends do not return the same text for the same instant: SQLite keeps a
  `TEXT` column and hands back the string it was stamped with (chrono renders
  nanoseconds on Linux), while PostgreSQL keeps `TIMESTAMPTZ` (microsecond int8)
  and re-renders the readback through `DateTime::<Utc>::to_rfc3339()` (`+00:00`,
  `AutoSi` digits). Every path that RE-MINTS a cid from a row read back out of
  storage therefore minted a **different address on the two backends for the
  same logical memory** — the v74 `backfill_memory_cids` migration
  (`storage/migrations.rs`, which re-reads each row through `row_to_memory`), a
  supersede/re-store, a federation reconciliation, a forensic re-derivation.
  `verify_cid` was never affected (it recomputes from the stored `cid_genesis`
  BLOB), which is why this stayed latent. Flagged by the #3422 review.
  - **The control.** `created_at` is folded through the #3422 canonicaliser
    (`identity::attest::canonicalize_attested_created_at`: parse RFC3339 → UTC →
    truncate to microseconds → `to_rfc3339()`) **inside
    `canonical_cid_preimage`** — the ONE funnel that all 19 mint sites across
    both backends already share (`stamp_memory_cid` → `stamp_cid` →
    `canonical_cid_preimage`), so no site is enumerated and no future site can
    miss it. It sits beside the existing mode-independent
    `secret_screen::screen` fold of `title`/`content`, and carries the same
    intent: **the pre-image commits to the *instant*, never to a per-backend
    rendering of it.**
  - **Existing addresses are untouched, by construction.** `cid_genesis` stays
    the authoritative pre-image for an already-stored row and `verify_cid`
    recomputes from that BLOB — never from the row's fields — so every minted
    `(cid, cid_genesis)` pair keeps verifying byte-for-byte. Nothing rewrites a
    stored `cid`. Only pre-images minted from here on are canonical, and only
    for rows whose `created_at` was not already in the canonical rendering.
  - **Unparseable stamps are committed verbatim**, which keeps
    `approvals::execution_exemption_cid` — the one caller that deliberately
    passes `created_at = ""` so an approve-time key matches the re-stamped
    replay — byte-stable across this change (pinned by a regression test that
    reconstructs its exact pre-image).
  - Regression coverage for the allowed and the denied direction on BOTH
    backends: `tests/cid_created_at_canonical_3446.rs` (sqlite mint → store →
    read back → re-mint reproduces the address; the two backend renderings of one
    instant mint one cid; a *different* instant still mints a different one; the
    stored genesis still verifies — and, against the live cluster, the issue's
    exact ask: sqlite-side mint → postgres `TIMESTAMPTZ` store → readback →
    re-mint → identical `cid` **and** identical pre-image bytes), plus five
    `identity::cid` unit tests including microsecond truncation, instant-pinning,
    and the pre-#3446 genesis staying authoritative.
  - Documented in `docs/attestation.md` beside the #3422 `created_at` contract.
