- **A daemon booted over a backlog of unembedded rows stopped responding while
  it embedded them**
  ([#3988](https://github.com/alphaonedev/ai-memory-mcp/issues/3988)).
  At `serve` boot a detached task re-embeds every row that has no vector
  (#1579 A4, sqlite since #2639). It ran each 100-row chunk's `embed_batch` (a
  CPU-bound model forward pass) inline on a tokio worker thread instead of on
  the blocking pool.
  - **Effect.** While a chunk was being embedded, the process did not
    respond. Tokio 1.52.2 reverted LIFO-slot stealing (tokio#8100), and this
    tree moved from 1.52.0 to 1.53.1 in #3940. Since then, work parked behind
    the busy worker, such as the postgres pool acquire behind `/health`, stays
    stranded until the embed returns.
  - **Measured on a debug build** with 1,500 unembedded rows on PG 18 + AGE
    1.8: boot took 3 min 48 s to bind. Over the next 5 minutes, `/health`
    answered 1 of 456 probes.
  - **Found by.** Promotion 4: `signed_events_fresh_store_signs_3354_pg` never
    became healthy on linux-fed, macos-fed and the coverage leg. Earlier tests
    had filled the shared per-job database with rows written without an
    embedder.
  - **Fix.** Each chunk now embeds on `spawn_blocking` (rust-1.98
    CONCURRENCY-22). A panicked or cancelled embed stops the sweep without
    writing anything, so those rows stay keyword-recallable and are retried on
    the next boot.
  - **Test.** `backfill_sweep_embeds_off_the_runtime_worker_3988` pins the fix
    on a one-worker runtime.
  - **Related.** The pg test's own hermeticity and stderr draining landed
    separately in #4019. With #4019 the test runs with the embedder off, so
    it no longer exercises this path. The unit test above does.
