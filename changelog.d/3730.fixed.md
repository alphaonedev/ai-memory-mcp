**The agent inbox has a handled state: drain it by deleting, and reads never mark anything (#3730, data-integrity, GA).**

`memory_inbox --unread-only` inferred "unread" from `access_count == 0`, a TOUCH counter that no inbox operation ever advanced (only a namespaced `recall` plus the periodic #1869 fold did), so an agent draining with `inbox` then `get` never marked a message read and a redelivery loop keyed on the marker re-sent the same message forever. Measured on the fleet's own wake plane: 50 of 50 messages unread while the operator's side ledger held 237 handled ids. Now the inbox is the PENDING set: a recipient declares a message handled by **deleting** it (`memory_delete`, `DELETE /api/v1/memories/{id}`, `ai-memory delete` — the recipient is already authorised), and every message still listed is unhandled. Inbox reads stay pure (#1869); no read path writes.

- **Delete retention policy for the inbox (both backends):** `delete` means remove from the caller's view; whether a copy is RETAINED is a retention policy that varies by namespace, and the inbox's is now specified — a message in `_inbox/<agent>` (legacy `_messages/`) is ARCHIVED on `memory_delete`, HTTP `DELETE`, and both SAL stores (`archive_reason = "delete"`, listed by `memory_archive_list`, restorable), exactly as the CLI `delete` already did for every row (#3012). Every other namespace keeps its erasure semantics. The disposition is on the wire: `archived: true|false` on the MCP, HTTP and CLI delete responses. `ai-memory delete --hard` on an inbox message still erases, and prints one line naming what it destroys first.
- **`read` is gone from the inbox wire shape** (it reported touches as reads); `access_count` stays under its own name. `unread_count` equals `count` by contract.
- **BREAKING, permissive direction:** `unread_only` is accepted for compatibility and now narrows NOTHING (its contract is stated in the tool docs and `--unread-only` help). The `AND access_count = 0` pushdown is retired on both backends, so `--unread-only` starts RETURNING messages it used to hide once a recall had been folded: a consumer whose loop depended on that hiding sees MORE, not fewer. The `Filter::unread_only` SAL axis and the `list_filtered` parameter are removed.
- **#3463 dissolved, not reverted.** #3463 pushed the unread narrowing into SQL because an agent whose newest `limit` rows were all read got `unread_count: 0` while older unread messages sat behind the page. With no read rows in the inbox there is nothing for the limit to be spent on; its pins are retargeted to the new contract and say so.
- **The recipient's delete admission is DERIVED from the namespace, on every funnel (security).** The addressed recipient (`metadata.target_agent_id`) is admitted to delete a row it did not author ONLY when that row lives in an inbox namespace — the one case the retention policy archives. Before this fix the admission was a bare `allow_inbox = true` asserted beside the namespace routing rather than derived from it: on sqlite (`SqliteStore::delete`, MCP `memory_delete`, HTTP `DELETE`) that pre-dated #3730, and the r4 postgres "parity" commit copied it to `PostgresStore::delete` — so a non-owner who merely had a row ADDRESSED to it could sever, tombstone and crypto-erase that row in ANY other namespace, an irrecoverable loss by someone who was never the owner, reachable by writing `target_agent_id` into a row's metadata. Now the namespace is looked up first and `inbox_delete_retains(namespace)` is what the gate receives, at all four sites, so the gate and the disposition read one value and cannot drift. Measured on the reviewer's probe (2026-09-15): RED on r4 `14748e776` on both backends, GREEN on this fix; on the `c3ba52943` base postgres refused the recipient outright (the r4 commit introduced it there) while sqlite already erased. Pinned by `tests/recipient_gate_derived_from_namespace_3730.rs`, one cell per funnel, each driving the FORBIDDEN path then the permitted drain as its control — the existing drain pins could not see this because they only exercise the inbox namespace, which is exactly the case the defect exempted.
- Widening archive-on-delete to every namespace (a change to erasure semantics a customer who deletes IN ORDER TO ERASE is owed a decision on) is deliberately separate: tracked for v1.0.1.
