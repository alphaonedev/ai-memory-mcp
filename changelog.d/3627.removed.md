**Removed: one LLM provider alias, and unrecognised backend selectors are
now refused (#3627, operator directive 2026-09-11).**

**What it costs you.** Any selector the substrate does not recognise — the
retired token, a typo like `opena1`, or an arbitrary label such as `tei` /
`litellm` that used to work as long as you also supplied an explicit
`base_url` — is now REFUSED at client construction, on
`AI_MEMORY_LLM_BACKEND`, `[llm].backend`, `AI_MEMORY_EMBED_BACKEND` and
`[embeddings].backend` alike. Previously it silently built a client against
`http://localhost:11434` with your Bearer token attached; on the embed side
it returned vectors from a model you never chose, which is wrong recall
ranking rather than a visible failure. **Remedy:** switch to a recognised
selector, or — for a self-hosted OpenAI-compatible endpoint (TEI, LiteLLM,
llama.cpp server, vLLM behind a proxy) — use `openai-compatible` with an
explicit `AI_MEMORY_LLM_BASE_URL` / `[llm].base_url`. That is the documented
escape hatch and it is unaffected.

**Degrade, not die.** `serve` and `mcp` still boot: the LLM client resolves
to `None` with a `WARN` naming the backend and LLM hooks become no-ops; a
refused embed selector logs `EMBEDDER LOAD FAILED … Semantic recall DEGRADED
to keyword` and keyword recall continues. Stored memory text, embeddings and
indices are untouched. `reembed` exits `3` (`EXIT_EMBEDDER_INIT_FAILED`)
rather than re-embedding with the wrong model; `atomise` returns
`atomise: LLM init failed (backend=…)`. Two surfaces stay quiet: `curator`
discards the error via `.ok().flatten()`, so a refused selector there yields
no client and no message; and `doctor` does NOT report the refusal — its
reachability probe never consults the selector gate and still probes the
resolved URL with your API key as a Bearer. Both are pre-existing, not
introduced here, and tracked in #3811.

**Model-family attestation.** The retired vendor's stem also leaves the
`src/identity/model_family.rs` classifier. The live consequence is an
Ollama-served open-weights model whose *name* carries that stem (an
`AI_MEMORY_LLM_MODEL=<retired-vendor>-r1:8b` on `backend = "ollama"`; the
CHANGELOG `Removed` entry spells it out): it previously
received a `loader_observed` family attestation from
`cli/curator.rs::capture_loader_attestation` and now records as CLAIMED with
no family. Existing rows keep their stamped family — nothing durable is
rewritten — so such a corpus becomes mixed-attestation. Fail-safe direction:
unattestable reads as "we do not know".

**Why general.** Deleting the alias arms alone could not fail closed:
`AppConfig::resolve_llm` is infallible and its `backend_default_base_url`
catch-all hands an unknown alias the loopback Ollama URL. A refusal narrowed
to the retired token would have left that hole open for every other
unrecognised value and would have had to keep the token in the source.

Alias tables, per-vendor key/model maps, model-family stem, vendor-literal
gate pattern, current docs and the v1.0.0 capabilities inventory drop the
row. Historical release records, the dated review records under
`docs/reviews/`, and two published-research citations keep the name. The
retired token itself is named in the CHANGELOG `Removed` entry.
