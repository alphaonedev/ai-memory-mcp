The count-assertion gate (`scripts/check-count-assertion-declared.sh`) compares the assertion set of every `.rs` file under the repository-root `src/` and `tests/` directories (#5711, #5716; a nested crate such as `tools/<name>/src/`, and `examples/`, `benches/` and `fuzz/`, are not checked) between a commit and its parent (rename and copy sources included) and flags every assertion `assert_eq!(<expr>.len()|.count(), <rhs>)` or `assert!(<expr>.len()|.count() == <rhs>)` (a trailing message argument is ignored, and a prefixed macro name such as `debug_assert_eq!` or `debug_assert!` matches too) whose count moved, appeared or disappeared (#5499, #5517, #5518, #5710). The whole first argument decides what is read (#5759): an `assert_eq!` is read only when its first argument is one operand that ends in the count call (a first argument whose last term is not exactly `.len()` or `.count()`, such as a tuple, a cast, `v.len() + 1`, `f(v.len())`, a path call such as `<[u8]>::len(v)` or `v.len ()` with a space inside the call, is neither read nor tracked; #5799, #5801), and an `assert!` is read only when its first argument has exactly one `==` and no `&&` or `|` outside every bracket and its left operand ends in the count call, so a comparison inside a closure, as in `v.iter().filter(|x| x.len() == 2).count() == 3`, binds to the outer count; any other `assert!` first argument in which the left operand of some `==`, at any bracket depth, holds a count call (`.len()` or `.count()`, spaces allowed after the dot and inside the call, never an argument) is ambiguous (#5797, #5798): that operand runs back from the `==` to the nearest `&&`, `||`, `==`, `!=`, `=>`, comma or semicolon at the same depth, or to the bracket that opens that depth, so nothing between the call and the `==` other than one of those stops hides it (a cast to any type, braces, a block comment, a generic argument list, a method chain such as `.into()`, a line break or arithmetic), and a comparison inside a closure only, behind `&&` or `||`, negated, parenthesised or chained with a second `==` is ambiguous exactly when such a left operand holds the count call; an ambiguous `assert!` is tracked under its whole spelling with the value `?count#ambiguous`, which is never exempt, and every const name in it is tracked with that const's resolved value. Inside the arguments of an `assert!` or `assert_eq!` a `/* */` block comment, nested ones too, is blank space, and a generic argument list `<..>` (after `::`, after the type path that follows `as` or `->`, or a qualified path at the start of an operand; as rustc reads it, a `<=`, a `<<=`, a `<` after `as _` and a `<` right after the `>` that closes a generic list compare and open nothing; #5960, #5961) is a bracket, so an operator, a comma, a semicolon or a bracket inside either never ends an operand, splits an argument or hides a compare (#5872, #5873). An assertion whose arguments cannot be read (a block comment with no closing `*/`, which is also what a quote or a `//` inside a block comment becomes until #5715 brings a lexer; or, in arguments that hold a count call, a generic argument list with no closing `>`) is tracked as `!unreadable line <N> (<reason>): <spelling>` with the value `?count#unreadable`: it is red in every commit that changes its file or moves a const or static, of any type and any name case, that file names, or a const defined through one of those (#5888, #5963, #5965), it cannot be declared, and one that leaves the tree is a count change `?count#unreadable -> (none)`, declared as usual. An assertion whose values are all undecidable `?<spelling>` values that hold no `#` is not flagged when it appears or disappears, `//` line comments and double-quoted string literals are not read, outside the arguments of an assertion a `/* */` block comment is read as code (so an assertion inside one is read), and a raw string is blanked only up to its first inner quote (#5715), and reversed operands (a count call only on the right of every `==`, as in `assert!(18 == v.len())` or `assert!(ok && 18 == v.len())`) and `assert_ne!` are not read (#5712, #5714), nor is an `assert!` whose count is compared without `==`, such as `v.len().eq(&18)` or `matches!(v.len(), 18)` (#5800), or whose count is a path call such as `<[u8]>::len(v)`, a free function such as `row_count()` or a call with an argument such as `m.count(k)` (#5801). A brand-new assertion is skipped only when its file is added in that commit and the same expression or const name does not exist in any checked `.rs` file of the PARENT tree; the same expression added in two new files of one commit is skipped in both. The right-hand side is read in full (decimal, `0x`, `0o`, `0b`, underscores and type suffixes are normalised; any other right-hand side is an undecidable `?<spelling>` value that a declaration must repeat: whitespace is dropped, kept as `~` between two word characters, a comma is written `;` (#5966), and every const or static of the tree it names follows after a `#` as `#NAME=<value>`, expanded the same way, a cycle as `#NAME=cycle`, so a cast, `.get()` or arithmetic over a const moves with that const; #5964, #5965), and a named const or static is resolved over every checked `.rs` file of the tree, so a const bumped in another checked file moves every assertion spelled through it, also through a const defined by it (#5965); a name that does not resolve to exactly one const is read as an undecidable `?NAME#unresolved` or `?NAME#ambiguous(<value>|<value>...)` value, so a commit that changes that state or newly asserts such a name is flagged, and an identical state on both sides is no move (#5577, #5578). A move is accepted only when the commit's own `Count: <what> <old> -> <new> (<why>)` trailer, or a later `Count-Declared: <40-char sha> <what> <old> -> <new> (<why>)` trailer of the same range, names it: `<what>` is the whole expression, or words of which at least one is a whole token of the expression or of the file-name stem other than `len`/`count` and the rest are prose of at least 3 characters (a word with a one- or two-character chunk, or a punctuation-only word, refuses the item; #5712), and items are consumed one-to-one, one item per changed assertion (#5575, #5576). The workflow chooses the range only through `scripts/ci-commit-range.py` (#5579), which refuses what it cannot decide and has no fallback range: `pull_request` runs merge-base(base, head)..head; `merge_group` runs `merge_group.base_sha..head_sha`; `push` runs `before..sha` only when `before` is a full, non-zero, 40-char lowercase sha that resolves to a commit in the checkout; any other event, or a missing, zero, malformed or unreachable sha, is a red job (exit 1), never a one-commit check. Limits: a creation push (all-zero `before`) is a red job, and a force-push is checked over `before..sha` when the previous tip is present in the checkout as a commit object (whether or not a fetched branch or tag still contains it) and is a red job when that commit object is absent; and the `merge_group.base_sha` field is taken from the GitHub event payload and has not yet been observed in a real merge-queue run. Carrier-history offenders outside the range are not checked. Merge commits are exempt by design.
