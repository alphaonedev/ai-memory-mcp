### Fixed

- **[security][fail-open] `memory_skill_export`'s `target_folder` was unjailed —
  an arbitrary-directory write primitive from an unprivileged MCP tool**
  ([#3357](https://github.com/alphaonedev/ai-memory-mcp/issues/3357)).
  The register side got its path jail in #1923
  (`AI_MEMORY_SKILLS_IMPORT_ROOT` + canonicalize + `starts_with`); the export
  side did not. `handle_skill_export` passed the caller's `target_folder`
  straight to `create_dir_all` + `write`, so any co-located agent could create
  directories and write `SKILL.md` / `resources/` anywhere the daemon user
  could reach: a relative `<workdir>/../jail-escape-probe` left the working
  root, and an absolute `/etc/...` was stopped only by filesystem permissions
  (`EACCES`) — no guard of ours ever fired.
  - Export is now confined to an **export root**, resolved fail-closed:
    `AI_MEMORY_SKILLS_EXPORT_ROOT` when the operator sets one (it must already
    exist — an operator root is never created, so an env typo REFUSES rather
    than silently minting a jail nobody meant), otherwise a `skills-export`
    directory **beside the resolved store** — the parent of the `--db` path the
    process opened, the same store path already threaded to every other
    path-taking handler — created on first export with mode `0700`
    (`DirBuilder::mode`, so the group-writable window never exists; same #3198
    posture as the identity key directory). If neither rung resolves to an
    existing directory the export is REFUSED; it never degrades to an
    unconfined write.
  - The process working directory is deliberately NOT the fallback root: a
    daemon's CWD is arbitrary — frequently `/` or `$HOME` — which is not a
    jail. Anchoring on the store ties the jail to the deployment the operator
    actually launched.
  - The target is confined *before any I/O*: a `..` component is refused
    lexically, a relative target is anchored at the root, and the deepest
    existing ancestor is canonicalized — so symlink traversal out of the root
    (`<root>/link -> /etc`) collapses and is refused. Containment is
    **re-asserted after `create_dir_all`**, closing the create-then-swap
    window before `SKILL.md` is written.
  - Every wire surface goes through one funnel: the MCP dispatch, the
    admin-gated `POST /api/v1/skill/{id}/export` route and the
    `ai-memory skill export` CLI all call `handle_skill_export(conn, db_path,
    …)`, which resolves the root and delegates to the new root-taking
    `handle_skill_export_in_root`. Confinement applies identically to both.
  - Regression pins for BOTH directions: DENIED — `..` escape (and nothing
    created), absolute `/etc` refused before any I/O, symlinked component
    leaving the root, a missing configured root (and it is not created for
    you), a file as root, an in-memory store with no configured root, an
    unresolvable root at the handler; ALLOWED — in-root relative and absolute
    exports still write `SKILL.md`, and the export root itself is a legal
    target. The **default** root is pinned by name, location and `0700` mode,
    and asserted to differ from the working directory.
  - Documented in `docs/API_REFERENCE.md` (*Skills export root*) and
    `docs/CLI_REFERENCE.md`.
  - Operator note: exporting **outside** the store-adjacent `skills-export`
    directory now requires `AI_MEMORY_SKILLS_EXPORT_ROOT` to name an existing
    root that contains the target.
