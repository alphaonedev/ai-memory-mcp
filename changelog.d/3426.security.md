Cross-owner authorization refusals no longer disclose the owning agent id, on
either backend. `PUT /api/v1/memories/{id}`, `DELETE`, `promote`,
`GET /api/v1/kg/timeline`, `POST /api/v1/kg/invalidate` and
`POST /api/v1/links` all answered `403` with an `"owner"` field naming the
agent that holds the row, and both SAL twins of
`assert_caller_owns_for_mutation` interpolated the owner into
`StoreError::PermissionDenied.reason`, which `store_err_to_response` renders
straight into the 403 body — its sanitizer redacts URLs and filesystem paths,
never principals. A caller with a row id it was not entitled to therefore
learned who holds it: a cross-tenant identity oracle on the certified tier.

Every refusal on the HTTP surface is now built by one constructor,
`handlers::parity::owner_gate_refusal`, which takes no owner parameter — a
refusal built through it is structurally incapable of naming the owner, so the
disclosure cannot be reintroduced by copying a neighbouring `json!` literal.
The SAL twins refuse with the bare `errors::msg::CALLER_DOES_NOT_OWN_MEMORY`
const, byte-identical on both backends. Operators keep full `caller != owner`
attribution in the server-side `ai_memory::authz` trace line.

Folding #3339: the sqlite write path also stopped being an existence oracle.
For a row the caller cannot READ — another agent's `private` row, which is the
default since a row with no `metadata.scope` key is private — update, delete
and promote now return the same `404 {"error": "not found"}` the read path
returns, instead of a `403` that confirmed the id exists.

This is not a new posture — it is the house rule these three routes were
missing. `GET` has masked since #927; `POST /api/v1/archive/restore` returns
404 rather than 403 for a non-owner "so the surface cannot be used to
enumerate other owners' archived ids" (#940), and `DELETE /api/v1/archive`
returns `{purged: 0}` for the same reason (#936); and the postgres branch of
update/delete/promote already masked, because its handlers read through a
visibility-scoped `store.get` that yields `NotFound`. The `403 (not 404)` note
#930 left on the sqlite update path was the outlier, and it predates #3339.

A row that is readable but unowned (`collective`) still refuses `403`, where
masking would be a lie. The change is denial-preserving — every mutation
refused before is still refused, only less informatively.
