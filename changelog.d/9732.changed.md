CI speed (#9732): a pull request into a `chain/**` branch now restores a warm Rust cache for the android leg of `Cross-compile (aarch64-linux-android)`, the leg that builds the pinned cargo-audit binary and the release-profile smoke (#9680). That leg's cache was keyed by a `key:` input that rust-cache suffixes with the job id, and only a trunk push ever saved it, so a chain pull request found no entry and built both cold. The leg now keys by `shared-key: mobile-aarch64-linux-android-audit-release` under the chain generation `prefix-key: chain-cache-g1`, and `.github/workflows/rust-cache-warm.yml` gains the push-only, hosted job `mobile-android-audit-release`, which runs the leg's exact cargo lines (the target check, the pinned `cargo install cargo-audit`, `cargo build --release`) with the same toolchain, NDK steps and key environment, and saves the same key on each `chain/**` push. The pull-request step still saves only on a `push`, so a pull-request run never writes a cache the chain reads; the iOS leg of the same job stays unpaired (#9681 V-12). `scripts/ci/tests/test_chain_android_cache_9732.py` pins the pair, and the #9681 save-scope test counts it as the third pair (six paired cache steps) under the one generation constant. This corrects the #9681 note that the warm job runs neither the release smoke nor cargo-audit: the third warm job, `mobile-android-audit-release`, now runs both builds for the android leg. The 9732 test also compares every key of every mirrored step and of the job-level inputs of the two jobs (`runs-on`, `env`, `defaults`, `container` and the rest) against a hand table of the keys allowed to differ, so an added or changed step `env:`, `with:`, `run:` or `if:` on either side fails the test. No required-check name changes, no self-hosted step changes, and no gate decision logic changes.
