**Receiver lifecycle state is a federation merge barrier; an accepted signed nonce is never replayable.**
Closes #9147, #9149, #9150, #9140 and #9192 (umbrella #8741; wire envelope #9234), on SQLite and PostgreSQL.

- A row the receiver holds at a hidden state (archived without a live copy,
  quarantined, contaminated, federated-deleted) is no longer made live again,
  and the bytes behind a hold no longer change, through any inbound funnel
  (`apply_remote_memory`, `merge_inbound`, `restores[]`, the archive-restore
  verb). A barrier hit is an idempotent no-op inside the funnel's write
  transaction. `dequarantine` lifts a hold only when the stored
  `attest_level` is `agent_attested` (#9150).
- **A barrier drop is never counted as applied.** The `/sync/push` response
  counts barrier drops in the new field `merge_barrier_dropped`, apart from
  `applied` (which counted them before) and from `skipped` (which would make
  the sender dead-letter the push). The counter
  `ai_memory_fed_merge_barrier_dropped_total{barrier}` (labels `tombstoned`,
  `archived`, `quarantined`, `contaminated`) moves once per dropped row on
  both backends; catch-up no longer counts a drop as applied and
  `ai-memory sync` no longer counts one as pulled or pushed.
- **Nonce replay (#9140, #9192).** The signed nonce carries no time, so the
  replay window is the lifetime of the signing key. Every accepted
  `(signing key, nonce)` pair is one row in the v103
  `federation_nonce_claims` table of the receiver's store, keyed by
  domain-separated SHA-256 fingerprints of the verifying key and of the
  length-prefixed nonce. One `INSERT ... ON CONFLICT DO NOTHING` decides; no
  row is ever pruned. The namespace is the verifying key, so `/sync/push` and
  the signed `GET /sync/since` share it, and a peer removed and re-added with
  the same key still has its old nonces refused. A sibling daemon over the
  same store refuses a nonce the other daemon accepted. Rows of the sqlite
  v51 `federation_nonce_cache` table are still honoured (read-only lookup).
  The in-process cache is a bounded cache only: every check asks the store,
  and evicting a cache entry never makes a nonce fresh again.
- **The claim is made only after the signature verifies**, so a forged
  request adds no row. A nonce longer than 256 bytes
  (`FEDERATION_NONCE_MAX_BYTES`) is refused with 401
  `x_memory_nonce_oversize` before any claim.
- **Fail closed, retryable.** When the store cannot answer a claim (store or
  disk error, a failed commit), push and signed GET return **503**
  `{"error":"nonce_store_unavailable"}` for new and already-cached nonces
  alike, nothing is admitted, and the counter
  `ai_memory_federation_nonce_store_unavailable_total` moves. A per-op
  transition nonce that cannot be claimed skips that op. The daemon no longer
  falls back at boot to an in-memory-only nonce cache.

**What it costs you.** A replay that used to return 200 (after a restart,
after 10 000 newer nonces, from a sibling daemon, on the other route) now
returns 401 `x_memory_nonce_replay`. Each accepted signed push and signed GET
adds one claim row: about 162 bytes on SQLite and 235 bytes on
PostgreSQL, PRIMARY KEY index included (measured at 100 000 rows). A peer
polling `GET /sync/since` every 30 s adds 2 880 rows a day. The claims are
per receiver store: a database restore forgets the claims made since the
backup, and a request captured on its way to one receiver can be replayed to
a different receiver that never saw it.
