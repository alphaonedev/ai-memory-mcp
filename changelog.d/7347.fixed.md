**Test processes no longer race `getenv` against `setenv` in `federation_pending_resurrection_2529` (#7347).** The sync test `upsert_sql_does_not_clobber_decided_status_2529` called `db::open`, which reads the process environment, without the `ENV_LOCK` that its three sibling tests hold while they write the environment, so under `cargo test` (all tests are threads of one process) glibc `getenv` could read a freed `environ` block and the binary died with SIGSEGV. It now takes the lock. A new gate `scripts/check-test-env-mutation.py` (CI job `test-env-mutation-gate` in `c8-precheck`) requires every test fn of a `tests/*.rs` that calls `env::set_var` or `env::remove_var` to hold a lock, or the file to declare `// env-mutation-gate: process-isolated -- <reason>`; the existing violations are the ratchet baseline `scripts/qc-allowlists/test-env-mutation-unlocked-baseline.txt`, which may only shrink. The gate checks that a lock is taken, not that it is the same lock the writers use.
