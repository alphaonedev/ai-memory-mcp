**Test processes no longer race a C-level `getenv` against `setenv` in `federation_pending_resurrection_2529` (#7347, #7355).** The sync test `upsert_sql_does_not_clobber_decided_status_2529` called `db::open` without the `ENV_LOCK` that its three sibling tests hold while they write the environment. Under `cargo test` all tests are threads of one process, and the first SQLite open runs the bundled SQLite's `unixTempFileInit`, which calls C `getenv("SQLITE_TMPDIR")` / `getenv("TMPDIR")` without a lock; racing a sibling `setenv` / `unsetenv` it could read a freed `environ` block and the binary died with SIGSEGV. Rust `std::env` reads are guarded by std's own env lock and only see a stale value, so they are not the crash path. The test now takes the lock. A new gate `scripts/check-test-env-mutation.py` (CI job `test-env-mutation-gate` in `c8-precheck`) scans every `tests/*.rs` that mutates the environment, directly or through the tests/common guards, and requires each test fn that can reach an env or C reader to hold the lock the writers use before its first SQLite open, or the file to declare `// env-mutation-gate: process-isolated -- <reason>`. Existing violations are the per-fn ratchet baseline `scripts/qc-allowlists/test-env-mutation-unlocked-baseline.txt` (`<path>::<fn>` lines); a new violating fn fails even when another one was fixed in the same change, and an entry that no longer violates must be removed.
