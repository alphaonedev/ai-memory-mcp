The ADMIN_GUIDE now documents how to enrol a per-agent api-key on a deployment
that terminates TLS at a reverse proxy.

`POST /api/v1/agents/{id}/api-key` hands a bearer secret to the wire, so it is
refused unless the daemon's OWN listener is confidential. The section states the
marker's derivation exactly — `(--tls-cert AND --tls-key) OR the bind host is
loopback`, default refuse, nothing else feeding it — because the two proxy
topologies behave differently and the difference is not guessable. A same-host
proxy that terminates TLS and forwards to `127.0.0.1` already works and needs no
configuration: that daemon's bind host IS loopback. A daemon bound to a
NON-loopback address without in-process TLS (the proxy-on-another-host case)
is refused, and the section quotes the exact `403` an operator sees.

That refusal is the intended posture, not a gap: the daemon cannot verify a
claim about a hop it did not terminate, and the only evidence available to it
would be a request header, which is exactly what an attacker who can reach the
plaintext port also controls. There is deliberately no trust-the-proxy header,
env var or config key, and `AI_MEMORY_ALLOW_PLAINTEXT_NONLOOPBACK` (which
acknowledges cleartext off-host serving for CONTENT) does not unlock minting.

Three supported paths are documented: enrol from the CLI on the host that owns
the data tier (`ai-memory agents bind-api-key` / `revoke-api-key`, sqlite
directly or postgres through the `AI_MEMORY_STORE_URL_FILE` channel, with the
32-byte floor and the #3418 note that it reaches a running daemon with no
restart); bind the daemon to loopback with the proxy in front of it on the same
host, reached off-host through an SSH tunnel that terminates on it; or give the
daemon its own TLS listener with `--tls-cert` / `--tls-key`. Revocation is
deliberately not transport-gated and works in every topology. The API reference
links to the section from the mint endpoint row.
