The `ai-memory wake-hub` can now be fed from the `agent_notified` wake bus, so a
committed `memory_notify` wakes its recipient in about a millisecond instead of
on that agent's next poll. A new `crate::wake_sink` module bridges the two in
the two deployment shapes the wake plane supports. When the hub is CO-HOSTED
with the daemon, `wake_sink::in_process::install_in_process` attaches a
fire-and-forget `InboxWakeSink` that hands the encoded frame to the hub's own
`Router::deliver` — the same injection point a peer-relayed wake uses, so a
substrate wake obeys the identical per-recipient queue depth, byte cap, hub-wide
egress budget and coalesced offline set. When the hub runs as a SEPARATE
process, `wake_sink::uds::install_uds` starts a forwarder that is an ordinary
hub client over the hub's Unix domain socket: the same handshake, the same
length-delimited framing and the same frame ceiling, with no privileged side
channel and no second admission path.

A wake carries exactly `{inbox_row_id, namespace, sender, digest,
seq_high_watermark}` and structurally cannot carry a body or a title. It is
stamped with a new reserved `wake-hub-producer` identity rather than with the
notifying agent's id — no hub session authenticated that agent for that frame —
and the name is a reserved agent id, so no wire caller can register it and forge
a substrate-originated wake. Wakes are addressed DIRECTLY to the recipient and
never to a topic, so a wake for an agent can only ever reach a session that
authenticated as that agent (own-inbox only). The forwarder authenticates as
that one reserved identity and nothing else, and the shipped join credential
refuses, so a daemon with no enrolled producer identity refuses to start a
forwarder rather than opening a socket it could not authenticate on.

Delivery is fire-and-forget with bounded buffering throughout: a slow, full or
absent hub costs a HINT and a counter, never a committed notify, and every drop
cause — unaddressable recipient, unencodable frame, hub queue or egress
overflow, offline-coalesced, offline-unknown, hand-off channel full, hub down,
and bus lag — lands on its own metric so a hub that stopped waking anyone cannot
look like a quiet fleet. Reconnects use jittered exponential backoff capped at
the backstop interval, so a hub restart cannot produce a synchronised reconnect
blast. A lost wake self-heals: the next wake carries a higher
`seq_high_watermark`, and a client that sees a gap does ONE catch-up inbox read.
The `<=60 s` backstop inbox poll is now stated NORMATIVELY
(`wake_sink::BACKSTOP_POLL_MAX`, `docs/wake-hub.md`) — it is what makes every
bound in the wake plane a bounded latency cost rather than a correctness one.
Wakes are still never sourced from the webhook lane.
