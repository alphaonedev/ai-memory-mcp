### Security

- **[control-integrity] commit-signing posture gate: merges are evaluated again, and the
  web-flow carve-out is narrowed to content-neutral merges**
  ([#5065](https://github.com/alphaonedev/ai-memory-mcp/issues/5065)).
  The carve-out that cleared #5046's 8 web-flow merge artifacts was implemented as a blanket
  `--no-merges` on the scan in `scripts/check-commit-signing-posture.sh`. That dropped **every**
  merge before **any** evaluation, so neither the enrolled-identity half nor the pinned-`%GF`
  half of the rule ever saw a merge commit. Measured on the real range
  `4fff967ce..6e3f6066b`: 487 commits, 386 scanned, 101 exempt — 8 web-flow merges (the
  documented rationale) and **93 local merges exempt purely for having two parents**. Repaired
  per the crossroads verdict `5-agent vote (4d3ea1c5)`, OPTION B adopted 4-1.
  - **The exemption is now a three-term predicate.** A merge is exempt **iff** its committer is
    the web-flow identity `noreply@github.com`, **AND** `%P` is exactly two parents, **AND** its
    recorded tree equals `git merge-tree --write-tree p1 p2`. Every other merge — including every
    merge by an enrolled identity — is evaluated under the normal rule (enrolled author +
    enrolled committer + `%G? = G` + `%GF` in the pinned set). `%P` was added to the scan's
    format, which previously carried no parent information at all.
  - **Why identity alone is not sufficient.** `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` are
    plain environment variables — no key, no privilege, no config write — and
    `git commit-tree <any-tree> -p p1 -p p2` mints a two-parent merge carrying the web-flow
    identity and pointing at an arbitrary tree. Demonstrated during the vote: a file absent from
    **both** parents was present in the merge's tree and in `ls-tree -r HEAD`, while
    `git log --no-merges base..evil` listed only the two parents. Content that exists in neither
    parent and in no scanned commit lands through an identity-only exemption. The tree term is
    the only term in the predicate that an attacker without a key cannot set, which is what makes
    it the substitute for the key pin that was refused.
  - **Pinning GitHub's web-flow key was refused 5-0, on two independent grounds.** It would make
    a third-party key a standing trust root with no revocation path this repo holds, and it would
    not even work without the keyring import: a forged merge with that `gpgsig` header grafted on
    reads byte-identically to a genuine one on every field git exposes, so a key-**id** pin is
    vacuous (the shape-validated-never-resolved class). `%GF` pinning for **enrolled** signers —
    the operator's own fingerprints, already in the gate — is a different mechanism and is
    untouched.
  - **Mandatory capability probe; the gate never degrades to cannot-compute-therefore-exempt.**
    Before the walk, the gate builds a hermetic three-commit fixture whose two sides touch
    different files and asserts that `merge-tree --write-tree` returns rc exactly 0, exactly one
    line, that the line is 40 hex characters, that the oid resolves as a tree, **and** that the
    tree carries both sides' content. Anything else is exit 2 (INOPERATIVE). There is no
    `|| true` and no `2>/dev/null` on that call. The runner is bare `ubuntu-latest` with no
    container and no git pin, so the subcommand is not version-guaranteed; it fails loudly when
    absent (rc=129 + usage), and the content assertion is what catches an implementation that
    returns a well-formed but wrong oid.
  - **The non-vacuity floor was rebuilt.** The #5047 floor counted **non-merge** commits, which
    says nothing about merges once merges are evaluated. It now counts **evaluated** commits with
    exempted merges excluded, prints
    `SCANNED: N commits (M merges evaluated, X merges exempted content-neutral web-flow)`, and
    returns exit 2 when zero commits were evaluated — so a range consisting only of exempted
    merges fails closed instead of reporting PASS.
  - **Self-tests: 15 shapes → 26.** Both variants of the forged-web-flow merge are refused naming
    `signature-not-verified`: unsigned (`%G? = N`) and carrying a non-verifying signature
    (`%G? = E` with a populated `%GK`, which is the realistic shape since the real web-flow cohort
    reads `E` — the first alone would be left green by any future `%G? != N` filter). A web-flow
    merge with three parents is evaluated, not exempted. A non-web-flow unsigned merge is refused
    naming only the signature reason. A merge whose OpenPGP signature fully verifies from an
    unpinned key in the same keyring is refused as `signing-key-not-pinned`, extending the
    load-bearing case (i) across the merge boundary. An enrolled, signed, conflict-resolving merge
    **passes** and the case asserts it was counted as *evaluated*, so a pass can never be
    manufactured by an exemption. The all-exempt range fails closed at exit 2. Three cases drive
    the capability probe to exit 2 — subcommand absent, subcommand lying, git binary unusable —
    through a Python git stand-in, `scripts/selftest-git-shim-merge-tree.py`, that breaks only
    `merge-tree` and selects its mode from its own `argv[0]` so there is no environment variable
    to get wrong.
  - **False-refusal cost measured, not assumed: 0 of 382.** Every web-flow merge in all reachable
    history reproduces its recorded tree under `merge-tree --write-tree`, including 18 that
    touched a `merge=union` path and 1 with renames: zero diffs, zero conflicts. The 10
    non-reproducing merges in the range are all enrolled operator conflict-resolutions; they are
    not `noreply`, so the tree term never applies to them and they pass the normal rule. Coverage
    on `4fff967ce..6e3f6066b`: **479 of 487 commits scanned, 93 merges evaluated, 8 exempted,
    zero violations**, 5.8s. Runtime is 0.043s per merge.
  - **The residual, recorded rather than left implicit.** A forged `noreply` merge whose tree
    *equals* the automerge of its two parents is still exempt. It is content-neutral: every byte
    derives from two parents that are themselves scanned, and of the 202 parents of the 101
    in-range merges, 0 fall outside the scanned set. A dedicated positive self-test case pins this
    in both directions. Drift in git's merge resolution is **fail-closed** — a formerly tree-equal
    merge falls to the normal rule and is refused, not exempted.
