**Wake-hub: an inbox row applied by federation now wakes its recipient on the receiving node (#3631).**

A `memory_notify` reaches a peer node through the federation receive path (the signed `/sync/push` fan-out or the catch-up pull), never through `MemoryStore::notify`, and that path published nothing to the inbox wake bus. A recipient on the peer host therefore heard about the message only on its 60 s backstop poll. All five apply sites (sqlite and postgres `/sync/push`, the SAL catch-up, the store-less sqlite catch-up and the default-build catch-up) now publish the same `agent_notified` wake a local notify publishes, through one shared decision in `src/federation/applied_wake.rs`. A wake fires only for a notify row in an inbox namespace (`_inbox/<agent>` or the legacy `_messages/<agent>`) whose apply committed and left the row readable with an `updated_at` newer than before, so a replayed row, an older row that lost the newer-wins merge, a tombstoned drop, a quarantined row, or an invalid row wakes nobody. The wake carries the recipient, row id, namespace, author and a body digest, never the body (#3578 unchanged), and its `from` stays the reserved hub producer. Rows without an inbox namespace cost no extra read. `ai-memory sync-daemon` and the one-shot `ai-memory sync` still publish nothing: they run in their own process, which has no wake sink.
