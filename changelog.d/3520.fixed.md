### Fixed

- **[data-integrity] PostgreSQL deadlock (`40P01`) between an ordinary write
  and a peer daemon's bootstrap DDL no longer fails the write**
  ([#3520](https://github.com/alphaonedev/ai-memory-mcp/issues/3520)).
  `PostgresStore::connect` replays the bundled idempotent schema on every
  start and self-heal, and `CREATE INDEX IF NOT EXISTS` takes a relation-level
  `ShareLock` *before* it discovers the index already exists — so ~70 of those
  statements locked ~40 relations on every boot, for nothing. `ShareLock`
  conflicts with the `RowExclusiveLock` every writer holds, so a booting peer
  and an in-flight `size_gc` / `forget` / `archive` could take two relation
  locks in opposite orders; PostgreSQL broke the cycle by aborting the
  DML side, and the store surfaced that abort verbatim as
  `BackendUnavailable { detail: "size_gc delete victim: ... deadlock detected" }`.
  The caller's operation simply failed. Two independent changes close it, and
  they compose:
  - **The collision is removed.** `connect` now asks the catalog once
    (`pg_class` / `pg_extension` — catalog reads only, so the probe itself
    takes no relation lock and cannot join the cycle) which of the script's
    objects already exist, and replays only the statements whose object is
    genuinely absent. On a fully-migrated database no `CREATE TABLE` and no
    `CREATE INDEX` survives the filter, so **connecting takes no
    relation-level DDL lock at all**. The bootstrap stays idempotent and
    self-healing (a missing index is still created — proven by a partial-
    catalog unit test), the migration ladder is untouched (no rung added,
    moved or skipped), and a fresh database still receives every statement.
    Definition-carrying statements (`CREATE OR REPLACE VIEW` / `FUNCTION`, the
    `DO` corruption-refusal block) are never skipped, because existence does
    not imply currency and a stale view would return WRONG rows; they are also
    not part of this class, since replacing a view takes
    `AccessExclusiveLock` on the *view* and only `AccessShareLock` on the
    tables it reads. Any statement shape the classifier does not recognise —
    a schema-qualified name, an `ALTER`, anything new — is kept, so the filter
    fails SAFE toward running the DDL. A probe that itself fails degrades to
    replaying the full script, i.e. exactly the pre-#3520 boot.
  - **A writer that still loses a race is retried, not failed.** On `40P01`
    (`deadlock_detected`) and `40001` (`serialization_failure`) PostgreSQL has
    already rolled the whole transaction back atomically, so re-running it is
    a first attempt against an unchanged database, never a partial replay.
    The six destructive transaction funnels — `size_gc`, `run_gc`, `forget`,
    `archive_by_ids`, `archive_restore`, `delete` — now route through ONE
    shared bounded-retry driver (`store::postgres::tx_retry`): 3 attempts,
    20 ms base backoff doubling to a 320 ms ceiling with +/-50 % jitter (so a
    fleet's victims do not march back into the same collision), each retry
    logged at `WARN` under the `store::postgres::tx_retry` target with the
    SQLSTATE and attempt number. No env knob: the whole budget is a few tens
    of milliseconds.
  - **Classification is STRUCTURAL, never textual.** `StoreError::BackendUnavailable`
    now carries the backend's own error code (`sqlstate`), captured by the
    adapter's single `sqlx::Error` -> `StoreError` funnel before the error is
    rendered. The retry decision reads that field and never substring-matches
    the message: message text is an operator-facing rendering that changes
    across server versions and locales, and branching control flow on it is
    how a transient abort gets mistaken for a permanent one. `None` means the
    failure was not a database error at all (a pool / connect / config fault),
    which is likewise never retried.
  - **Fail-CLOSED terminal state, and a closed retry set.** After the bounded
    budget the ORIGINAL `BackendUnavailable` is returned unchanged, so a
    genuinely wedged database still produces a prompt, honest refusal — never
    a silent partial application and never an unbounded stall. Only the two
    rolled-back SQLSTATEs are retried: `55P03` (`lock_not_available`, whose
    correct disposition on the DML path is to surface the contention), a
    constraint violation, or a disk-full each fail on the first attempt.
    Every retried block is a whole transaction with no effect outside it —
    `archive_by_ids`' row accumulator moved INSIDE the block for exactly this
    reason, since a retry would otherwise have double-counted rows the
    rolled-back attempt never archived.
  - **Test hygiene.** The `store::postgres` lib tests share one database and
    run in parallel, which is how #3520 was observed. With the catalog
    pre-check, no `connect` after the first emits any relation DDL against a
    given database, and a `cfg(test)` guard serialises that first bootstrap so
    no peer test can be handed a store that starts writing mid-DDL.
    Production concurrency behaviour is unchanged (the advisory lock, not this
    guard, governs it — and #3519's live 8-store concurrent-boot regression
    test still exercises it).
  - Coverage: `store::postgres::tx_retry::tests` (SQLSTATE classification
    including the "detail says deadlock, no code" case that must NOT retry;
    backoff bound / floor / spread; retry-then-commit; permanent and
    non-database errors never retried; bounded budget with the terminal error
    preserved) plus a LIVE regression that provokes a real `40P01` the way the
    issue describes — two sessions taking two relation locks in opposite order,
    ordered through `pg_locks` rather than a sleep — and asserts the funnel
    RETRIED and then COMMITTED, on the retry counter and the attempt count.
    `store::postgres::bootstrap_ddl::tests` parses the REAL bundled script
    (dollar-quoted function bodies and the `DO` block survive whole) and pins
    all three directions: a fully-migrated catalog emits no relation DDL, an
    empty catalog keeps the script whole, and a partially-present catalog
    still re-emits exactly the missing object.
