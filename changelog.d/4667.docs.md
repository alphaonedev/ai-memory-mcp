**PgBouncer: `session` mode is the only supported pool mode (#4667).** The
enterprise guide (section 5.6 and 10.4, the section 14 checklist),
`infra/pgbouncer` and the ROADMAP prescribed `pool_mode = transaction` as
required. The Postgres adapter is not safe behind it: the migration advisory
lock (`pg_try_advisory_lock` on `MIGRATION_ADVISORY_LOCK_KEY`), the connect-time
`search_path` (`set_config('search_path', .., false)`) and the connect-time
`statement_timeout` / `lock_timeout` (plain `SET`) all live on the server
session (`src/store/postgres.rs`, the `after_connect` hook in
`connect_with_dim_and_timeout`). The probe recorded on PR #4710 (PgBouncer
1.23.1) exits 1 on `transaction` and `statement` pooling (a second client was
granted the migration lock, saw the first client's `search_path` and timeout,
and a reused backend kept its temporary table and prepared statement), exits 0
on `session`, and exits 2 when a client never got a server connection. The guide
now states session mode (or no pooler), the sizing rule
`sum(AI_MEMORY_PG_POOL_MAX) (+ reserve_pool_size per PgBouncer pool) <=
max_connections - superuser_reserved_connections` with the T4/T5 numbers
recalculated, and a migration path for deployments that already ran transaction
mode (direct-connection migrations one daemon at a time; role-level
`search_path` and timeouts). `infra/pgbouncer/pgbouncer.ini` ships
`pool_mode = session`, and its README, the T4 architecture page, the v0.7.0
pool-sizing prompt (marked superseded) and the pillar-4 envelope README say the
same. Making the adapter safe under transaction pooling is tracked in #4679.
Decision: 5-agent vote (4d3ea1c5), memory b6ed2e38-4e37-4cd9-997e-49bb99d241c0.
