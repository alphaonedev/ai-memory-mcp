### Fixed

- **[data-integrity][claims-truth] `curator --rollback` reported `applied` for a
  priority reversal the substrate refused**
  ([#3526](https://github.com/alphaonedev/ai-memory-mcp/issues/3526)).
  The store-backed `autonomy::reverse_rollback_entry_store` `PriorityAdjust` arm
  restored the prior priority with `get → mutate → store.store`. `store.store` is
  the CREATE funnel, and its `ON CONFLICT (title, namespace) DO UPDATE` arm
  resolves `priority = MAX(memories.priority, excluded.priority)`
  (`GREATEST(...)` on postgres). The row always exists on that path, so the merge
  always fired: a reversal that RAISES a priority worked, and a reversal that must
  LOWER one — undoing an earlier raise, which is the entire point — was a silent
  no-op on the durable row that still printed `rollback <id>: applied`. On an
  AUDITED reversal path that is a claims-truth defect: the log says the adjustment
  was undone, the substrate says otherwise. Found by the #3521 coverage lane,
  which documented the gap rather than pinning the broken direction as correct.
  - The reversal now writes through the EXPLICIT `MemoryStore::update` funnel
    addressed BY ID (`priority = COALESCE($n, priority)` on postgres,
    `priority=?6` on sqlite — a REPLACE on both backends), never the create
    funnel. `db::insert`'s MAX-merge is **unchanged**: other callers depend on it
    (a re-store must never silently demote a row), so it is the rollback that
    stopped using it, not the funnel that changed.
  - **The receipt is now asserted against the substrate.** Every arm — not just
    `PriorityAdjust` — reads the durable row back after its write and compares it
    to what the reversal intended: the restored snapshot must be LIVE at its own
    id, the consolidated summary must be GONE, the `contradiction_*` markers must
    be CLEARED, the priority must equal `before`. A divergence is REFUSED: an
    `Error`-outcome leaf lands on the existing audit path, the CLI prints
    `rollback <id>: not applied (…)` and exits non-zero, and the rollback-log row
    is left UNTAGGED so the entry stays reversible. `applied` is never printed for
    a reversal that did not land.
  - The rusqlite (direct-connection) twin never rode the merge — it already wrote
    through `db::update` — but it discarded that call's `found` bool and returned
    `true` unconditionally, so it printed `applied` for a memory that no longer
    exists. It now reports the honest no-op and carries the same read-back
    verification, keeping the two twins in parity.
  - Regression suite `tests/rollback_priority_claims_truth_3526.rs` pins the
    lowering direction, the raising direction, the vanished-target no-op, the
    unchanged create-funnel MAX-merge and the CLI receipt on the rusqlite twin,
    the SAL sqlite store and live postgres, plus a probe adapter that ACCEPTS the
    write without moving the row (the pre-fix substrate behaviour) and must be
    refused.
