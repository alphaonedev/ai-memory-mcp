**[release][supply-chain] The shipped artifact is bound to the binary the strict feature assert checked (#4752, umbrella #6062).**
Nothing proved that the file `release.yml` packaged, checksummed, attested
and uploaded, or the file the Dockerfile's runtime stage executes, was the
file the strict `ai-memory features` assert ran on: a later step or
instruction could replace it and both the static guard and the runtime assert
stayed green. Now (1) the assert step (`id: assert`) records the SHA-256 of the
bytes it checked in `GITHUB_OUTPUT`, and the package step reads it through
`env` and refuses to package `dist/ai-memory` unless its hash is exactly that
value (the guard self-test drives the package body with the right, an empty, a
wrong and an upper-cased hash); (2) `scripts/check_release_features.py` pins
the release job WHOLE (`RELEASE_STEPS`, the way the `docker` job already was):
every step's keys, SHA-pinned `uses`, `with` / `env` / `if` values and exact
`run` lines, with the build, assert and package units in their slots, so no
step can be added, removed, reordered or changed unseen; (3) the Dockerfile's
runtime stage copies the declaration and the asserter from the builder stage
and re-runs the strict assert on `/usr/local/bin/ai-memory`, the shipped path,
on the runtime base image (which also catches the glibc-mismatch class of
PR #465 at build time), and the guard refuses any COPY, ADD or RUN after it.
The assert step's name is now quoted: unquoted, YAML cut it at ` #2728)` (the
#2473 truncation class). Regression: the `4752 ...` guard self-test cases.
