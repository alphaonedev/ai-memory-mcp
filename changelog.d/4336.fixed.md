**The live-Postgres lock-barrier test suites no longer fail on a cold backend (#4336).** `owner_gate_toctou_pg_3953`, `lifecycle_owner_lock_pg_4053`, `contaminated_stamp_f1_fixes_pg_item3_3266` and `node_local_containment_item3_r2_3266` park a writer behind a held lock and poll `pg_blocking_pids` for it, each with a free-standing 20 s deadline. The writer cannot reach its lock wait before it owns a connection, and the first backend started against a freshly created database on a busy host can take longer than that, while the production pool waits `acquire_timeout_secs` (30 s) for a connection. A healthy first run therefore panicked with `barrier not reached` and passed on the repeat. The deadline now comes from one shared helper, `tests/common/pg_barrier.rs`, derived from the production pool-acquire and lock timeouts (twice their sum); it is a ceiling only and no assertion is weakened. `tests/pg_cold_connect_barrier_4336.rs` reproduces the cold backend deterministically with a login event trigger that delays every new connection by 24 s. The production bootstrap was ruled out: sixty concurrent boots against ten fresh databases all succeeded under the existing migration advisory lock.

**Scratch databases of the cold-backend cell no longer leak (#4489).** The scratch database carries a login-delay trigger. Its name is now `ai_memory_4336_<10-digit unix seconds>_<8 lowercase hex>` (server clock), a guard drops it on every exit including a panic unwind (bounded, never panicking in `Drop`), and the start of each run sweeps scratch databases older than ten minutes, matching ONLY that exact whole-name shape with a quoted single-statement `DROP` (a concurrent live run, a lane database or any lookalike name is never touched). A `SIGKILL` cannot be caught, so a killed run still leaves its database behind until the next run's sweep removes it. The injected delay is now derived from the pool acquire timeout minus 8 s (22 s) rather than a literal.
