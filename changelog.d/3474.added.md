Admin HTTP enrolment for per-agent api-keys — `POST /api/v1/agents/{id}/api-key`
(mint or bind) and `POST /api/v1/agents/{id}/api-key/revoke` — so a fleet
controller with no shell on the data tier can enrol a dynamically minted agent.
#3418 made the enrolled registry live and gave the CLI a `--store-url`; without
a network surface the only workable posture for such a fleet stayed `advisory`
(self-asserted `X-Agent-Id`), which is exactly what `enforce` exists to refuse.
Both routes are served on BOTH backends and take effect through the #3418 live
registry with no daemon restart.

The controls, and what each is for:

* **Authorization** is the canonical `require_admin` gate every other admin
  route uses — no new role. A non-admin receives the same generic
  `403 {"error":"admin role required"}` whether or not the target agent
  exists, so the surface is not an enumeration oracle, and the principal the
  handler acts and audits as is the gate's return value, never a request field.
* **No-log token transport.** The body is read as raw bytes and parsed in the
  handler, so no extractor rejection can render any part of it into an error
  string; a malformed body answers with a fixed `invalid request body`. The
  request type's `Debug` prints `<redacted>` for the token. Only
  `sha256(token)` is persisted and only its 12-hex-character fingerprint is
  logged or audited. The response is `Cache-Control: no-store`, and a mint is
  REFUSED unless the daemon's own listener is loopback or TLS-terminated
  in-process — closing the hole `AI_MEMORY_ALLOW_PLAINTEXT_NONLOOPBACK` leaves
  open, which is survivable for content and not for a bearer secret. Revoke is
  deliberately NOT transport-gated: refusing a revocation is worse than
  performing one over a channel the operator already accepted.
* **Rate limit.** Ten mints per sixty seconds per admitted caller, in a bounded
  table that REFUSES rather than admits when it is full of live windows.
* **Approval gate.** Revoking your own key is immediate. Revoking another
  principal's key — or the last enrolled key, which would make the identity
  gate inert in every mode (#1985) — queues a pending action that only a
  DIFFERENT registered approver can apply, through the same
  `approve_with_approver_type` eligibility gate and a K10 HMAC signature that
  additionally binds the APPROVER into the signed subject
  (`<ts>.POST.<pending_id>@<approver>.<body>`), so a captured approval
  signature cannot be presented by a different principal. One approval applies
  exactly once — a decided row is `409`, never a re-application, because a
  standing `approved` row any admin could re-post would turn one authorisation
  into an unbounded credential mint.
* **Audit.** Mint, bind, revoke, queue, approve and every refusal append to the
  signed forensic chain with the actor, the target agent, the key fingerprint
  and the outcome — never the token.

New SAL seam `MemoryStore::queue_pending_action` (both adapters) so a surface
whose approved action is not a memory mutation can park an approval without
claiming the generic executor can run its payload.
