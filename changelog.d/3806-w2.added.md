Wire the first two `[decision]` seams, and route every surface that can
reach one through the boot chokepoint.

`detect_contradiction` becomes a typed JUDGEMENT. Its verdict used to come
from `answer.starts_with("yes")`, so a refusal ("I'm sorry, I can't help
with that"), a preamble ("yes, because …" from a model that then argues
itself to no) and a hedge all became a `true`, and `false` meant both
"decided no" and "the parse fell through". With `[decision]` configured
the verdict comes from a strict closed-vocabulary answer, prose is an
ABSTAIN, and the seam takes a conservative NON-ACTION branch instead of a
fabricated verdict. `classify_kind` becomes a CHOICE over all sixteen
`MemoryKind` variants — the prompt it used named eight, so half the
vocabulary was unreachable whatever the model knew — and the option set is
derived from `MemoryKind::all()`, so a variant added later cannot fall out
of it silently.

**`[decision].fallback` governs UNAVAILABILITY, not abstention.** Three
cases, and only the middle one is `fallback`'s business. (1) `[decision]`
unset: the v1.0.0 path runs entirely, text parse and all — byte-identical,
including a `/metrics` body unchanged byte for byte. (2) The provider was
UNAVAILABLE (not constructed, egress refused, timeout, transport error,
non-2xx status): nothing declined, so falling back to the instrument used
before is legitimate and `fallback` selects it — `generative` means the old
path, `abstain` means abstain, `refuse` means error. (3) The provider
ANSWERED AND DECLINED — a refusal, a preamble, a hedge, a label outside the
closed vocabulary: **terminal.** The seam takes its conservative non-action
branch, the question is never re-asked by anything, and `fallback` does not
apply, `refuse` included.

Case 3 is the point of the feature, so it is an executable invariant
(`AbstainReason::is_unavailable`) rather than a comment. Re-asking the same
question of a weaker reader would manufacture a definite answer out of a
deliberate refusal — worse than the `starts_with("yes")` defect, not a
milder version of it. An abstain is information, not an absence of
information. The same reasoning now bars the provider-level fallback chain
from re-asking after a decline, which **changes behaviour landed earlier in
this programme**: `FallbackChain::may_fall_back(Unusable)` was `true` and is
now `false`, and its pin was inverted with a new presence control (an
UNAVAILABLE primary still falls back). To keep that distinction honest,
`AbstainReason` gained an `Unavailable` variant: a transport failure, a
non-JSON body and a non-2xx status used to be reported as `Unusable`, which
conflated "could not reach the model" with "the model declined".

An egress refusal is case 2 at the seam — the `[llm]` lane passed its own
egress gate at boot, and under `deny` there is no `[llm]` client to reach —
and terminal inside the decision plane, so `fallback` can never become an
egress bypass.

The MCP stdio surface (and its between-request reload) and the CLI one-shot
curator now obtain their decider from the SAME boot chokepoint the HTTP
daemon uses, which the W1b review named as this unit's acceptance item.
There is one attachment verb, one chokepoint call, and one construction
site for the gated handle in the whole crate; the structural pin asserts
the routed surface list in BOTH directions, so a new decision consumer
cannot appear — and an existing one cannot lose its gate — without editing
a reviewed list. The per-call outbound check now also requires the request
origin to be one the boot gate approved, so a mis-joined path or a
redirected base cannot send memory content to an endpoint no gate saw.

**What this costs an operator, stated plainly.** If you run
`[decision].fallback = "generative"` and your decision model returns prose
rather than a value from the closed vocabulary, you previously received a
second model's opinion and you now receive an abstain — which at these two
seams means the caller's memory kind is left alone and no contradiction
edge is recorded. You lose an answer you used to get. The trade is right
because the answer you used to get was a different model's guess,
substituted for a deliberate refusal, at a seam whose siblings (W3, W4)
delete data; asking a second model until one answers is answer-shopping,
and this is an abstain shop. If you want the old behaviour on a model that
declines, the honest fix is a decision model that answers in its
vocabulary, not a reader that guesses. An UNAVAILABLE endpoint still falls
back exactly as before.

Three new series make all of this visible.
`ai_memory_decision_latency_seconds{seam}` and
`ai_memory_decision_outcome_total{seam,outcome}` answer "did the seam get a
decision?" — an abstain is a first-class outcome there, so "no opinion" is
never indistinguishable from "decided no".
`ai_memory_decision_abstain_total{seam,reason}` answers "why not?", which
is a different question: at the outcome level an outage and a model that
declined are both `abstained`, and an operator must still be able to page
on the first and not the second. Every label set is closed (4 seams x 5
outcomes, 4 seams x 6 reasons) and every series is created lazily by its
first observation. **No exposition budget was raised for this feature.**
The worst case — more than the two wired seams can produce — grew from
5,663 bytes to a deterministically measured 8,142, which still fits the
unchanged 8 KiB inner budget with 50 bytes spare; total 25,275 of the 64
KiB `/metrics` read cap (#3654), also unchanged. The measurement moved into
its own test binary so the number is byte-identical on every run: measuring
an exposition budget against a body carrying a real observed latency is
measuring the clock, not the feature.
