The declaration-hash gate's D1b check (a re-pin of `scripts/qc-allowlists/declaration.sha256` must raise the revision) is no longer silently skipped (#5604). It used to compare against `${DECLARATION_GATE_BASE:-HEAD}` with every git error discarded, so an all-zero, empty or unreachable push `before`, a `merge_group` run (empty base) or a bare run skipped D1b or compared the pin with itself. The previous-pin base now comes only from the base side of `scripts/ci-commit-range.py` (new `--base-only` mode; closed-world event handling, strict 40-char lowercase non-zero commit-resolving shas); a base named by hand (outside CI only, `DECLARATION_GATE_LOCAL_BASE` since #5970) must resolve to a commit; the default `HEAD` is removed; an undecidable or unresolvable base, a pin file absent at the base, or a malformed previous pin is a red job. The refusal names its cause by kind (#5970): an all-zero, empty or missing `before` reads as no previous tip (a creation push carries an all-zero `before`); an unreachable `before` reads as a previous tip that is not a commit in the checkout (a force-push dropped it, or the checkout lacks it); a missing or unresolvable `merge_group` base reads as an event with no usable base_sha; each of these also says the next ordinary push produces a comparable range, and a malformed sha is refused as malformed; a creation push is always red and a re-run cannot turn it green, while a force-push whose previous tip is still reachable is checked over before..sha (see #5643). The workflow passes the six event inputs, `declaration-hash-gate` joins the helper's static workflow pin (with mutants of the workflow and the script), and the self-test gains fourteen base legs (all-zero, empty and unreachable before, merge_group with and without base_sha, pull_request, push, unknown event, no base, unresolvable and absent-pin bases). The required-contexts lists are unchanged. 5-agent vote (4d3ea1c5).
