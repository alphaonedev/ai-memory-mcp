Two concurrent self-revokes by the last two holders of an enrolled per-agent
api-key can no longer empty the registry, and an approval granted for revoking
one principal's key can no longer become the thing that empties it.

`POST /api/v1/agents/{id}/api-key/revoke` used to read the enrolled key set,
conclude "this is not the last key", and then revoke as a separate step. Two
self-revokes in flight at once each observed the other holder's key, each
concluded correctly from what it saw, and both applied — leaving ZERO enrolled
keys, which makes the identity gate inert in every mode (#1985) with no second
approver ever having authorised it. A check-then-act pair cannot be fixed by
ordering it more carefully, so the count and the delete are now ONE atomic
decision: a new store seam `revoke_agent_api_key_unless_last` on both backends
(sqlite: `BEGIN IMMEDIATE`, so the write lock is taken before the count is
read and the CLI twin on the same file cannot slip between them; postgres: one
transaction opened with a `pg_advisory_xact_lock`, which serializes the whole
check-and-act independently of the isolation level — a single clever statement
would be atomic but could not tell "the agent had no keys" from "the agent held
every key", and answering "revoked, 0 rows" for a credential that is still live
is a wrong answer, which is worse than a refusal). The loser of the race is
PARKED for a second approver rather than refused: that is the same answer it
would have received a millisecond later, its intent survives as a
`pending_actions` row, and the caller gets the same `202` envelope the
non-racing caller gets.

The approval applier re-checks the same way. A revoke is parked for one of
three reasons and only one of them tells the approver that applying it leaves
the deployment with no enrolled keys at all, so every queued row now records
`empties_registry` and every `202` discloses it. An approval that DID disclose
it applies unconditionally — that is exactly what the second principal
consented to. An approval that did not is routed through the atomic seam, and
if the target has become the last enrolled key in the meantime the apply is
refused with `409 {"error":"revoke_would_empty_registry"}`, nothing is revoked,
and the refusal lands on the signed forensic chain. The refusal spends the
approval, which is the safe direction: the registry is untouched and re-issuing
the revoke queues a fresh approval that discloses the emptying.

The sqlite seam is record-stop gated, matching its postgres twin — a revoke is
a write, and the two backends now refuse the same writes during a record stop.
