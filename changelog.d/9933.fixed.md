**PostgreSQL boot never NULLs stored embeddings on a dimension mismatch.**
When the configured or defaulted embedding dimension differed from the live
`memories.embedding` column, the daemon boot auto-migrate converted the column
in place and set every stored vector to NULL. The boot now converts only an
empty column. A populated column at another dimension refuses the boot with a
typed error that names the live dimension, the requested dimension and its
source (configured by an environment variable, a config file or an embedding
model, or defaulted from a tier preset or the compiled default), the number of
embeddings at risk and the explicit opt-in:

```text
invalid input: refusing destructive embedding-dim conversion: live column is vector(768), requested vector(384) from a defaulted dimension (tier preset or compiled default); 1 stored embeddings would be NULLed. To keep them, configure an embedder whose dimension is 768; to convert them and re-embed, run `ai-memory schema-init --embedding-dim 384 --force-reembed`.
```

`ai-memory schema-init` without `--embedding-dim` now adopts the live column
dimension instead of converting it; a defaulted dimension with
`--force-reembed` over a populated column refuses, and an explicit
`--embedding-dim N --force-reembed` is the one destructive path. The
conversion re-reads the column and re-counts the stored embeddings under an
`ACCESS EXCLUSIVE` table lock, so a vector written after the boot count makes
it refuse instead of being NULLed. With no constructible embedder the stored
vectors are preserved as before (#2567). SQLite stores embeddings as
dimension-agnostic BLOBs and has no conversion path.
