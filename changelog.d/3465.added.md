`memory_notify` now emits an `agent_notified` write event and agents can be
pushed instead of polling. Every notify funnel — the MCP handler (and the CLI +
HTTP surfaces that route through it) and both SAL adapters — fires the event
through the shared `crate::write_events` funnel after the inbox row commits, so
`agent_notified` joins the canonical `WEBHOOK_EVENT_TYPES` list that webhook
subscribers can opt in to. The same emitter also publishes a low-latency wake on
a new in-process `tokio::sync::broadcast` bus (`crate::inbox_wake`), which backs
the new `GET /api/v1/inbox/stream` SSE endpoint: a recipient holds one
connection and is woken the instant it has mail, instead of polling its inbox on
a timer. The stream is identity-bound to the caller's OWN inbox (no delegation,
no namespace widening, fail-closed on an unresolved identity), keeps alive every
15 s, and emits a synthetic `lagged` frame when a slow subscriber overruns the
bounded buffer so the client does one catch-up inbox read. Wakes carry a
`sha256:` content digest, a correlation id and the inbox row id — never the
notification body; the durable row remains the record and the wake is only the
prompt to go read it. A fire-and-forget `InboxWakeSink` trait (no-op by default)
lets an out-of-process consumer such as the forthcoming `ai-memory wake-hub`
attach to the bus without a line changing on the notify write path. Wakes are
deliberately NOT sourced from the webhook lane, whose global dispatch semaphore
and subscription-scan ceiling must never gate a recipient's wake latency.
