**`rules keygen --out` refuses a key file name the operator-key loaders cannot read (#3437).**
`rules keygen --out <path>` wrote `<path>` and `<path>.pub` under any name, but
the signer (`rules enable --sign` and the other signing verbs) and the
verifier read only `operator.key` + `operator.key.pub` (or the legacy
`operator.priv` + `operator.pub`). A run such as `--out <dir>/team.seed` or
`--out <dir>/operator.priv` exited 0 and left a key nothing could load. The
`--out` basename must now be `operator.key`: `--out` relocates the directory,
and any other name is refused before anything is written, with an error that
names the fix. With a key-dir override in force (`rules --key-dir <dir>` or
`AI_MEMORY_KEY_DIR`), an `--out` outside that directory is refused too, with an
error naming both paths: the signing verbs read the key from the key dir only,
so such a key could never be loaded. The loaders are unchanged, so signing and
verification still read the same files. The operator workflow in
`docs/integrations/claude-code.md` now runs as written: every `rules` step
names the same `--key-dir <dir>`, and `rules enable` takes the rule as
`--id R001` (the positional `rules enable R001 --sign` it documented was
rejected).

**`agents bind-api-key --token-file -` reads the api-key token from stdin (#3437).**
Per the #3781 ruling, the `--token-file <0600 path>` and
`AI_MEMORY_AGENT_API_KEY_FILE` channels and the refusal of an argv `--token`
shipped with #3781; the stdin channel this issue also asked for did not ship
there, and `--token-file -` failed trying to open a file named `-`. It now reads
the token from stdin, for a token piped from a secret manager rather than
written to disk: exactly one line (the trailing newline is not part of the
token), at most 4096 bytes; an empty, whitespace-only or multi-line stdin is
refused and nothing is bound. The command help documents the form.
