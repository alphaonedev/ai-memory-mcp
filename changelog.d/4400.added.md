**Opt-in fail-closed mode for the flat audit trail: `AI_MEMORY_REQUIRE_AUDIT_TRAIL` (#4400).** By default a flat audit event that cannot be written is counted (`ai_memory_audit_write_failures_total`), reported on stderr and in `doctor`, and the memory operation goes ahead (#3975). With `AI_MEMORY_REQUIRE_AUDIT_TRAIL=1`, a failed audit write or flush makes the process refuse every later mutating operation with `503 AUDIT_TRAIL_UNAVAILABLE` (MCP and CLI show the same refusal) until the trail records again. Reads keep working. The refusal runs through the same checkpoints as the record-stop control (#1955), so it covers both storage backends, the coordination writes, federation receive and every MCP write tool, and it carries its own code so it cannot be mistaken for an operator's stop. The next write after a failure retries the trail, at most once a second, by writing a real `trail_resumed` record; when that succeeds the refusals stop and the trail shows where recording resumed. `doctor` shows the mode and the refusal state, and `/metrics` exports `ai_memory_audit_trail_latched` while the mode is on. What it does not do: every audit event is written after its memory operation commits, so the one operation that discovers the failure has already happened (it is counted, as before); a single CLI command cannot refuse its own write and relies on the existing refusal to start when the trail cannot be opened (#3651); and it covers the flat audit trail only, not the signed event chain or the forensic log. The mode is off by default and the `asi-hard` profile does not turn it on, following a vote that it should run for a release before becoming a hardened default.
