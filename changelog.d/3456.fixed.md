`POST /api/v1/import` now enforces the destination namespace's governance
standard on **both** backends. F-A2A1.5 (#705) gated the postgres branch —
an imported row is a Store action and must be gated by the namespace's standard
— but the sqlite branch was never followed up: its loop was
`restamp -> validate -> db::insert` with no `consult_pre_governance_decision_gate`
and no `enforce_governance_action(GovernedAction::Store)`. The same admin
request against a sqlite-backed daemon therefore bypassed a `write: Deny` /
`write: Approve` standard entirely, while the postgres-backed daemon refused it
or parked it pending — a backend-dependent authorization outcome for one wire
call. (`db::insert` did consult the substrate `GOVERNANCE_PRE_WRITE` hook, but
that is the operator-signed substrate layer, a different control from the
namespace standard.) The sqlite loop now runs the same presence consult and the
same `GovernedAction::Store` decision through the sqlite-native
`db::enforce_governance` twin, with byte-identical per-row dispositions and
refusal strings, and the optional `X-AI-Memory-Capability` token is parsed once
for both backends instead of only for postgres. The sqlite response envelope
gains the `pending` field, so an `Approve` standard is expressible on that
backend at all — previously a caller had no way to learn a row was parked
awaiting consensus. Additive: `imported` and `errors` are unchanged and an
empty `pending` is the ordinary case.
