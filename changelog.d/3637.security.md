### Security

- **[wake-hub] The packaged refresher's root hand-off no longer follows a symlinked source (CWE-59) and is now atomic**
  ([#3637](https://github.com/alphaonedev/ai-memory-mcp/issues/3637) M4, follow-up
  [#3971](https://github.com/alphaonedev/ai-memory-mcp/issues/3971)).
  `ai-memory-wake-hub-refresh.service` ran `ExecStartPost=+/usr/bin/install … /var/lib/ai-memory/hub-allow.json
  /run/ai-memory-hub/hub-allow.json` as root. The source directory is writable by the `ai-memory` uid and
  `install(1)` dereferences its source, so a swapped-in symlink made root copy any file it can read into the
  hub directory; `install(1)` also unlinks-then-recreates the destination, so the hub could find no snapshot
  mid-copy, contradicting `docs/wake-hub.md` ("publishes ATOMICALLY"). The unit now runs the new
  `ai-memory wake-hub --publish-snapshot SRC --allowlist DEST`: an `O_NOFOLLOW` walk of both parent
  directories from `/`, a descriptor-proven single-link `0600` source owned by its directory's owner, a
  1 MiB cap and full validation with the hub's own parser, then an `O_EXCL` temp file handed to the
  destination directory's owner at `0600`, `fsync`, `renameat` and a directory `fsync`. The publish mode short-circuits
  in `main` straight after argv parsing, so the root step loads no config, initialises no logging, audit
  trail or keys, and touches no path but its two arguments. Any refusal, and any failure
  before the rename, publishes nothing (the previous snapshot ages out, refusing hellos); a directory
  `fsync` failure after the rename exits non-zero with an error stating that the validated snapshot WAS
  published and only its durability is unconfirmed. **Operators with a customised refresher unit
  must replace their `install` line** with the shipped `ExecStartPost=`.
- **[wake-hub] Disclosed: wake metadata, including `AI_MEMORY_WAKE_SENDER`, is peer-asserted and not
  authenticated** ([#3637](https://github.com/alphaonedev/ai-memory-mcp/issues/3637) M1, structural fix
  tracked in [#3972](https://github.com/alphaonedev/ai-memory-mcp/issues/3972)). Any admitted hub peer can
  send a direct wake with arbitrary `sender`/`namespace`/row id/digest, and the listener presents the
  payload's claims rather than the hub-stamped sender. `docs/wake-hub.md`, `docs/CLI_REFERENCE.md` and the
  `wake-listen` docs previously described `AI_MEMORY_WAKE_SENDER` as "agent that wrote the row"; they now
  say it is a hint, and that a hook must decide on the durable row's recorded author and a recomputed digest.
