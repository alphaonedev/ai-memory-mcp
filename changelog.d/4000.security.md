### Security

- **[docs][audit] The audit-trail coverage docs no longer claim every
  successful write is chain-logged**
  ([#4000](https://github.com/alphaonedev/ai-memory-mcp/issues/4000)).
  `docs/security/audit-trail-coverage.md` said memory writes (`store` /
  `update` / `link` / `delete` / `archive` / `consolidate`) append a
  `memory.<verb>` row to `signed_events` "on every successful substrate
  write" with no success-leg gap; `honest-limitations.md` said "every
  state-changing operation appends to `signed_events`"; the NSA-CSI mapping
  said "every recall writes a `recall_observations` row"; and `docs/index.html`
  said every state-changing operation lands in the audit chain. Measured on
  the code: among memory writes only link creation (`memory_link.created`)
  and signed-link invalidation (`memory_link.invalidated`) append to
  `signed_events`, and SQLite link creation does so best-effort (a failed
  append logs a WARN; the link is kept and reported). No `memory.store` /
  `update` / `delete` / `archive` / `consolidate` event type exists; those
  verbs are chain-recorded only by the opt-in append-only `memory_revisions`
  spine (`AI_MEMORY_APPEND_ONLY`, default off) or the opt-in JSONL audit log
  (`[audit] enabled`, default off). Recall-observation recording is
  best-effort on MCP and HTTP. The docs now say exactly this. **Operators who
  need a tamper-evident record of every memory write must enable the
  append-only spine or the audit log.** Pinned by
  `tests/link_audit_append_best_effort_4000.rs` (forced append failure: link
  kept, no audit row, WARN emitted) and
  `tests/fit_docs_b_false_claims_4000_4009.rs`.
