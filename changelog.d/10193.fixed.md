**The row-attestation seal is written under a lock.** The anchored seal that
records the highest attestation id and the head of every attested table
(#10087) was moved forward by an unlocked read, merge and write, so two
concurrent advances (a signing session and a clean verify, or two processes on
one database) could write a seal built from a stale read and lower a mark the
other had recorded. Every seal write (advance and the verified-restore
replace) now holds an exclusive lock on the sibling file `<seal>.lock` for the
whole read-merge-write; a lock that cannot be opened or taken refuses the write
and leaves the seal unchanged. Before the lock is opened, the seal directory is
created owner-only (0700) whatever the umask, and the seal directory and
every directory up to the anchor directory are checked as key directories are
(#10205): a group- or world-writable directory, one owned by another user, or
a symlink in that chain to such a directory refuses the write with the reason
and nothing is repaired, so an existing seal directory left group-writable must
be made 0700 by its owner. An advance that adds nothing to the seal on disk
writes nothing and does no fsync (#10206). The wait for the lock has no time
limit, as for the scope-key store lock. The seal file format is unchanged.
