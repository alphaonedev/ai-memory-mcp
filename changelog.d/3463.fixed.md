Inbox `unread_only` is now applied **inside the query, before the SQL `LIMIT`**, on both backends. `handle_inbox` (MCP, and the HTTP-sqlite `get_inbox` that delegates to it) and the HTTP-postgres arm of `get_inbox` both fetched the newest `limit` rows first and dropped the read ones in Rust afterwards, so an agent whose newest `limit` messages were all read was answered `count: 0` / `unread_count: 0` while older unread messages sat untouched in its namespace — a silent false negative, and an unsound foundation for any "wake, then read the inbox once" push design. The narrowing now rides the shared `list` query on both adapters: a new `Filter::unread_only` axis threads into `build_list_query`'s `AND access_count = 0` fragment on sqlite and into the `AND access_count = 0` predicate on postgres, both emitted only when the axis is set (so every pre-#3463 list shape keeps its byte-identical SQL and cached plan) and both placed before the `ORDER BY ... LIMIT` tail. `access_count == 0` remains the #3027 unread marker, and both adapters re-apply it in-process on the rows they return so a drift between the SQL and the Rust predicate can only narrow, never widen. The postgres inbox envelope now also carries `count` and `unread_only`, and the sqlite/MCP envelope now carries `unread_count`, so the two surfaces report the same shape.
