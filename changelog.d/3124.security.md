### Security

- **[authz] One cross-backend policy for UNSTAMPED (legacy-unowned) rows**
  ([#3124](https://github.com/alphaonedev/ai-memory-mcp/issues/3124)). Before
  this change the two backends disagreed: postgres refused a caller-scoped
  update / delete / If-Match `PUT` / archive of a row with no
  `metadata.agent_id` (#1412 / #1628), while sqlite let ANY caller mutate it on
  every funnel — and even the definition of "unstamped" differed (a
  non-string `agent_id` was mutable by anyone on sqlite, and matchable by a
  caller of the same spelling on postgres).
  - **One definition** (`identity::owner_stamp::OwnerStamp`): a row is
    stamped iff `metadata.agent_id` is a non-empty JSON string. Missing / null
    / `""` is unstamped; a non-string value is malformed and is never matched
    or admitted, on either backend.
  - **One knob**, `AI_MEMORY_UNSTAMPED_MUTATION=warn|refuse`. `warn` (the
    default) changes no funnel's outcome on either backend — postgres keeps
    refusing where it already refused — and every mutation it admits on an
    unstamped row now logs a WARN (`target: authz.unstamped`) and increments
    `ai_memory_unstamped_mutation_allowed_total{backend,funnel}`. `refuse`
    refuses an unstamped row on every caller-scoped mutation funnel of both
    backends. An unrecognised value resolves to `refuse`. `asi-hard` pins
    `refuse` (the pinned set is now 28 knobs).
  - **No silent claim.** An update can no longer write an owner onto a row
    that has none: the caller's `metadata.agent_id` is dropped with a WARN and
    the row stays unstamped (claiming is `ai-memory reown` only).
  - **Census.** `ai-memory doctor` reports `Unstamped owners (#3124)` on both
    backends: live unstamped, malformed and archived-unstamped counts
    (Warning when non-zero, Critical when non-zero under `refuse`).
  - Upgrade note: nothing changes by default. Before setting `refuse` (or
    enabling `asi-hard`), run `ai-memory doctor` and re-own any unstamped rows
    to the principal you call as.
