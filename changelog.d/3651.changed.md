**Behaviour change — a log sink that cannot start now stops `ai-memory` from starting.**
When `[logging].enabled = true` and the selected sink cannot be initialised
(an unusable log directory, a `syslog` sink that is misconfigured or not
compiled into the binary, or another log subscriber already installed), every
`ai-memory` command now exits with code 78 and a message naming the sink, the
error and the fix. Previously it printed "continuing without" and ran with no
logs at all, which made a broken log pipeline look exactly like a quiet one.
`ai-memory doctor` still runs and reports the failure as a Critical
"Logging pipeline (#3651)" section. If you upgrade a deployment that has logging
enabled, run `ai-memory doctor` first: a sink that was silently broken will now
stop the service until you fix it, choose another sink, or set
`[logging].enabled = false`. Scripts that call `ai-memory` without checking the
exit code should be checked too.

The log pipeline now also reports what it delivers. A running daemon exposes
`ai_memory_log_pipeline_active`, `ai_memory_log_records_delivered_total`,
`ai_memory_log_write_failures_total`, `ai_memory_log_queue_dropped_total` and
`ai_memory_log_last_delivery_seconds` on `/metrics` (the last one only after
the first delivery, so a fresh node has no series rather than a `0`), and
reports delivery failures on stderr at most once a minute. The `syslog` sink bounds name
resolution, connect, write and flush, and backs off after a failure instead
of stalling on a dead collector.
