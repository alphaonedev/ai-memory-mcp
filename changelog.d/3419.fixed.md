A captured attested direct write can no longer be replayed. `POST
/api/v1/memories`, `POST /api/v1/memories/bulk` and MCP `memory_store` validated
a caller-presented Ed25519 write signature by shape and by the ±300 s
`ATTEST_CREATED_AT_SKEW_SECS` freshness window and nothing else — and an Ed25519
signature is re-verifiable forever, so inside that window the same captured body
verified an unbounded number of times: a network observer, or anything that
logged a request body, could re-submit it to mint duplicate rows or to
**resurrect a memory the owner had deleted**, each landing
`attest_level="agent_attested"` with a genuine signature. The federated
`/sync/push` surface has carried an `X-Memory-Nonce` guard since v0.7.0 (#922);
the direct write path had none.

Schema **v95** adds the durable `attested_write_ledger` table on **both**
backends (deliberately not a sqlite-only sidecar, which would leave every
postgres deployment unguarded). One row per accepted envelope, keyed on the
SHA-256 `(agent_id, created_at, signature)` fingerprint as the PRIMARY KEY, so
the admit-once decision *is* the storage engine's uniqueness constraint rather
than a check-then-act read: two concurrent submissions of the same body can
never both be admitted. Retention is exactly the replay window the freshness
gate already enforces and is pruned on every admission, so the ledger is bounded
by the attested-write rate and never by history — no background sweep, no
operator tuning. A replayed envelope is refused with `409 CONFLICT` /
`ATTESTED_WRITE_REPLAY` (and, on the bulk surface, as a **non-retryable** row
error, so retry middleware is never armed to re-submit exactly what the guard
rejected); a ledger that cannot be consulted refuses the write `503` rather than
admitting a possible replay. A signed envelope is single-use: re-sign with a
fresh `created_at` to submit again.
