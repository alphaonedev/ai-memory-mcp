### Security

- **[federation-sync-clock] `/sync/since` records a sync clock only for the authenticated peer**
  ([#9596](https://github.com/alphaonedev/ai-memory-mcp/issues/9596)). A pull recorded a durable
  `sync_state` watermark keyed on request fields (`X-Agent-Id` and `?peer=`), so a caller could
  write or advance the clock row of another principal, including the receiver's own catch-up cursor
  rows. The row is now keyed on the authenticated peer only: the asserted `X-Peer-Id` whose
  `X-Memory-Sig` verified against its enrolled key, or the peer id the mTLS client certificate is
  bound to. A clock-writing pull (one that sends `?peer=`) whose `?peer=` or `X-Agent-Id` names a
  different principal is refused with HTTP 403 and the error tag `sync_since_peer_mismatch`; it is
  never silently re-keyed. A pull with no authenticated peer is still served and records no clock
  row. The production pullers send `?peer=`, `X-Peer-Id` and `X-Agent-Id` equal to their own id,
  so their clock rows `(peer, peer)` are unchanged. The `X-Agent-Id` trust question for other
  routes is tracked separately in
  [#9341](https://github.com/alphaonedev/ai-memory-mcp/issues/9341). Tests:
  `tests/sync_since_clock_authn_peer_9596.rs` and the
  `authenticated_pull_peer_9596_tests` unit module.
