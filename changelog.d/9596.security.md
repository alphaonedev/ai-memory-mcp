### Security

- **[federation-sync-clock] `/sync/since` records a sync clock only for the authenticated peer**
  ([#9596](https://github.com/alphaonedev/ai-memory-mcp/issues/9596)). A pull recorded a durable
  `sync_state` watermark keyed on request fields (`X-Agent-Id` and `?peer=`), so a caller could
  write or advance the clock row of another principal, including the receiver's own catch-up cursor
  rows. The row is now keyed on the authenticated peer only: the asserted `X-Peer-Id` whose
  `X-Memory-Sig` verified against its enrolled key, or the peer id the mTLS client certificate is
  bound to. The `X-Agent-Id` trust question for other routes is tracked separately in
  [#9341](https://github.com/alphaonedev/ai-memory-mcp/issues/9341).

  What this closes, exactly:
  - **Forged clock write.** A pull with no authenticated peer is still served but records no clock
    row; a request can no longer create or advance any `sync_state` row.
  - **Peer mismatch.** A clock-writing pull (one that sends `?peer=`) from an authenticated peer
    whose `?peer=` or `X-Agent-Id` names a different principal is refused with HTTP 403 and the
    error tag `sync_since_peer_mismatch` (fields `error`, `authenticated_peer`, `note`); it is
    never silently re-keyed.
  - **Unreadable agent id** ([#9665](https://github.com/alphaonedev/ai-memory-mcp/issues/9665)).
    The route reads `X-Agent-Id` once, fail closed: a repeated header or a value that is not
    visible ASCII is refused with HTTP 400 `sync_since_agent_id_unreadable` (`reason` `repeated`
    or `not_visible_ascii`) instead of being dropped or cut to its first copy. An empty value
    counts as absent, following the HTTP identity resolver
    ([#9656](https://github.com/alphaonedev/ai-memory-mcp/issues/9656)).
  - **Log level.** A failed clock write is now logged at WARN (it was DEBUG), like the
    `/sync/push` and catch-up clock writes; the pull is still served.

  What this does not change: whether an unauthenticated pull is served at all is still decided by
  the signing gate. A deployment where the operator opted out of the signing gate
  (`AI_MEMORY_FED_REQUIRE_SIG=0`) still serves unauthenticated `/sync/since` reads. Which rows such
  a read may see is a separate read-side question, tracked in [#9657](https://github.com/alphaonedev/ai-memory-mcp/issues/9657). Clock rows that a
  pre-upgrade binary wrote from request fields stay in the database; their cleanup is tracked in
  [#9655](https://github.com/alphaonedev/ai-memory-mcp/issues/9655).

  **Upgrade note (pullers).** Every puller this release ships (the sync daemon and both catch-up
  bodies) sends `X-Peer-Id`, `?peer=` and `X-Agent-Id` equal to its own id, so its clock row
  `(peer, peer)` is unchanged; every release since v0.7.0 sends the same three equal values. A
  v0.6.x puller sends no `X-Peer-Id` (its sync daemon sends `?peer=` and `X-Agent-Id`, its catch-up
  sends `?peer=` only): it is not authenticated, so it is never refused with
  `sync_since_peer_mismatch`, but an upgraded node no longer records a clock row for it until that
  puller is upgraded too. A custom client that signs as one peer and names another in `?peer=` or
  `X-Agent-Id` now receives 403 `sync_since_peer_mismatch` and must send its own id in all three.

  Tests: `tests/sync_since_clock_authn_peer_9596.rs`, `tests/sync_since_puller_ids_9596.rs` (one
  row per puller form over every agent-id character class) and the
  `authenticated_pull_peer_9596_tests` and `read_agent_id_header_9665_tests` unit modules.
