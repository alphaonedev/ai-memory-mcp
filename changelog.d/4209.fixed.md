### Fixed

- **[postgres] One ascending-id lock order for every multi-row `memories` lock path**
  ([#4209](https://github.com/alphaonedev/ai-memory-mcp/issues/4209),
  [#4210](https://github.com/alphaonedev/ai-memory-mcp/issues/4210)).
  The #4010 containment writers (swarm rewind, contamination auto-stamp) lock
  rows ascending by `id COLLATE "C"`; bulk re-own and `link` did not, so an
  interleaved pair closed a wait-for cycle and Postgres aborted one side with
  40P01 (in the observed runs the containment write). Bulk re-own now plans AND
  locks its set inside the write transaction (`ORDER BY id COLLATE "C" FOR
  UPDATE`) and rewrites exactly the locked ids, so the report names the
  rewritten rows; `link` locks source (`FOR UPDATE`) and target (`FOR KEY
  SHARE`) in id order before the owner gate. Same-shape siblings fixed with
  them: `apply_remote_link`, `consolidate` sources, `reflect` sources and
  `archive_restore` link peers. Live-PG red-first cells in
  `tests/pg_lock_order_4209_4210.rs`.
  The re-own cell's heap-placement fixture now re-seeds both rows (bounded) instead of
  relying on a no-op update to move one row, so it no longer panics on a churned
  `memories` table ([#4412](https://github.com/alphaonedev/ai-memory-mcp/issues/4412)).
  Lands as one unit with the #4010 rewind order and the #4329/#4330 forget and `run_gc`
  order: alone it would move a link-vs-rewind deadlock to the other direction.
