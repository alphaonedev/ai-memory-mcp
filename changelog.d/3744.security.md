**Userinfo in a webhook URL no longer hides the target from the SSRF guard at registration (#3744, security, GA).**

`subscriptions::validate_url` — the syntactic SSRF guard `insert` runs when a tenant registers a webhook — took the host as the text before the last `:` of the raw authority. For `https://a:b@169.254.169.254/` that made the "host" the USERNAME `a`; the loopback and private-range checks ran against that literal and passed, so a subscription aimed at a private, loopback or cloud instance-metadata address was ACCEPTED whenever the caller added userinfo. At dispatch the DNS-resolved guard refused it, but only because `user:pw@host` is not a resolvable name — a defence that held by accident, under the wrong reason (`dns_ssrf_rejected`), and that nothing recorded as load-bearing. Both guards now strip userinfo at the LAST `@` of the authority before any host extraction (`subscriptions::authority_without_userinfo`), so the syntactic guard refuses the row at the door naming the real host, and the DNS guard reads the same host and refuses for the address class, not for a resolver hiccup. Userinfo is stripped, not refused: a public host behind basic auth still registers. Pinned by three unit cells beside the guards (each planted shape refused at registration naming the real host and never echoing the userinfo; the DNS guard's role stated explicitly) and `tests/webhook_userinfo_ssrf_3744.rs` on the `insert` surface — RED on the pre-fix tree, where every `insert` succeeded.
