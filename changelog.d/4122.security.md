**`ai-memory reembed` goes through inference-egress admission and the
pinned builder (#4122).** The verb built its embedder with the unpinned
`Embedder::from_resolved` and never consulted `AI_MEMORY_INFERENCE_EGRESS`:
under `deny` (or `loopback-only` against an off-host vendor) it sent the
content of EVERY memory in scope to the configured embedding endpoint — the
most content-heavy egress the product performs — and on the ollama+Nomic lane
it ran an unadmitted model pull. Every other embedder-building surface (MCP
stdio init, `build_embedder`, curator, atomise, reload) admits through
`admit_inference_target` and builds through `from_resolved_pinned`; `reembed`
was the outlier. The verb now admits the resolved embed endpoint BEFORE any
client exists: a refusal is audited (a signed `egress.inference_refused`
row), named on stderr with the posture knob (never the endpoint secret), and
exits with `EXIT_EMBEDDER_INIT_FAILED` having sent nothing and written no
vector; an admitted endpoint is built pinned (`internal-only`
resolve-then-pin). `allow` is byte-identical. Pinned by
`tests/reembed_egress_admission_4122.rs` (RED on the pre-fix tree: the `deny`
run exited 0 and the endpoint received the content; the `loopback-only`
off-host run was not refused) with an `allow` control, an `internal-only`
admitted-and-pinned end-to-end cell, and a structural leg that refuses any
unpinned `Embedder::from_resolved(` call site outside `src/embeddings.rs`.
