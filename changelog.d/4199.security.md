**The forensic audit log no longer forks its signed hash chain; an unreadable chain tail now runs without the forensic sink and records the outage, or refuses boot under `AI_MEMORY_REQUIRE_FORENSIC_SINK`.**
The forensic governance log (`forensic-<YYYY-MM-DD>.jsonl` in the audit
directory) is written on every boot. Before this, any failure to read its chain
tail (a directory or file that could not be listed, opened or read, or files
holding no parseable row) was discarded and the next signed row was written
with the genesis `prev_hash`, forking the chain silently (#4199). Now:

- The tail is the last parseable row of the newest daily file that has one. An
  empty or unparseable newest file no longer hides the chain held by older
  files; it continues from the most recent earlier row (#4202). A torn last
  line is still skipped, as before.
- A file dated after the current UTC day is never the tail. It is reported
  (an ERROR line, the metric below, and a Critical in `ai-memory doctor`) and
  never deleted (#4203). Because a backward clock step across midnight can
  make today's file look future-dated, and the next row then continues from
  an earlier day, the ledger-writing verbs also attest it with the signed
  outage row described below.
- A missing or empty forensic directory still starts a fresh chain.
- When the tail cannot be established, the process continues WITHOUT the
  forensic sink (no forensic rows are written, so the chain is not forked) and
  records the outage: an ERROR naming the directory and cause, the
  `ai_memory_forensic_sink_unavailable_total` metric, a Critical
  `Forensic audit log (#4199)` section in `ai-memory doctor`, and a signed
  `audit.forensic_sink_unavailable` row in `signed_events`. The signed row is
  written only by the verbs that write the ledger (`serve`, `mcp`,
  `sync-daemon` and the other writing commands). `doctor`, `backup`, `export`,
  `restore` and the read-only commands never open the store for it. The row
  is written without migrating the database and only when the database is
  already at this binary's schema; the first boot after an upgrade therefore
  reports the outage on stderr and in `doctor` without a signed row. A stuck
  outage produces one row per day, not one per command: a new row is written
  when the file or cause differs from the newest outage row, or on a new UTC
  day, so an outage that recurs after a repair is attested again.
- New knob `AI_MEMORY_REQUIRE_FORENSIC_SINK` (truthy: `1`/`true`/`yes`/`on`):
  the same condition refuses boot with exit code 78 instead; `ai-memory doctor`
  still runs. The `asi-hard` security profile pins it on, so a hardened
  deployment refuses to start without a working forensic log (31 pinned knobs).

To recover, repair the named file, or move it out of the audit directory; the
chain then continues from the newest readable file.
