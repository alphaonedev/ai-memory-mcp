`bind_agent_pubkey` now requires **target-bound authorization**, keeps an **append-only key history**, and `agent_subkey_certs.revoked` finally **gates verification**. Three defects, one control surface. (1) The bind funnel took a self-asserted base64 key — admin-gated, curve-validated and audited, but anyone with the admin role could bind a key they controlled to another agent's id and mint `agent_attested` writes as that agent: the strongest provenance claim the substrate makes, forgeable from a role claim. The daemon now issues a durable, single-use, domain-separated candidate-key challenge (`POST /api/v1/agents/{id}/pubkey/challenge`), and only the backend's atomic consume can construct the opaque receipt that mints a `PossessionProof`; both receipt and exact `(agent_id, candidate_key)` witness are consumed by value. Proof verification reads the process UTC clock internally and rejects the exact expiry boundary, so a direct Rust caller cannot revive an already-consumed receipt by supplying an earlier time. Both stores atomically compare those claims to current/history state: candidate proof admits only first bootstrap or an idempotent same-key retry; once an identity is anchored, every distinct replacement requires `append_lineage_record`'s current/predecessor-key signature (or guardian-quorum recovery). Generic admin authority can no longer substitute for target-agent possession. The CLI uses the same persisted challenge and atomic consume for offline bootstrap proofs; caller-constructed challenges are not accepted, rotation uses `identity succeed`, and the history records `lineage_succession`. (2) Rebinding used to OVERWRITE the flat `metadata.agent_pubkey`, destroying the anchor every prior `agent_attested` row depended on. Schema **v97** adds `agent_pubkey_history` on both backends — one row per `(agent_id, version)`, half-open `[bound_at, superseded_at)` window, and admitting authority — with existing bindings backfilled as `legacy_unproven`. Rows are never deleted and keys are never rewritten; a partial unique index permits at most one open key. Import, sync, and federation re-verification resolve the exact historical key at the signed envelope timestamp, fail closed on corrupt or ambiguous history, and never substitute the current key across a revoked gap; the flat-key fallback exists only when an identity has no history at all. (3) `revoked` shipped with the v79 sub-key certificate table but was never enforced. `agents revoke-subkey-cert` now sets it, and the v2 ingest gate refuses a revoked sub-key before stamping; a second certificate over the same instance key cannot resurrect it.

The v97 ledger is now the storage-authoritative projection: SQLite and PostgreSQL backfill only canonical `agent:<metadata.agent_id>` registration rows, then reconcile both registration JSON mirrors on every generic write, stripping transported keys and downgrading any signature/stamp whose signed bytes changed. A pre-v97 noncanonical `_agents` poison row therefore cannot win a victim's version-1 anchor. Authorized bind, lineage rotation/recovery, and revoke mutations likewise clear the registration's now-stale `write_signature` and force `claimed` in both mirrors inside the same identity transaction. Import, direct sync, federation pull/catchup, and both HTTP push backends sanitize before claim honor or verification, resolve history only for a usable presented signature, and report refused key transport. A predecessor-signed succession may advance only the matching open head; an independently verified M-of-N guardian recovery is recorded distinctly and is the sole route from a closed head. Stale prepared succession, challenge reuse, direct candidate-key replacement, missing/ambiguous historical windows, signed registration key planting, and stale registration-attestation survival all fail closed.
