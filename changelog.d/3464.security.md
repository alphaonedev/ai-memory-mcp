`bind_agent_pubkey` now requires **proof of possession** of the key being bound, keeps an **append-only key history**, and `agent_subkey_certs.revoked` finally **gates verification**. Three defects, one control surface. (1) The bind funnel took a self-asserted base64 key — admin-gated, curve-validated and audited, but with nothing proving the caller held the matching private key, so anyone with the admin role could bind a key they controlled to another agent's id and then mint `agent_attested` writes as that agent. The daemon now issues a single-use, domain-separated challenge (`POST /api/v1/agents/{id}/pubkey/challenge`) that the candidate key must sign; the answer rides on the existing `PUT /api/v1/agents/{id}/pubkey`. The control is a type, not a check: `identity::pubkey_bind::PossessionProof` has no public constructor and `storage::bind_agent_pubkey` (plus the `MemoryStore` trait method and both adapters) takes one, so an unproven bind is unrepresentable on every present and future surface rather than guarded at the ones that exist today. The CLI proves possession from the local key store, or accepts an offline signature via `agents bind-challenge` + `bind-key --proof-file`; the lineage-rotation path is admitted by the succession signature it already verifies, recorded distinctly as `lineage_succession`. (2) Rebinding used to OVERWRITE the flat `metadata.agent_pubkey`, destroying the anchor every `agent_attested` row the previous key signed is verified against. Schema **v95** adds the append-only `agent_pubkey_history` ledger on both backends — one row per (agent, dense 1-based key version), composite PK `(agent_id, version)` as the anti-equivocation constraint, a half-open `[bound_at, superseded_at)` window, and the `bind_authority` that admitted it — with every live binding backfilled as version 1 under the honest `legacy_unproven` label. Rows are never deleted and `pubkey_b64` is never rewritten; revoking a key CLOSES its window instead of losing it, and `storage::agent_pubkey_at` resolves the key that was live at any instant. (3) `revoked` shipped with the v79 table but was written by nothing and read by nothing, so delegation revocation never fired: a leaked instance sub-key kept attesting for the whole life of its cert. `agents revoke-subkey-cert` sets it, and the v2 ingest gate refuses a revoked sub-key after the §2.3 chain verifies and before the attestation is stamped — keyed on the sub-key, so a second cert over the same instance key cannot resurrect it.
