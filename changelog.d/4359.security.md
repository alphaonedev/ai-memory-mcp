**Notify is now bound per sender, not only per (sender, recipient inbox) (#4359).** The daily write quota is keyed `(agent_id, namespace)` and a notify was charged in the recipient's `_inbox/<target>` namespace, so one sender notifying 1,500 distinct recipients opened 1,500 fresh rows and was never refused (1,001 to one recipient was). Every notify on every surface and both backends (`memory_notify`, `POST /api/v1/notify`, `MemoryStore::notify` sqlite and postgres) now also charges a per-sender aggregate row `(sender, "_notify")` in the existing `agent_quotas` table (no migration): count-only, the same `AI_MEMORY_MAX_MEMORIES_PER_DAY` ceiling, refused with the existing `QUOTA_EXCEEDED` shape naming `_notify`, refunded when the per-recipient charge or the insert fails; postgres charges it in the same transaction as the insert. The aggregate row is excluded from the namespace-omitted rollup so a notify is not reported twice, and visible via `memory_quota_status` with `namespace: "_notify"`. A legitimate sender fanning out more than the daily ceiling must raise `AI_MEMORY_MAX_MEMORIES_PER_DAY`. Federation receive (#4354) and CLI writes (#1621) are unchanged. 5-agent vote (4d3ea1c5).
