**A queued MINT's token is returned to the APPROVER, not to the requester** —
documented rather than changed (#3474 advisory 2). When the identity
namespace's governance policy parks a mint, the requester's `202` carries a
`pending_id` and NO token: there is none yet. A token cannot be produced at
queue time and delivered later without persisting it in raw form, which this
surface never does, so the mint is deferred to the apply step — the approving
principal's `{"approve_pending_id": …}` request is what mints, and the `200` it
receives is the only place that token ever appears. The requester must obtain
it from the approver out of band, or the approver hands it to the agent
directly. The queued BIND form has no such wrinkle: its payload already carries
the digest of a token the operator holds. Stated on the route rows, in the
admin guide and in the module docs, and asserted by a test so the documentation
cannot quietly stop being true.

**The mint rate limit is a FIXED window, so the bound at a boundary is 2N**
(#3474 advisory 4). Ten mints per sixty seconds per admitted caller means a
caller straddling a window edge can issue up to twenty across two adjacent
seconds. That is burst-shaping, not a bypass of the cap: the fixed window is
what keeps the limiter's table bounded and each decision auditable from one
`(window_start, count)` pair. A sliding window is deliberately NOT used, and
alerting on mints-per-minute should be sized for 2N.
