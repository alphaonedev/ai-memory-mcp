### Fixed

- **[postgres] Bulk `forget` and the `run_gc` evict sweep lock their victim rows in ascending id order**
  ([#4329](https://github.com/alphaonedev/ai-memory-mcp/issues/4329),
  [#4330](https://github.com/alphaonedev/ai-memory-mcp/issues/4330)).
  Both funnels ran bare predicate statements (the `forget` crypto-erase `UPDATE` and `DELETE`, the
  `run_gc` unordered `SELECT ... FOR UPDATE` and `DELETE`, and the archive path with no prior lock),
  so Postgres took `memories` row locks in heap order. Interleaved with an ascending-order
  containment writer (#4010) on an overlapping pair, the wait-for cycle aborted a side with 40P01.
  Each transaction now reads and locks its victim set up front with
  `ORDER BY id COLLATE "C" FOR UPDATE` and every later statement (archive copy, link snapshot,
  scrub, erase, delete) is bound to that locked id set, so the archived, erased, tombstoned and
  deleted sets are one set. A lock or serialization error rolls the whole transaction back through
  the existing typed error and bounded retry funnel; nothing is partially erased. The ordering is
  written locally in `src/store/postgres/lock_order_4329.rs` in the same form as the #4209 helper,
  so the two compose and either can land first. Tests: `tests/pg_lock_order_4329_4330.rs`
  (live-Postgres `pg_blocking_pids` barrier cells, no triggers, no sleeps).

  Refs [#4037](https://github.com/alphaonedev/ai-memory-mcp/issues/4037): on the carrier a row that
  matched the predicate after the victim read was hard-deleted with no archive copy when
  `archive = true`, for both `forget` and `run_gc`. Binding the archive copy, link snapshot and
  DELETE to the locked id set closes that shape (a late row waits for the next call). Land together
  with or after #4369: alone, this change moves which `memory_links` direction can deadlock against
  forget and `run_gc` rather than removing it.
