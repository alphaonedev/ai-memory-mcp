Owner-scope the MCP archive read and restore surface. `memory_archive_list` and
`memory_archive_stats` took no caller and queried the archive owner-blind, so
any agent could read every other tenant's archived title, content and
`metadata.agent_id` — the same rows `memory_get` masks as not-found for that
agent, and exactly the corpus-shape metadata the HTTP twins have gated behind
the admin role since #943. `memory_archive_restore` called the owner-blind
restore primitive while the gated `restore_archived_for_caller` twin — used by
`POST /api/v1/archive/{id}/restore` since #940 — sat unused on this surface, so
any agent could pull another owner's archived row back into the live working
set by an id it cannot even read. All three verbs now resolve the same
read-visibility principal the rest of the MCP read surface does, and the
listing, the aggregate and the restore gate share one single-sourced ownership
predicate, so what a caller can see in the archive is exactly what they can
restore from it. A refused restore returns the same message an absent id
produces, so the surface is not an archived-id oracle.

The `memory_archive_restore` tool documentation claimed `expires_at` is cleared
on restore. It never was — the original expiry is preserved, so a row archived
by TTL expiry is reapable again on the next gc tick. The text now says so and
points at `memory_update` for extending the deadline.

No `as_admin` escalation is added to the listing or the aggregate here: that
switch has to be gated on the `[admin].agent_ids` allowlist introduced
alongside the archive-purge fix, so it is carved out to a follow-up (#3455).
Until then an operator on the MCP surface sees only their own archived rows —
a functional narrowing versus the admin-gated HTTP twin, reversible, and never
a disclosure.

The single-operator default (`AI_MEMORY_AGENT_ID` unset) is unchanged on all
three verbs.
