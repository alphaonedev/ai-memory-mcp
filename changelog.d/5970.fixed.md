The cert-expiry and declaration-hash gates take their base only from `scripts/ci-commit-range.py` in CI (#5970; GOD ruling 2026-10-05; 5-agent vote (4d3ea1c5), decision 424172a1). Before, a job-level or workflow-level `DECLARATION_GATE_BASE` or `CERT_EXPIRY_BASE` passed the static workflow pin and won over the helper at run time, so a creation push with `DECLARATION_GATE_BASE: HEAD` compared the pin with itself and passed. Each gate is now closed-world on its own variable family: every `DECLARATION_GATE_*` or `CERT_EXPIRY_*` shell variable, exported or only set in the shell (for example by a `BASH_ENV` file), other than the local overrides (`DECLARATION_GATE_LOCAL_BASE`, `DECLARATION_GATE_LOCAL_PREVIOUS_PIN`, `DECLARATION_GATE_LOCAL_ROOT`, `CERT_EXPIRY_LOCAL_BASE`, `CERT_EXPIRY_LOCAL_HEAD`) is refused by name wherever it is set, even when empty, and the local overrides are refused whenever `GITHUB_ACTIONS` is set, even to an empty string; the refusal is a red job that names the variable and `scripts/ci-commit-range.py`. The cert gate's empty-event local path is also refused whenever `GITHUB_ACTIONS` is set. The static pin now reads the env that reaches each script-gate step (workflow, job and step levels, the way Actions merges them; it must be exactly the six event inputs), refuses either variable prefix anywhere in the workflow, and refuses `continue-on-error`, `GITHUB_ENV`, `GITHUB_PATH` and `container:` in a script-gate job. A new `--gate-step-env JOB --workflow FILE` mode prints that env, and each gate's self-test uses it to plant the variable at job level and at workflow level in a copy of the real workflow (and in a `BASH_ENV` file as an unexported shell variable) and run the gate under `GITHUB_ACTIONS=true` and an all-zero `before`: every such leg is red and names the variable. A creation push with the unmutated workflow is red, never not-applicable and never a skip; that verdict is advisory by construction, because a required status check does not gate a branch-creation push (#5851).
