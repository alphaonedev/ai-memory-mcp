**A forensic audit log that cannot be written is now a visible outage, not a silent drop.** A read-only forensic directory, or a read-only daily file, used to let every process start "with the forensic sink" while the background writer dropped every row with only a trace line: no metric, no `doctor` signal, and no refusal under `AI_MEMORY_REQUIRE_FORENSIC_SINK`. Start-up now proves the log can be appended to (the directory accepts a new file and today's file, if present, opens for append), so this degrades with the #4199 outage signals or refuses to start under require-mode. A row the writer cannot persist later (a remount, a full disk) is counted in `ai_memory_forensic_sink_unavailable_total` and reported on stderr at most once a minute, with the number of rows dropped since the previous line, so a log that turns read-only mid-run does not flood stderr (#4310), and `ai-memory doctor` reports whether the log is writable (Critical when not). Each row and its newline are also written in one call, so two processes appending the same daily file cannot glue two rows onto one line (#4302, #4304). The forensic chain can still fork when two processes write the same log at once (each keeps its own chain tail); that is tracked in #4304. The start-up write check creates its probe file exclusively and never through a symbolic link, under a random name, so a link planted in the audit or log directory cannot make it truncate another file (#4322). A process killed between creating and removing that probe can leave an empty hidden `.ai-memory-write-probe-*` file behind; it holds nothing and the next start is unaffected.
