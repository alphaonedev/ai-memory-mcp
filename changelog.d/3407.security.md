### Security

- **[authz] Cross-tenant `DELETE /api/v1/subscriptions` and
  `DELETE /api/v1/namespaces` answer with ONE closed refusal shape on both
  backends, and the refusal names nobody**
  ([#3407](https://github.com/alphaonedev/ai-memory-mcp/issues/3407)).
  Pre-fix the sqlite unsubscribe answered `200 {"removed": false}` for
  another agent's row while postgres answered 403; the namespace-standard
  clear answered 400 (sqlite) / 403 (postgres) with a body that named the
  owning agent — the identity oracle #3426 closed for memories and left open
  on the namespace-standard SET and CLEAR gates (`(caller=…, owner=…)` /
  `(owner: …)`, on MCP and HTTP). Both routes now refuse a cross-tenant act
  through `handlers::parity::owner_gate_refusal` (403, `code: NOT_OWNER`,
  the SSOT `error`, `caller`, and the resource key — `id` / `namespace`);
  the owner goes to the `ai_memory::authz` trace at the gate. A genuinely
  absent subscription id keeps the idempotent `200 removed: false`. New SSOT
  consts `errors::msg::{CALLER_DOES_NOT_OWN_NAMESPACE_STANDARD,
  CALLER_DOES_NOT_OWN_PARENT_NAMESPACE_STANDARD,
  CALLER_DOES_NOT_OWN_SUBSCRIPTION}`; the `memory_namespace_set_standard` /
  `memory_namespace_clear_standard` MCP refusals carry the same bare text.
