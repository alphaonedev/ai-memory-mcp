### Fixed

- **[test-only] Two load-sensitive tests failed on a saturated gate host, measuring
  the host rather than the code**
  ([#3509](https://github.com/alphaonedev/ai-memory-mcp/issues/3509)). Both were
  green in isolation on the very same binary; neither ever indicated a product
  defect. Test-only change — no `src/`, schema, or product behaviour is touched.
  - `tests/auto_atomise/core.rs::test_auto_atomise_refused_memory_not_atomised`
    read the **suite-wide** mock-curator counter after a 300 ms `sleep`
    (`curator must not fire when the originating insert was refused — left: 2,
    right: 0`). Both halves were wrong: the counter is incremented by every case
    in the binary through one process-lifetime worker whose in-flight jobs cannot
    be awaited, and `drain_workers` only waits for that counter to *look* stable
    for a wall-clock window — so on a loaded host a previous case's queued jobs
    were still running and their curator calls landed after this case's
    `reset_mock()`. The "2" was another case's leftovers. The case now owns a
    **private** curator and a **private**
    `background::atomise_worker::spawn_joinable` worker, so the observed count is
    attributable to this case alone, and quiescence is the substrate's own
    completion signal — `drop(queue)` then `join()`, which returns only after
    every buffered job has drained. No sleep, no poll, no deadline to lose under
    load. A new `store_then_maybe_enqueue` helper performs the production
    sequence (commit, *then* offer the committed id to the auto-atomise funnel),
    so the refused write is unreachable-by-construction rather than by the test
    politely declining to call the funnel; a positive control runs first through
    the same wiring so the negative leg cannot pass vacuously; and the refusal is
    additionally asserted against the ledger (no durable row, no derived atoms).
    Measured under a deliberate 12x CPU oversubscription: **7/10 failures before,
    0/20 after**.
  - `tests/capture_layers_perf_budget.rs::l4_capture_turn_p95_under_budget`
    asserted a 100 ms wall-clock p95 in a **debug** binary
    (`p95 = 390 ms > budget 100 ms over 200 calls`). The release-profile budget
    (25 ms) — the load-bearing contract — is unchanged and still unconditional.
    Under `debug` the wall-clock assertion is now armed only by the test-harness
    knob **`AI_MEMORY_PERF_BUDGET=1`**, read by this integration-test binary and
    by nothing else (never written — no `set_var`; no `src/` path consults it;
    deliberately absent from `.github/`, so CI cannot silently arm a wall-clock
    budget on a host it does not control). The default debug path is **not** a
    no-op: it still drives all 200 calls, asserts each completed and missed
    dedup, asserts the reported p95 is a genuine measured sample, and prints
    p95/min/max so a regression stays visible in the log. Measured under a
    deliberate CPU+I/O load: **10/10 failures before, 0/20 after**, with the p95
    (371-448 ms) still measured and recorded; with the knob armed the assertion
    still fires (5/5) under the same load, proving it is a real gate and not a
    disabled one.
