### Fixed

- **[data-integrity][cost] Every curator sweep stored a `_curator/reports`
  self-report as a first-class, permanently-retained, EMBEDDED memory**
  ([#3345](https://github.com/alphaonedev/ai-memory-mcp/issues/3345)).
  Measured on the certified f1 tier (`curator --daemon --interval-secs 300`,
  2026-09-01): **24,930 rows in `_curator/reports` — 24,801 of them carrying a
  paid embedding — against 512 memories outside system namespaces**. 97% of the
  store, and of every backfill / re-embed pass over it, was the curator talking
  about itself, at recurring embedding cost, polluting stats and inventory. The
  same namespace was the recurrence site of
  [#1466](https://github.com/alphaonedev/ai-memory-mcp/issues/1466)
  (2,905 of 2,921 leaked rows).
  - **No embedding is ever spent on a substrate row.** All four SQLite
    unembedded selectors and BOTH postgres `list_unembedded` arms now carry
    `visibility::SQL_AND_NOT_SUBSTRATE`, the SQL twin of the #3348
    `is_substrate_namespace` predicate, built from the SAME closed const lists —
    one posture in two forms, not a second visibility mechanism. A namespace
    added to the substrate SSOT inherits the no-embed posture with no second
    list to keep in sync, and compile-time assertions prove every entry is safe
    to splice into SQL (`substr(col,1,n) = '…'`, deliberately not `LIKE
    '_curator/%'`, because `_` is a LIKE wildcard in both engines). The
    operator-driven `reembed` scan uses the #3348 opt-in shape: an unscoped
    sweep skips substrate rows, `reembed --namespace _curator/reports` still
    heals that namespace on purpose.
  - **Bounded retention.** The per-sweep report is `Tier::Short` with an
    explicit 24 h expiry. The writer previously asked for `Tier::Mid` and
    `expires_at: None`, i.e. a first-class memory minted once per sweep with
    only the 7-day tier default (backfilled by `db::insert` per #1466) standing
    between it and permanence — and with no GC running, not even that. Each
    cycle now folds the day into ONE summary row in `_curator/reports/daily`, so
    the day's aggregate outlives its per-sweep detail: bounded retention with no
    information loss.
  - **The missing reaper.** Expiry stamps are inert without a GC tick, and
    `spawn_gc_loop*` is pushed only from `bootstrap_serve` — a host running
    nothing but `ai-memory curator --daemon` (the measured f1 topology) ran NO
    GC at all. The curator daemon now runs `gc_if_needed` per cycle, honouring
    the operator's resolved `[storage].archive_on_gc` posture rather than
    assuming the safe-looking default (an explicit `false` is an erasure
    posture, #1775 / #3272).
  - **`ai-memory curator --prune-reports [--apply]`** collapses the historical
    backlog: DRY RUN by default with a count, folds each affected UTC day into
    its summary before touching anything, then re-targets that day's rows onto
    the #3345 retention — `Tier::Short`, `created_at + 24 h`, earliest-wins —
    so a June row is already past its window while a fresh one keeps its full
    day. It NEVER deletes (reaping stays with the audited, archiving GC path),
    only ever moves an expiry earlier, touches no namespace but
    `_curator/reports`, and is chunked, resumable and idempotent on both
    backends (`MemoryStore::prune_curator_reports`, admin-gated, refusing a
    tenant caller loudly rather than returning a misleading zero count).
    A row is only ever re-targeted AFTER its day's summary is durable, so the
    one way this could lose information is structurally excluded.
  - The backlog marker is the **tier**, not a missing expiry, and that is a
    measured correction: `db::insert` backfills the tier default (#1466), so
    the pre-fix `Tier::Mid` writer's rows were stamped `created_at + 7 days` on
    the way in. The 24,930 f1 rows were **expired-and-never-reaped**, not
    missing-an-expiry — a NULL-expiry prune would have reported "nothing to do"
    against the very store that motivated the issue.
  - **Stats and inventory stop hiding the pollution.** `Stats` gains an
    additive `substrate` count and `ai-memory stats` leads with
    `memories: <total - substrate>`. `total` deliberately keeps its documented
    [#2334](https://github.com/alphaonedev/ai-memory-mcp/issues/2334) meaning
    (the RAW physical count) — redefining it would re-open exactly the
    boot-vs-stats reconciliation defect #2334 closed. `GET /api/v1/namespaces`
    withholds substrate namespaces from an unscoped listing on both backends,
    with naming the namespace (or an ancestor of it) as the opt-in — the #3348
    shape, so no new query parameter and no MCP-schema / param-census / docs
    pin moves.
  - Regression suites on both backends: `tests/curator_report_bloat_3345.rs`
    and `tests/curator_report_bloat_3345_pg.rs` (live cluster), plus in-module
    truth-table and projection tests. No schema rung; no new admin/bypass site.
