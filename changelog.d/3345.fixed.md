Stop the curator's per-sweep self-report from being a first-class, embedded,
recall-visible memory. Every cycle wrote a `_curator/reports` row that the
boot-time embedding backfill then paid to embed: on one node that was 24,930
rows — 97% of the store — and 24,801 embedding calls, against 512 real
memories. Self-reports are now written in a system-only `operational`
lifecycle state, so the one already-audited visibility allow-list hides them
from recall, list, stats, taxonomy and export on both backends, and the
embedding backfill selectors (SQLite and PostgreSQL) are gated on that same
allow-list — it never spends an embedding on a row no read path can return,
which also stops paying for tombstoned, quarantined and contaminated rows.
Reports carry a 24-hour TTL, the existing backlog is stamped (never deleted)
by a chunked, idempotent, self-terminating boot sweep on both backends, and
`ai-memory curator --daemon` now runs the TTL sweep it never had — the absent
reaper, not the writer, is why the rows accumulated. This is a recurrence of
#1466, which leaked 2,921 rows, 2,905 of them in this same namespace.
Operators read the ledger with `ai-memory curator --reports`.
