**The External-PR operator-approval gate now judges push runs, and merge-queue runs through the PR the queue ref names (#6117, #6193, #6227).**
The required context `External-PR operator-approval gate (author outside team
=> @alphaonedev review)` answered every non-`pull_request` event "not
applicable (pass)". Once `chain/**` pushes ran the workflow, a push run could
post a passing check of that name on an external PR's head sha beside the
failing PR run. The gate is now `scripts/check_external_pr_approval.py`
(self-tested in the job): on `pull_request` it judges the event's PR; on
merge_group it parses the PR number from `merge_group.head_ref`
(`gh-readonly-queue/<base>/pr-<N>-<sha>`, the number capped at 9 digits; the
queue commit is never a PR head), requires the ref's `<sha>` to equal
`merge_group.base_sha` (the queue commit's parent, as every recorded real
payload shows; #6242, #6325) and judges that open PR at its own head sha,
failing closed when no PR can be derived or the sha is missing, short,
non-hex or different; on any other event it lists the open PRs whose head is the run's sha
and applies the same rule to each (no such PR: pass). An API error, unparsable page or
malformed entry fails the job. The checkout that supplies the script uses
`persist-credentials: false`. A PR opened after a push run already judged its
sha is tracked in #6213.

Rounds 4-5 tightened the verdict and its output. The operator's LATEST
deciding review of the head sha decides: APPROVED, CHANGES_REQUESTED and
DISMISSED count, ordered by `(submitted_at, id)`, so a later change request or
dismissal makes the next run of the check fail (#6329). The workflow has no
`pull_request_review` trigger and `release/v1.0.0` has no merge queue, so a
check that already passed stays green until the job runs again (#6511, kept
open by the 3-agent vote (6def5ab6), Q3). Bot authors such as `dependabot[bot]`
are judged instead of refused, and from a fork they need the approval (#6259).
Text relayed into `::error::` lines is workflow-command escaped (CR, LF, `%`,
C0 controls, DEL, NEL, U+2028/9), tokens are redacted (`gh[pousr]_`,
fine-grained `github_pat_` including its tail, and `Authorization`-style
`bearer`/`basic`/`token` values; #6243, #6328), and a relayed gh stderr line
is cut to 300 characters. An error page between paginated arrays fails closed
(#6332). The approval job is pinned exactly: its keys, its token scopes
(`contents: read`, `pull-requests: read`; workflow default `contents: read`),
its steps' keys (no `shell:`, no `defaults:`), and its env (`GH_TOKEN` from
`github.token`, no `secrets.`) (#6261, #6335, #6341, #6387, #6388). Every
workflow `python3 <script>.py` runs with `-I` (#6240, #6241, #6389).

Round 6. On merge_group an open-PR listing that names the queue PR more than
once fails closed with its own message instead of claiming the PR is not open
(#6637). A token prefix followed by any body is redacted, its underscore may
arrive percent-encoded (`%5F`, `%255F`), and a message that holds a token only
after percent-decoding (up to 4 rounds) or still decodes after them is
redacted whole, so an encoded or line-wrapped credential never reaches the
`::error::` line (#6578). The checkout that supplies the evaluator is pinned to
exactly `with: persist-credentials: false`, so a `ref:`, `repository:`, `path:`
or `token:` there fails the pin (#6629). The workflow's top-level keys are
pinned exactly (`name`, `on`, `permissions`, `concurrency`, `jobs`), so a
workflow `env:` such as `GH_HOST` cannot redirect the Evaluate step (#6630).
The `merge_group: types: [checks_requested]` trigger is pinned on c8-precheck,
ci, coverage, claude-md-guard, cert-postgres-age and postgres-ignored (#6682,
#6727): the last two carried required contexts without it, so a merge queue
would wedge on them. The pinned set is derived from the required-contexts
gate's covered workflows, and every self-hosted job in a workflow a fork
pull request can reach keeps the fork-PR refusal ci.yml's `check` job uses (#6727). A new `scripts/check_commit_trailers.py --range <base>..HEAD` refuses
a `Claude-Session:` trailer (#6580). The CI v2 shard partition step runs
`python3 -I scripts/ci/partition_test_binaries.py`, like every other workflow
`python3` script or module run the `-I` scanner covers (#6734, #6241).
Round 7 makes these pins check effect, not text. The fork-PR refusal pin
evaluates each job-level and refusal-step `if:` against fork pull-request
contexts on every self-hosted runner leg, and requires the refusal step to
carry only `name`, `if` and `run` with an `exit 1` line. A commented-out,
never-true or `continue-on-error` refusal now fails (#6849). The self-hosted
set and the merge_group set are derived from every workflow under
.github/workflows/, so a new merge_group trigger or a new self-hosted
fork-reachable job outside the pinned list fails (#6850). The `-I` scanner
also covers `python3 -m` module runs, including glued and option-separated
forms; ci.yml's `python3 -I -m unittest discover -s scripts/ci/tests` is
pinned, and coverage.yml's `python3 -m pip install` is the one allowlisted
row (#6799). The percent-encoded underscore forms and the decode bound of 4
rounds in the approval-gate redaction are pinned by exact-output tests (#6845).
