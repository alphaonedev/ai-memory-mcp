**Webhook dispatch dead-letters a forbidden-address target on the first
attempt (#4165).** The DNS-resolved SSRF guard recorded every refusal under
one DLQ reason, `dns_ssrf_rejected`, which lumped a permanent verdict (the
stored URL resolves to a private, link-local, loopback or cloud-metadata
address, or names a host that can never resolve) together with a transient
one (the resolver did not answer). The retry ladder could not tell them
apart, so it had to treat the shared token as retryable and a webhook aimed
at `169.254.169.254` or `10.0.0.1` burned the full backoff ladder (about
6.2 s of a bounded dispatch worker per event) for the same answer before
reaching the DLQ. The guard now returns a typed refusal
(`subscriptions::dns_guard::DnsGuardRefusal`): the address-class verdict
lands as `dns_ssrf_forbidden_address` and is terminal (one attempt, no
backoff sleep); a resolver failure lands as `dns_resolution_failed` and is
retried as before. The old token is removed; nothing but tests pinned it.
Pinned by the ladder cell in `src/subscriptions/dns_guard_4165_tests.rs`
(RED on the pre-fix tree: four attempts, 6.4 s) and the classification
matrix beside it; `tests/credential_to_sink_3711.rs` and
`tests/webhook_userinfo_ssrf_3744.rs` re-pin the class each of their
fixtures belongs to.
