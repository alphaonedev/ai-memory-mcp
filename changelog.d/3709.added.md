**Zero-config TLS on first boot, and same-installation trust for the bundled clients (#3709 items 1 and 5).**

Under the "only encrypted data in transit" mandate (#3705) a plaintext
listener is refused, so a SINGLETON `serve` with no `--tls-cert`/`--tls-key`
now generates an installation-local CA and server certificate under
`<key_dir>/tls/` (`local-ca.pem`, `local-ca.key` 0600, `server.pem`,
`server.key` 0600, directory 0700; CA 3650 days, leaf 90 days covering the
bind host), renews the leaf inside a 30-day window at boot and by a daily
in-daemon task that hot-reloads the listener, and reports every outcome
loudly — a renewal failure never downgrades to plaintext
(`src/tls_bootstrap.rs`, `daemon_runtime::resolve_tls_material`). Generation
is not trust: the bundled clients (`doctor --remote`, the MCP forwarder)
add the local CA as a root for THIS installation only; it is never used to
trust a federation peer (the #2448 posture is unchanged). `ai-memory doctor`
"Transit encryption (#3705)" gains the `local_tls_material` fact (absent /
days to expiry + SANs / inside the renewal window / EXPIRED — refuses /
unreadable). Per the 3x7 audit ruling — an unmanaged CA minted into an
enterprise estate is an audit finding, not a feature — zero-config minting
is SINGLETON-only by DECLARED shape (`[deployment] shape`, #3714): a team,
production, federated or hive deployment must bring enterprise PKI
(`--tls-cert <fullchain.pem> --tls-key <key.pem>`) and is refused without it
(`transit_encryption::fleet_needs_enterprise_pki_refusal`, naming the
declaration). Nothing observed at runtime promotes a node into that refusal
(#3700 ruling: detection warns, promotion is an operator act); doctor
reports the missing enterprise PKI as Critical with the remedy. Every refusal names only what exists in this release (`--tls-cert/--tls-key`, the `sslmode=verify-full&sslrootcert=<ca.crt>` DSN parameters, the files under `<key_dir>/tls/`); the `ai-memory tls init|import|renew` and `db check-tls` verbs the
refusals name are #3709 items 2–4.
