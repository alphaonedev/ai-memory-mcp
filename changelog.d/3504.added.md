`ai-memory wake-hub` no longer re-parses its identity snapshot on every
identity check, and the refresh that keeps that snapshot alive now ships as a
job instead of as an instruction.

The hub re-checks identity on every hello AND once per second for every
established session, and each of those checks re-opened, re-read and re-parsed
the derived allowlist JSON — hundreds of parses per second at the
256-connection ceiling. It now REUSES the parsed snapshot while the file's
identity (device, inode, mtime, size) is unchanged and the parse is younger
than a new `wake_hub::limits::ALLOWLIST_CACHE_TTL` (2 seconds, thirty times
under the 60-second threshold past which a snapshot is refused outright).

Reuse changed the cost and nothing about the decision, and three properties
still hold on every single check whether the parse is warm or not. The
permission gate runs every time: each check opens the file with `O_NOFOLLOW`
and re-proves through that descriptor that it is a regular file owned by this
uid at exactly mode 0600, so a snapshot whose mode is widened, whose owner
changes, which is replaced by a symlink, or which is removed is refused
immediately. The age gate runs every time: the snapshot's own `refreshed_at` is
re-tested against the clock on a reused parse exactly as on a fresh one, so
reuse can never extend a snapshot past the ceiling and a stale file stays
refused. And a replaced snapshot is honoured on the very next check, so a
refresh or a revocation still lands within the same one-second session
revalidation it always did. The permissions that are checked, the identity that
reuse is keyed on, and the bytes that are parsed all come from ONE descriptor,
so there is no `stat`-then-open window for a swap to slip through.

The refresher ships as `packaging/systemd/ai-memory-wake-hub-refresh.service`
plus its companion `.timer` on Linux and
`scripts/templates/dev.alphaone.ai-memory.wake-hub-refresh.plist` on macOS.
Both run the existing `ai-memory identity hub-cache` exporter every 30 seconds
— half the hub's refusal threshold, jittered so a restarted fleet does not
derive in lockstep, with no catch-up for a missed window because a snapshot
derived for a past instant is already expired. They publish to the path the
#3471 hub units read (`/run/ai-memory/hub-allow.json` on Linux, which is the
`$ALLOWLIST` that unit passes to `--allowlist`, and `~/.ai-memory/hub-allow.json`
on macOS), so installing both templates gives a hub whose allowlist is actually
being written. `/run` is a tmpfs, so the snapshot does not survive a reboot and
the hub admits nobody until the first post-boot refresh — which is what
`OnBootSec=15s` and `RunAtLoad` are for. They are deliberately SEPARATE
units from the hub itself: the refresher opens the store and the hub never may.
For the same reason `wake-hub` grew no in-process `--refresh-from` loop — that
would put a live store handle and its credentials inside the one process whose
entire security story is that it holds only public material and opens no
database on either backend.

`ai-memory wake-hub --posture` gains the snapshot's age and whether the hub
still accepts it — one line in the human rendering
(`allowlist snapshot: 12 s old (ceiling 60 s)`) and an `allowlist_snapshot`
object carrying `age_secs` / `max_age_secs` / `within_max_age` in the JSON one —
so an operator whose refresher has stopped sees it before the agents notice
they can no longer join. An unreadable snapshot reports no age and
`within_max_age: false`; a snapshot the hub cannot read is not a fresh one.
