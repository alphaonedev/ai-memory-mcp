**`signal_send` now refuses an invalid `to_agent` identically on every funnel and both backends (#4408).** `memory_signal_send`, `POST /api/v1/signals` and both `MemoryStore::signal_send` adapters accepted an empty, blank, oversized, control-character or reserved recipient: it was persisted as a direct signal no agent could ever be, written into the coordination audit identity tuple, and left out of the #1807 storage quota bytes. One shared validator, `validate::validate_signal_recipient`, now applies the agent-registration contract to a present `to_agent` in the MCP handler (and again after a `pre_signal_send` rewrite), the HTTP handler above the backend branch, and the sqlite and postgres adapters, before any sign, quota charge, insert, audit record or fan-out. A refused recipient returns the same typed `InvalidInput` / HTTP 400 with a fixed message that never echoes the value; an absent recipient is still a broadcast and a blank one is refused. The recipient is now counted in the storage-only quota bytes.

**Federated signals get the same recipient check on both backends (#4408).** Both `POST /api/v1/sync/push` `signals[]` receive loops (sqlite and postgres) now validate a present `to_agent` per signal before any quota charge, insert or audit record. An invalid recipient is a per-signal skip (counted in `skipped`, the rest of the batch still applies) with the fixed, value-free log line `federation signal skipped: invalid recipient`; previously sqlite stored the bad row while postgres skipped it only indirectly, after charging quota and logging an "invalid signature". Behaviour notes: a blank recipient is refused (it was a dead letter, never a broadcast), and reserved ids such as `daemon` can no longer receive direct signals, matching the registration contract.
