The SQLite deep FTS integrity check compares postings with the external `memories` table again (`integrity-check` with `rank = 1`), re-landing the lost #4036 fix. A live memory missing from the index, a ghost posting for a deleted row, or stale equal-count postings now turn the background worker's cached verdict `failed`, so `/api/v1/health` answers 503 and `/api/v1/monitoring/status` answers 503 with the `index_failed` reason, instead of reporting "ok". The `ai-memory doctor` verb opens the database read-only, so it does not run this check: its `fts_index_integrity` fact reports `not_observed` and claims no verdict; use the health or monitoring surface to see the drift. The liveness-probe documentation no longer claims the reachability probe detects a dropped sync trigger.
