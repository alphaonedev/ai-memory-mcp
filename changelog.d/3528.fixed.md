**The #3401 v98 inbox-alias migration case no longer rewinds the SHARED live
postgres schema stamp (#3528).**

`src/**/*.rs` compiles into ONE `cargo test --lib` binary and every postgres
test in it reaches the SAME database through `AI_MEMORY_TEST_POSTGRES_URL`.
`src/store/postgres_inbox_tests.rs` rewound that database's `schema_version`
to 97 with two autocommit statements. Between them the shared, POPULATED
database carries no stamp row at all: the #2564 guard reads that as version 0,
sees durable rows plus structure no version-0 database ever had, and correctly
REFUSES every concurrent `PostgresStore::connect` with `SchemaStampInvalid`.
That is how `store::postgres::tests::live_get_taxonomy_assembles_hierarchical_tree`
failed a `--test-threads=8` gate run while doing nothing wrong itself; while
the stamp then sat at 97, every concurrent `connect` also raced the v98 ladder
over the same shared schema.

Serialising the writer would not have fixed it — the victims are ordinary
`connect` calls that take no lock, the same reader-victim shape as #3475 /
#3517. The case now creates and drops its OWN database (`ScratchDb`, mirroring
`tests/postgres_schema_downgrade_guard_2445.rs` /
`tests/postgres_ladder_replay.rs`), which removes both the unstamped window
and the shared schema by construction; the shared URL is used only as the
admin connection that creates it, and its stamp is never touched. The rewind
itself is additionally wrapped in ONE transaction as defence in depth.

`tests/pg_shared_schema_stamp_guard_3528.rs` ratchets the class: a `src/**`
file that reaches the shared URL may not execute an INLINE stamp-MUTATING
`sqlx` statement unless it also creates its own database. Scoped so it is
usable — the dozens of `rusqlite` rewinds on private temp files are not
flagged, the production named-`const` ladder writer is not flagged, and stamp
READS are not flagged. Six detector self-tests pin both directions; measured
RED (2 findings) against the pre-fix file and GREEN against the corrected
tree.

Test-only. No schema change, no `set_var`, no production behaviour change.
