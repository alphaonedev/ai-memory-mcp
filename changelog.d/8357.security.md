**mTLS client certificate bound to agent identity (#8357, umbrella #8493).** A new operator map, `AI_MEMORY_MTLS_AGENT_BINDING_MAP` (one `<sha256-hex> <agent-id>` per line, the same file format as `AI_MEMORY_FED_CERT_PEER_BINDING_MAP`), binds each pinned client-certificate fingerprint to one agent id. The posture knob `AI_MEMORY_MTLS_AGENT_BINDING=off|warn|enforce` defaults to `enforce` when the map is set and to `off` when it is not, so a deployment with no map boots unchanged. Under `enforce` a request whose `X-Agent-Id` differs from the certificate's agent is refused `403 agent_id_certificate_mismatch`; under `warn` it is served as the certificate's agent. Under `enforce` the certificate also wins over an enrolled per-agent api key for a different agent (refused `403 agent_id_certificate_mismatch`, header present or not), and an allowlisted certificate that is not in the map cannot claim an agent id the map binds (refused the same way on every route; an unbound claimed id is kept). An explicit `warn` or `enforce` with no map refuses boot. Every mismatch writes a forensic audit row (kind `mtls_agent_binding`). On `/api/v1/sync/*` the mTLS api-key bypass stays, but with a map the peer certificate must map to an agent (`403 agent_id_certificate_unmapped` otherwise) and that agent is the caller id. A matching request resolves with the new authority binding `client_cert`. Boot is refused for an empty, duplicate, malformed or reserved-id map entry, for a mapped fingerprint that is not on `--mtls-allowlist`, and for a map without `--mtls-allowlist`. `ai-memory serve --check` prints the parsed map as JSON without starting the daemon. mTLS with no map logs the boot warning "mTLS on, no agent binding map" and writes an audit row.
