**[release][supply-chain] The strict feature assert's inputs are bound to the verified commit by content, in a sanitized shell (#4768, umbrella #6062).**
The release build and the strict `ai-memory features` assert read the
feature declaration (`scripts/release-features.sh`) and run the asserter
(`scripts/assert-compiled-features.sh`). An earlier step or a third-party
action in the same job could rewrite both consistently, so the assert passed
on a binary missing the advertised features. A working-tree compare
(`git diff HEAD`) does not close this: index flags, an in-job commit, a
redirected repository, a `git` shim on `PATH` or a shell startup file in the
job environment all hide the rewrite. Now the build, assert and two-build
proof steps run under an absolute `bash` in POSIX mode that reads no
startup file, and before reading either file they compare its blob hash
(`/usr/bin/git hash-object --no-filters`, in an `env -i` shell with a fixed
`PATH`) with the blob the verified preflight commit records, and `HEAD` with
that commit; any difference stops the job (#6275). The asserter runs in the same
sanitized shell. The Dockerfile build RUN checks both files against SHA-256
digests the guard pins and recomputes from the tree (#6277). The guard refuses any
other form of these steps. Chosen by `5-agent vote (4d3ea1c5)` (option C,
5-0). Regression: the `4768 ...` and `6275 ...` guard self-test cases and the
runtime tamper probes (plain rewrite, assume-unchanged, skip-worktree, in-job
commit, `PATH` shim, startup file, exported function, repository redirection).
