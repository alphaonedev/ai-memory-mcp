**An admin api-key enrolment whose TARGET is not a registered agent is now
refused** (#3474 advisory 1). `POST /api/v1/agents/{id}/api-key` answers
`404 {"error":"agent_not_registered"}` and binds nothing when the id is absent
from the `_agents` roster. A key bound to an id nothing registered is a
credential for a principal that does not exist: under `enforce` the presented
key binds an `X-Agent-Id` to that id while `is_registered_agent` — the SAME
predicate the governance `registered` level, every pending-action approver
gate, and `bind_agent_pubkey` consult — says there is no such agent, so two
identity subsystems disagree about who exists and a typo'd `{id}` is how it
arrives. The check runs once, ahead of the approve dispatch, so it covers the
direct bind, the row this route QUEUES for an approver, and the APPLY of an
approved row (re-checked against the roster as it stands at apply time, the
#3529 discipline). It sits after the rate limiter, so the existence signal
shares the mint's 10/60 s budget; it is reachable only after `require_admin`
admits a caller who can already read the whole roster, so it adds no oracle.
Registering the target is one further call by the same principal
(`POST /api/v1/agents`). REVOKE is deliberately NOT gated this way — refusing a
revocation is worse than performing one, and revoking a key bound to an
unregistered id is exactly the cleanup a pre-existing binding needs.
`ai-memory agents bind-api-key` is also not gated this way, on the same
reasoning that already governs the supplied-token minimum: it is a shell on the
data tier, not a fleet-reachable route, and it stays the bootstrap and recovery
path.

**A per-agent api-key digest already bound to another agent is now refused
instead of silently re-pointed** (#3474 advisory 3). `agent_api_keys` is keyed
by `sha256(token)`, and both adapters bound with an upsert that overwrote the
row's `agent_id` — sqlite `INSERT OR REPLACE`, postgres
`ON CONFLICT … DO UPDATE SET agent_id = EXCLUDED.agent_id`. Re-binding a token
that already belonged to another principal MOVED the binding: one live bearer
credential stopped authenticating as A and started authenticating as B, with no
signal to either, no second principal consulted, and nothing on the signed
chain recording that a binding had moved — while the enrolment it replaced was
silently deleted. The seam now returns a typed `BindApiKeyOutcome`, the route
answers `409 {"error":"api_key_already_bound"}` with nothing changed, and the
CLI twin (both the sqlite arm and the `--store-url` SAL arm) exits non-zero
with the same disposition. Re-asserting the SAME `(agent, digest)` pair stays
an idempotent success and is a true no-op, so the recorded `bound_at` no longer
moves on a retried enrolment. The refusal names no incumbent: the caller
supplied a token, and a refusal must not tell them which other principal it
speaks for. Both backends do the read and the write in ONE transaction —
sqlite `BEGIN IMMEDIATE`, postgres one transaction under the same registry
advisory lock the #3529 last-key revoke takes, so a bind and a last-key revoke
cannot interleave.
