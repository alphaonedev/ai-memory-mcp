**A short-lived command no longer loses its forensic audit row at exit (#4319).** Forensic rows were handed to a background writer thread (#1472) and nothing drained it before a process exited, so a CLI command or per-call hook verb could exit with its row still queued: the chain did not fork, but signed decision evidence went silently missing (41 contended runs left 38 rows). Every process now writes each forensic row before recording returns, except the two long-running request servers (`serve`, `mcp`), which keep the background writer so per-request file I/O stays off the request path. That includes the other long-lived commands (`curator --daemon`, `sync-daemon`, `watch --daemon`, `wake-hub`, `wake-listen`), which now write each row inline: a small per-row latency traded for never holding a row in memory. `serve` and `mcp` drain the background writer at exit, bounded by 5 s; a drain that times out is counted in `ai_memory_forensic_sink_unavailable_total` and reported on stderr. `serve` drains on a normal exit and on SIGINT (Ctrl-C). `mcp` drains only on a normal exit (its input closed): it handles neither SIGINT nor SIGTERM, so Ctrl-C kills it and any row still queued is lost. Neither server drains when stopped by SIGTERM, the default stop signal of systemd, Docker and `kill`: rows still queued at that moment are lost. That is tracked in #4072 (`serve`, SIGTERM) and #4347 (`mcp`, SIGINT and SIGTERM). Several processes writing the same forensic log keep one chain since #4304.
