**#4371 — `memories.version` counters a peer pinned near `i64::MAX` before the #4218 bound are repaired and editable again.**
A legacy row pinned at or near `i64::MAX` behaved differently per backend after #4218: on sqlite the saturating `+ 1`
left the counter where it was, so the row's `If-Match` token was frozen and stopped fencing a lost update (a REAL-typed
overflow value even read back as version 1); on postgres every edit was refused (the row was un-editable). Schema v101
clamps every `memories.version` and `archived_memories.version` above 2^40 (`MAX_REPLICATED_VERSION`) back to 2^40 on both
backends, once, inside the migration transaction behind the pre-migration snapshot; only the counter is written (text,
`updated_at` and all other columns are untouched, so no row looks newer to a peer, and a restore can no longer carry a poisoned
counter back to a live row). A local sqlite edit at the `i64::MAX` ceiling is now refused with a typed `version counter
exhausted` error, matching postgres, instead of succeeding with a frozen token. The sibling postgres `access_count`
counter (a peer can replicate any non-negative value, and the recall touch / access fold did `access_count + 1`) is
clamped before the add so a row pinned at `i64::MAX` no longer fails every recall touch.
