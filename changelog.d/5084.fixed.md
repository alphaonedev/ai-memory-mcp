**SQLite read-then-write transactions now open `BEGIN IMMEDIATE` (#5084, the #2250 class).** Fourteen production writers opened a DEFERRED transaction, read, then wrote; under concurrent writers the lock upgrade fails at once with `SQLITE_BUSY_SNAPSHOT`, which `busy_timeout` does not retry, so a write that should wait for the lock instead failed. Converted to `WriteTxn::begin` (BEGIN IMMEDIATE with rollback on drop): `create_guarded`, `materialize_template_for_caller`, `mine` (both transactions), `generate_in_scope`, `stamp_contaminated_descendants_as`, `set_embeddings_batch`, `set_embeddings_batch_reembed`, `rekey_peer`, `reclassify_memory_kind`, and the write-first `sweep_expired_leases_reclaim`, checkpoint `resolve`, `run_repair_schema_version` and `sweep_pending_action_timeouts`. `WriteTxn::begin_deferred` and `SQL_BEGIN_DEFERRED` are removed so the helper can no longer open a deferred write transaction. The two read-only snapshots (`policy_version::with_read_snapshot` and the `keys prune` preview) stay DEFERRED and are allowlisted with a reason. New closed-world gate `scripts/check-sqlite-write-txn-immediate.py` (with `--self-test`) fails on any other non-IMMEDIATE transaction open in `src/`, run by `tests/sqlite_write_txn_immediate_gate_5084.rs`. Regression tests fire a second writer inside each function's read-then-write window and fail on the old DEFERRED code with `SQLITE_BUSY_SNAPSHOT`.
