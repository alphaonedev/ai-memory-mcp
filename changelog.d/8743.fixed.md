**Federation catch-up never loses or stalls on a peer-controlled timestamp or a refused row (#8743, #8788, #8789).** The receiver's pull cursor (`sync_state.last_seen_at`) was taken from values the peer controls: a row whose `updated_at` lay far in the future, or a `next_since` inside the skew window, moved the cursor past rows the peer had not yet delivered, and every later write on that peer was never pulled, with no error. One delivered row that the receiver permanently refused (namespace scope, attestation) halted catch-up for good, and a row that failed `validate_memory` was dropped with no log line while the cursor moved past it. Both catch-up loops (the `serve` catch-up and the sync daemon's `sync_cycle_once`) on SQLite and PostgreSQL now derive the cursor only from rows this node settled and cap it at this node's clock. A row beyond the skew bound is deferred (`deferred_future_skew`, WARN) and holds the cursor. A full page never advances to its newest timestamp, so a tie group across a page boundary is not skipped. Every refused row is logged, counted in the new `ai_memory_federation_pull_rows_refused_total{reason}` metric and listed in the window outcome, and the cursor passes it so the rows after it still arrive. A row that keeps failing for a transient reason is refused as `hold_stalled` (ERROR) only after 10 windows in which other rows applied, so a database outage never turns into row loss. A pull that leaves eligible rows behind no longer logs ok. The sync daemon's push half no longer seeds a new peer's pull cursor at the current time.
