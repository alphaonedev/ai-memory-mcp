Stop the `signed_events` ledger from being silently unsigned. When no signing
key matches the resolved agent id the daemon audit key was never installed and
every ledger row was tagged `unsigned` behind a debug-level log, while `doctor`
reported `signing: ready` (it only stat-ed the `daemon` keypair, not the
resolved identity) and both `verify-signed-events-chain` and
`verify-audit-trail` printed OK and exited 0. The append funnel on both
backends now refuses an unsigned row when `AI_MEMORY_REQUIRE_SIGNED_AUDIT` is
set, `doctor` and the daemon boot report the real audit-signing posture for the
resolved agent id, and both verifiers qualify a hash-clean-but-unattested chain
as UNSIGNED instead of reporting a bare OK.
Under `AI_MEMORY_REQUIRE_SIGNED_AUDIT` the posture is additionally enforced at
process START: any ledger-writing command (every write-class verb plus `serve`,
`mcp` and `curator`) refuses to run when no signing key for the resolved agent
id is loadable. The append-funnel refusal alone was not sufficient, because the
producers that treat the audit append as best-effort would swallow it — the user
write would commit with the audit row simply ABSENT, which is worse than the
`unsigned` row it replaced. Read-only and remediation verbs (`doctor`,
`identity generate`, the `verify-*` family, `stats`, `recall`) stay reachable so
the posture can be diagnosed and fixed.
