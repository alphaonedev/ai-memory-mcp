### Security

- **[identity] a registry refresh can no longer re-arm a revoked per-agent api-key**
  ([#4066](https://github.com/alphaonedev/ai-memory-mcp/issues/4066)). The live
  enrolled-key registry was published by whole-map replacement with nothing ordering a
  load's store READ against its PUBLICATION, so a refresh that read the key set before an
  admin revoke could install it after the revoke had narrowed the map — restoring a
  credential the revoke response had just called `"effective": "immediately"`. The
  handler's own clone → modify → install transform was likewise a non-atomic
  read-modify-write. Every registry mutation is now an atomic transform that bumps a
  mutation epoch under the same lock that publishes the map; every load takes a ticket
  BEFORE its read starts (`identity_binding::refresh_agent_keys`, structurally — the read
  is a closure invoked after the ticket exists) and is discarded as `Superseded` if a
  mutation overtook it. A bind's optimistic insert applies only when no mutation landed
  since its pre-write ticket; otherwise the authoritative re-read decides. The background
  refresh loop (both backends) and the admin mint/revoke/approval paths all publish through
  the one ordered funnel. Degrade, never resurrect: a discarded load keeps the mutation's
  map and the next refresh reads again. Pinned on sqlite and postgres by
  `tests/agent_key_stale_refresh_4066.rs` (barriered real refresh vs. the production
  self-revoke route, plus concurrent-transform and superseded-load pins).
