**PgBouncer: `session` mode is the only supported pool mode (#4667).** The
enterprise guide (section 5.6), `infra/pgbouncer` and the ROADMAP prescribed
`pool_mode = transaction`, which the Postgres adapter is not safe behind: the
migration advisory lock, the connect-time `search_path` and the connect-time
`statement_timeout` / `lock_timeout` live on the server session. The executed
probe `scripts/probe-pgbouncer-pool-mode.py` exits 1 on `transaction` and
`statement` pooling (a second client was granted the migration lock and saw the
first client's `search_path` and timeout) and 0 on `session`; an unmodified
daemon was also run end to end through a session-mode pooler. The guide now
states session mode (or no pooler), the sizing rule
`sum(AI_MEMORY_PG_POOL_MAX) <= max_connections - superuser_reserved_connections`
with the T4/T5 numbers recalculated, and guidance for deployments that already
ran transaction mode. `infra/pgbouncer` ships `pool_mode = session`, and
`scripts/check-pgbouncer-pool-mode-claims.py` (CI job `PgBouncer pool-mode claim
gate (#4667)`, not yet a required context) pins the documented mode to the
template. Making the adapter safe under transaction pooling is tracked in #4679.
