**PgBouncer: `session` mode is the only supported pool mode (#4667).** The
enterprise guide (section 5.6), `infra/pgbouncer` and the ROADMAP prescribed
`pool_mode = transaction`, which the Postgres adapter is not safe behind: the
migration advisory lock, the connect-time `search_path` and the connect-time
`statement_timeout` / `lock_timeout` live on the server session. The executed
probe `scripts/probe-pgbouncer-pool-mode.py` exits 1 on `transaction` and
`statement` pooling (a second client was granted the migration lock, saw the
first client's `search_path` and timeout, and a reused backend kept its temporary
table and prepared statement), exits 0 on `session`, and exits 2 when a client
never got a server connection. The guide states session mode (or no pooler), the
sizing rule `sum(AI_MEMORY_PG_POOL_MAX) (+ reserve_pool_size per PgBouncer pool)
<= max_connections - superuser_reserved_connections` with the T4/T5 numbers
recalculated, and guidance for deployments that already ran transaction mode.
`infra/pgbouncer` ships `pool_mode = session`, SCRAM, `server_reset_query =
DISCARD ALL`, verified TLS (`verify-full`) on both hops, separate admin and stats
roles, a loopback-only published port and no fixed password, and its smoke test
is now `smoke-test.py` (it reads `SHOW CONFIG`, uses a published image tag, and
passes secrets by environment only). `scripts/check-pgbouncer-pool-mode-claims.py`
(CI job `PgBouncer pool-mode claim gate (#4667)`, not yet a required context)
scans every tracked text file: each line that mentions a pooler mode must state
session mode or be on `scripts/qc-allowlists/pgbouncer-pool-mode-allow.txt`.
Making the adapter safe under transaction pooling is tracked in #4679.
