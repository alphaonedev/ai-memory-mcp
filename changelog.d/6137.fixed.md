**Cert-expiry gate judges the pull_request merge commit; ported to Python (#6137, #6138).**
`scripts/check-cert-expiry.sh` evaluated rule (C) at the PR head and took the
range base from the event payload, so a branch cut before the #6121 banner fix
failed although the merged tree records `EXPIRED`, and a stale payload base sha
skewed the range. The gate is now `scripts/check_cert_expiry.py` (Python 3.9+,
stdlib only, per the Python-not-shell rule; the bash gate is removed; the
workflow runs it with `python3 -I`). On `pull_request` it judges (B) and (C) at
the checked-out merge commit (`GITHUB_SHA`, falling back to `HEAD`) and computes
no merge-base: (A) drift and the (B) banner flip are measured from the merge
commit's first parent to the merge commit, so base-side changes since the fork
point are not re-counted against a stale branch. It fails closed when the base
ref, the head or the merge commit cannot be resolved, a sha taken from the
environment is not exactly 40 or 64 hex characters, the merge commit does not have exactly
two parents, its second parent is not the PR head, or its first parent is not on
the live base branch (`origin/$GITHUB_BASE_REF`, fetched explicitly if absent);
the first parent need not be the base tip, so a landing on the base after the
merge ref was built stays green. The remedy printed on a red is to push a new
commit or sync the branch with the base (a re-run reuses the same `GITHUB_SHA`).
Inside GitHub Actions the event payload range is authoritative and
`CERT_EXPIRY_BASE` / `CERT_EXPIRY_HEAD` overrides are refused (#5970; outside CI
they are honoured for local use). Every earlier rule, message and self-test cell
is preserved; the self-test adds the stale-branch, banner-flip, stale-payload-base,
merge-structure and CI-override cells. Refs #6121, #3556, #5970.
