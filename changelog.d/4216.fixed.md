**#4216 — a federation merge that changes a row's data now moves its `version`.**
The four apply funnels (sqlite `insert_if_newer` / `merge_inbound`, postgres
`apply_remote_memory` / `merge_inbound`) kept `version = MAX(local, remote)`
while they replaced content, so a client holding the pre-merge version still
passed `If-Match` (and the #4045 consolidation CAS) and silently overwrote the
merged edit. A merge that changes user data now lands on
`GREATEST(local, remote) + 1`; a replay, or a losing push that changes nothing,
does not bump, and a losing push that raises `priority` / `confidence` / `tier`
does. ONE shared predicate (`models::replicated_version::user_data_changed`)
decides: plaintext content, title, namespace, tags, metadata, tier, priority,
confidence, lifecycle, valid_from/until, kind, source and citations; it
EXCLUDES `access_count`, `last_accessed_at`, `expires_at` and, inside metadata,
the node-local keys, `crdt_field_clocks` and `version_vector`. The version
stays a NODE-LOCAL token (documented in `docs/API_REFERENCE.md`). 5-agent vote
4d3ea1c5, memory ea23f404.
