### Security

- **[supply-chain][release] `release.yml` ships only a verified, CI-qualified,
  immutable tree** ([#3546](https://github.com/alphaonedev/ai-memory-mcp/issues/3546)).
  The release preflight used to check the tag name against a SemVer regex and
  resolve it to a commit, and nothing more, even though the job was named
  "tag exists + is annotated". All eight later checkouts used the tag NAME.
  So a lightweight tag, an unsigned tag, or a tag moved between jobs could
  all ship, and no job asked whether CI had passed on the commit being
  released. Changes:
  - **Tag verification.** Preflight now refuses a tag unless all of these
    hold: it is annotated; its object headers name the requested tag and
    the peeled commit; it is SSH-signed by a key in the new
    `scripts/qc-allowlists/release-tag-signers.txt` (operator key only,
    asserted to be a subset of the commit-signer registry); its commit is
    on the release branch the workflow was dispatched from; and an active
    `refs/tags/v*` ruleset forbids update and deletion. The verifier and
    allowlist are read from the workflow's own commit, never from the tree
    the tag points at, so a tag cannot bring its own verifier.
  - **Qualify job.** A new `qualify` job needs every context declared in
    `required-contexts-release.txt` to have a successful check-run on that
    exact commit. Skipped, missing, in-progress and failed-latest-attempt
    runs all refuse. A check-run counts only if it came from the GitHub
    Actions app, inside one of the gating workflows. Every build and
    publish job needs `qualify` directly, and checks out the verified SHA.
  - **Publish-time re-assert.** Each GitHub-release upload first
    re-confirms that the remote tag is still the tag object preflight
    verified.
  - **Pinned tools.** The nfpm download is checked against a pinned SHA-256
    before extraction (it is no longer piped from `curl` into `tar`), and
    `cbindgen` is pinned to 0.29.4.
  - **Provenance for Homebrew and COPR.** Both jobs now require the release
    job's build provenance (`gh attestation verify`), not only a `.sha256`
    served from the same place as the asset.
  - **Tests.** `scripts/test/test-release-hardening.sh` runs in
    c8-precheck. It drives the verbatim workflow shell blocks over
    throwaway repositories and canned API responses, and it proves the
    frozen pre-fix workflow accepted each case.
  - **Before the first hardened release.** A repository admin applies
    `.github/rulesets/release-tags.json`. Release tags must be SSH-signed
    (v0.7.1 was annotated but unsigned). Dispatch with
    `gh workflow run release.yml --ref release/vX.Y.Z -f tag=vX.Y.Z`.
