**Postgres tool parity (#3064, lane L-PGP).** Two `/api/v1` paths that a
postgres-backed daemon refused with the fail-closed `501 NOT IMPLEMENTED`
envelope now serve real results, with no new schema and no new pg write SQL.

- **`POST /api/v1/find_paths`** (family F1) — `src/lib.rs` wires BOTH this
  bare alias and the already-pg-supported `/api/v1/kg/find_paths` to the SAME
  handler (`handlers::kg_find_paths`, which takes the
  `StorageBackend::Postgres` branch into `MemoryStore::find_paths` and never
  `app.db.lock()`), so the alias was refused only because it was missing from
  `postgres_endpoint_supported`.
- **`POST /api/v1/memory_smart_load`** (family F2) — the family PICK is now
  the shared pure `mcp::pick_family_for_intent` and the family-tagged READ
  rides the SAME `MemoryStore::list` + `Filter::metadata_eq` GIN pushdown the
  already-supported `memory_load_family` route uses, through one extracted
  helper (`handlers::power_consolidation::load_family_rows_via_store`) rather
  than a second copy that could drift on visibility filtering, the
  fail-closed family re-check, or the short-result escalation window. The
  wire envelope is built by the shared `mcp::smart_load_envelope`, so both
  backends emit identical bytes.

- **`POST /api/v1/memory_calibrate_confidence`** (family F3) — new SAL
  `MemoryStore::calibrate_confidence_report`, with the sqlite adapter
  delegating VERBATIM to the existing `calibrate_from_shadow` SSOT and a
  postgres adapter (`src/store/postgres/parity_3064.rs`) porting the same
  two-pass sweep over the pg `confidence_shadow_observations` table, which
  has shipped in the bootstrap schema since v0.7.0 — a port, not a new
  relation, and no schema rung. This route mattered most: the empty scratch
  sqlite ALSO carries that table, so an ungated handler would have returned
  a plausible all-zero calibration rather than failing. The one write in the
  sweep (the `recall_outcome` ledger backfill) is record-stop gated and
  SKIPPED with a WARN when the record plane is stopped — the baselines never
  depend on it, so a skip degrades the optional evidence fields to `null`
  and never yields a wrong number. The port reproduces sqlite's existing
  behaviour verbatim, including its caller-gate posture — the tool's
  caller-gate posture on both backends is tracked in [#3507](https://github.com/alphaonedev/ai-memory-mcp/issues/3507).

- **`POST /api/v1/memory_atomise`** (family F5) — nothing was ported, because
  the HTTP surface never had storage access to port: the atomisation engine
  lives on an `AtomiseToolHandler` the daemon owns only on the MCP dispatch
  path, and this handler's call site has always passed `handler: None`, so
  every HTTP call terminates in the tier-locked advisory envelope BEFORE any
  storage access — identically on both backends. Refusing it with a 501 was
  the LESS truthful answer, since a 501 implies the route works on a sqlite
  daemon. The postgres branch drives the extracted, storage-free
  `mcp::atomise_precheck` with `handler_present = false`, whose type
  signature makes the engine arm unreachable, and that arm fails CLOSED with
  the documented 501 envelope if a future change ever wires a real handler
  onto this surface. The extraction also removes two production-path
  `.expect()` calls (ERRORS-06).
