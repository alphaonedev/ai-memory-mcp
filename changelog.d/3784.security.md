### Security

- **[sdk] the Python SDK refuses an agent private key that is not owner-only**
  ([#3784](https://github.com/alphaonedev/ai-memory-mcp/issues/3784)).
  `AgentSigningKey.from_file` was `cls(Path(path).read_bytes())`: no
  regular-file check, no `mode & 0o077` check, no owner check, no
  `O_NOFOLLOW`. An SDK user whose `<agent_id>.priv` was left world-readable by
  a copy, a backup or a bad umask signed attestations with a key any local uid
  could read, and nothing in the SDK said so — while the daemon's own loader
  (`src/identity/keypair.rs::read_private_key_file`) refused the identical
  file, and so did this SDK's own wake bundle loader (#3780). Two loaders of
  local private keys with two standards is how the weaker one survives, so the
  #3780 descriptor-bound reader moved into one shared module,
  `ai_memory/_ownedfile.py`, and both loaders now import it: open ONCE with
  `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`, `fstat` THAT descriptor, refuse a
  symlink (`ELOOP`/`EMLINK`, reported as a symlink rather than a bare errno),
  a non-regular file, `mode & 0o077` or a foreign owner, and read the bytes
  from the same descriptor. The key loader's refusals raise the new
  `ai_memory.attestation.KeyFileError` (an `AiMemoryError`), name the path,
  the reason and the offending mode — with the `chmod 0600 <path>` that fixes
  it — and never render key material. The wake loader's behaviour, wording and
  exception type are unchanged, pinned by its existing tests. **Platform
  caveat, unchanged:** Windows has neither flag, so that leg keeps the
  historical path-based check-then-read and says so in the code. The
  TypeScript SDK has no path-based key loader (`AgentSigningKey.fromSeed`
  takes bytes), so nothing there to fix.
