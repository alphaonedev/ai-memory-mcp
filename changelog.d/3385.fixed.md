`[storage].archive_on_gc` now GOVERNS garbage collection instead of only
parsing. `AppConfig::effective_archive_on_gc()` — the resolver every GC
consumer calls (`ai-memory gc`, the `gc_if_needed` hot-path sites, MCP
`memory_gc` / `memory_forget`, the serve GC loop, both backends) — read the
DEPRECATED flat `archive_on_gc` key alone, while `resolve_storage()` read the
documented v2 key, so the two silently disagreed in both directions: a
`[storage].archive_on_gc = false` (crypto-erase-on-expiry) was ignored and
expired memories kept a recoverable copy, and — the data-loss direction — a
`[storage].archive_on_gc = true` sitting next to a stale flat
`archive_on_gc = false` let the flat key win, hard-deleting expired memories
with no archive and no rollback against an explicit instruction to keep one.
The resolver is now the single source of truth (`resolve_storage()` delegates
to it) with precedence `[storage].archive_on_gc` > deprecated flat key >
compiled default `true`. Resolving a config whose flat key is in effect, or
whose two keys disagree, emits a one-shot stderr WARN naming the winner — on
stderr, not `tracing`, so it is visible from plain CLI commands. `ai-memory
doctor` reports the effective `archive_on_gc` value and a new
`archive_on_gc_source` fact (`config` / `legacy` / `compiled-default`). The
schema-drift WARN no longer claims legacy fields are "IGNORED" under v2 — they
remain the lowest-precedence fallback for any key the sections leave unset,
which is exactly what made a stale flat key a live hazard.
