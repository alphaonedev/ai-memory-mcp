**Engaged read decisions: the "DLQ-backed" audit claim was false — wording corrected, the evidence gap is now measured, and `AI_MEMORY_READ_AUDIT_STRICT` lets an enterprise deployment refuse instead (#3660, audit #3645 F14).**

`gate_read`'s doc comment, inline comment and WARN line said an audit-append failure was "DLQ-backed" / "the deferred-audit DLQ keeps the trail recoverable". The code did not deliver that: `emit_check_event` is a direct `append_signed_event` in its own IMMEDIATE transaction, and the deferred-audit queue is the write pre-hook's refusal-only mechanism, unreachable from the read gate. A read decision whose append failed was never queued, spooled or retried; its only residence was the best-effort forensic file. The documentation (`docs/security/audit-trail-coverage.md`, CHANGELOG #1730) had always said only "logs a warning and the read proceeds" — the CODE wording was the overclaim, and it is what changed. No spool was invented to satisfy the comment. Instead: `governance::read_audit` counts evaluated decisions, chain appends and gaps by residence (`forensic_queued` when the best-effort forensic sink accepted the row onto its writer queue — an accept, not a confirmed write — and `none` when it is disabled or the send failed; `record_decision_checked` reports which), exported on `/metrics` as `ai_memory_governance_read_audit_*` (closed `residence` label, pre-touched to 0) and on `/health` under `governance.read_audit_delivery` as a #3646 signal object (`actionable = true` once any evidence has been lost). `AI_MEMORY_READ_AUDIT_STRICT=1` (the shared `1`/`true`/`yes`/`on` grammar) refuses a read whose decision cannot be chain-logged; the default stays the documented best-effort posture. Tests force a `signed_events` append failure (ABORT trigger) and verify: best-effort proceeds with the gap counted at residence `none`, strict refuses with the documented reason, a working sink is counted and never refused, and the zero-rule fast path is not counted.
