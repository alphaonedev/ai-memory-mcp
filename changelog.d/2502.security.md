### Security

- **[auth] Per-source auth-failure backoff on the HTTP transport gate**
  ([#2502](https://github.com/alphaonedev/ai-memory-mcp/issues/2502)). Before
  this change the `api_key_auth` middleware recorded nothing: a single source
  could present wrong keys forever at whatever rate the daemon completed
  them. Admission control (`AI_MEMORY_MAX_INFLIGHT_REQUESTS`) bounds how many
  requests run AT ONCE, not how many attempts one source makes over time.
  - **One predicate** (`handlers::auth_backoff::AuthFailurePolicy`): after 5
    failures a source is refused with `429` + `Retry-After` before its key is
    compared (a correct key during backoff is still refused, so the refusal
    is not a key oracle). The backoff doubles per further failure (1s base,
    5min cap); a success resets the source.
  - **Source is the TCP peer IP** (`ConnectInfo`), never a client header, so
    a forged header cannot lock someone else out. Bounded at 1024 sources
    (LRU, oldest evicted), fail-open on counter error, no env knob.
  - **Observability**: `ai_memory_auth_failures_total` (label-free) plus
    `ai_memory_auth_backoff_episodes_total` (episodes begun since boot,
    edge-triggered), and one WARN edge-triggered on crossing
    the threshold rather than per failure.
  - **Proxied deployments**: the source is the TCP peer IP, so put the daemon
    behind nothing that hides the client IP. Behind an L4 proxy (or NAT that
    pools many clients onto one address) every client behind that address
    shares one backoff budget: one misconfigured client retrying a stale key
    can earn `429`s for everyone sharing its egress IP.
