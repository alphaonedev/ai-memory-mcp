**Doctor flags an over-depth governance chain (#4715).** `ai-memory doctor`
now names every explicit `parent_namespace` chain that is longer than the
governance bound (`GOVERNANCE_CHAIN_MAX_DEPTH`, 8 hops) and marks the
section Critical, because #4477 already refuses every governed operation
under such a chain. Pre-#4477 or imported data can still hold one. The census
reuses the `bind_chain_depth` walk from root segments only, on SQLite (the
Governance section) and PostgreSQL (new section "Governance chain depth
(#4715)", connected through the #3705 sslmode floor with the #4333 refusal
shape). The note names the offending namespaces (first 20, plus a count) and
the shortening hint. The doctor also stops swallowing read faults here: the
depth histogram and the governance coverage (#4956) no longer fall back to an
empty value or `0`. A bound standard with invalid metadata JSON, or a missing
`namespace_meta` table, now makes the coverage probe return an error, so the
Governance section is Critical and prints `unreadable` with a
`governance_coverage_error` fact in text and JSON. An unreadable
`namespace_meta` row is a Critical finding.
The census is linear: each namespace's hop count is computed once and
memoised (cycles still terminate, and the result equals the per-root walk on
random graphs), so a 20k-row chain no longer takes seconds-to-minutes or gets
misreported on PostgreSQL as an extension-probe timeout. The section has its
own timeout message. When a read fails, the Governance facts
`namespaces_with_policy`, `namespaces_without_policy` and `inheritance_depth`
print `unreadable` instead of `0` / `empty`. The note says "operations that
resolve these chains are refused". The PG read-fault test cell now derives a
throwaway database from the test URL, fails instead of skipping on an unusable
URL, and drops the database in a guard; its derived name is kept within PostgreSQL's
63-byte identifier limit. The two 20k-row timing bounds are 10 s (still far
from the quadratic walk) so they do not flake under fleet load.
