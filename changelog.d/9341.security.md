### Security

- **[identity][http] Enforce refuses an unproven named principal on every route**
  ([#9341](https://github.com/alphaonedev/ai-memory-mcp/issues/9341),
  [#8502](https://github.com/alphaonedev/ai-memory-mcp/issues/8502),
  [#8590](https://github.com/alphaonedev/ai-memory-mcp/issues/8590),
  [#9342](https://github.com/alphaonedev/ai-memory-mcp/issues/9342)).
  Under `AI_MEMORY_HTTP_REQUIRE_ATTESTED_IDENTITY=enforce` with per-agent keys
  enrolled, a caller holding only the shared API key could name any agent in
  `X-Agent-Id` and write, signal or read as that agent on 15 routes that had
  no per-handler gate. The HTTP authority layer now refuses such a request
  with `403 attested_identity_required` before any handler, on every route
  except the probes and `/api/v1/sync/*`. A client certificate mapped to the
  named agent now counts as proof at the layer and at the handler gates
  (#8590). A present but malformed or non-ASCII `X-Agent-Id`, and an invalid
  caller id reaching a handler, is now a `400 VALIDATION_FAILED`, never the
  silent `anonymous:invalid` principal (#9342). **Operators running `enforce`
  with only the shared key must enrol per-agent keys
  (`ai-memory agents bind-api-key`) or map client certificates
  (`AI_MEMORY_MTLS_AGENT_BINDING_MAP`)**; until they do, named callers are
  refused, whether or not any per-agent key is enrolled and whether or not a
  shared key is configured (3-agent vote (71472661)); the alternative remedy
  is to select `advisory`. Under `advisory` the same request is served and
  reported: one WARN per (presented key, claimed id), the claimed id escaped
  and cut at 128 characters, plus a counter; nothing is persisted and the key
  is never logged. Requests without `X-Agent-Id` and `off` are unchanged.
  Under `enforce`, with any number of per-agent keys enrolled including zero,
  a body `agent_id` on `POST /api/v1/session/start` and
  `POST /api/v1/memory_reflect` is the same claim: absent, the request acts as
  the authority principal; equal to the proven principal, it is accepted;
  otherwise (a shared-key or anonymous caller naming an agent, or a proven
  caller naming another agent) it is refused with the same
  `403 attested_identity_required` before any read, so a shared-key caller can
  no longer receive another agent's private rows from session start (PR 9390).
  Under `advisory` the body claim is served and reported; `off` is unchanged.
  A refused request's audit row names the server-minted or proven principal
  as its actor and records the claimed id separately (`claimed_agent_id`,
  escaped and cut to the identifier length), never as the actor (PR 9390).
- **[authz][http] A row with no owner stamp that the caller cannot read
  answers like an absent id** (PR 9390). `PUT`, `DELETE`, promote, link
  create and delete and the KG timeline checked the unstamped-row posture
  (`AI_MEMORY_UNSTAMPED_MUTATION`, #3124) before visibility, so on SQLite a
  caller could overwrite or delete another tenant's hidden unstamped
  `scope=private` row and on PostgreSQL the refusal named the row (`403`)
  where an absent id answered `404`. Visibility is now decided first; a
  visible unstamped row keeps the #3124 posture unchanged. A store error on
  the update pre-read now answers its own status instead of "not found", and
  `DELETE /api/v1/links` with a hidden source answers like an absent source
  whatever the target.
