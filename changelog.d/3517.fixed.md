### Fixed

- **[test-isolation] Two independent mutexes guarded the same process-global
  caller principal, so lib tests raced on `AI_MEMORY_AGENT_ID`**
  ([#3517](https://github.com/alphaonedev/ai-memory-mcp/issues/3517)).
  Test-only change; no product behaviour is altered.
  `src/**/*.rs` compiles into ONE `cargo test --lib` binary whose `#[test]`
  functions run in parallel threads, and `identity::resolve_read_visibility_caller()`
  reads `AI_MEMORY_AGENT_ID` from the process environment with no injectable
  seam — so an installed principal is visible to every concurrently-running
  reader. The crate-wide `identity::agent_id_env_test_lock()` (#1772) was
  taken by `mcp::tools::*`, `storage`, `cli::recall` and `coordination_guard`,
  but `identity::tests` and `daemon_runtime::tests` each held a *module-local*
  `static LOCK: OnceLock<Mutex<()>>` named `env_var_lock` over the SAME
  variables. Holding either excluded only its own users, so
  `identity::tests::read_visibility_caller_returns_env_when_set` (installing
  `ai:alice`) and `mcp::tools::pending::tests::pending_reject_refuses_unregistered_approver_3388`
  (installing `ai:mallory`) could run at literally the same instant —
  the `agent_id mismatch: caller '…'` / cross-tenant-refusal flake class
  #3517 reports against `mcp::pending` and `coordination_guard`. This is the
  identical per-module-mutex defect `$HOME` suffered three times
  (#1998 → #2115 → #2127) before `config::test_env_lock()` unified it.
  - Both `env_var_lock` wrappers now **delegate** to the one canonical
    `identity::agent_id_env_test_lock()`, so the critical section is genuinely
    process-wide. `daemon_runtime`'s wrapper also covers the caller-affecting
    siblings `AI_MEMORY_ADMIN_AGENT_IDS` and `AI_MEMORY_ANONYMIZE`.
  - The two `identity::tests` functions that previously acquired *both* the
    crate-wide lock and the module-local one now acquire only the delegate:
    `std::sync::Mutex` is not reentrant, so a double acquisition would
    self-deadlock (CONCURRENCY-04). Lock order for the two `daemon_runtime`
    tests that also hold `test_support::env_lock()` is unchanged (that one
    first), and no site takes the pair in the opposite order.
  - Each converted wrapper gains an `env_var_lock_is_the_one_crate_wide_lock_3517`
    unit test that pins the unification by **observed mutual exclusion**, not by
    reading the delegate's source: while the test holds the module wrapper, a
    second thread taking `identity::agent_id_env_test_lock()` must not get
    through. On the pre-fix tree it got through immediately — which is exactly
    how `identity::tests` and `mcp::tools::pending::tests` came to install
    different principals at the same instant.
  - **The other half of the defect: the VICTIMS.** Serializing the mutators does
    not protect a test that merely *resolves* identity and never takes the lock.
    `mcp::pending::tests::subscription_dlq_list_cross_tenant_refused_1118` — the
    test whose triage opened this issue — passes an EXPLICIT caller
    (`Some("ai:bob-client")`), but `handle_subscription_dlq_list` resolves
    through `identity::resolve_agent_id`, which reads `AI_MEMORY_AGENT_ID`
    FIRST; a sibling installing `ai:alice` silently replaced the caller and
    alice's DLQ row became visible (`left: Some(1), right: Some(0)`).
    Reproduced **4 failures in 10 runs** of
    `cargo test --lib -- --test-threads=4 identity:: mcp::pending coordination_guard`
    *after* the mutator unification, and **0 in 10** once the guard below was
    added. Fourteen lib tests that assert an explicit-caller / owner-scoped
    path now hold `identity::agent_id_env_unset_guard()` — the #1874 fixture
    that exists for precisely this — across `mcp::pending` (4), `mcp::list` (3),
    `mcp::search` (4), `mcp::session_start`, `mcp::subscribe` and
    `storage::migrations`.
  - New `tests/agent_id_env_lock_gate_3517.rs` is the structural anti-regression
    gate: it walks `src/**/*.rs` and FAILS any non-comment `set_var(` /
    `remove_var(` line naming `AI_MEMORY_AGENT_ID` / `ENV_AGENT_ID` /
    `AI_MEMORY_ADMIN_AGENT_IDS` whose enclosing `fn` does not cite
    `agent_id_env_test_lock` / `agent_id_env_unset_guard`, directly or through
    a file-local wrapper whose own body cites one (which is what keeps a
    re-privatised mutex a violation). Its self-test drives the detector over
    six synthetic buffers, proving it catches the naked and module-local-mutex
    shapes and spares the canonical, delegated, and commented-out ones
    (M-TAUTOLOGICAL-TESTS). Complements `scripts/check-test-env-lock.sh`
    arm (d), which ratchets the #3475 *census* of installs; this gate polices
    *which lock* serializes them.
