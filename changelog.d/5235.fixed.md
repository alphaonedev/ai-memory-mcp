**The read-only policy snapshot is now read-only at run time, not only by convention (#5235).** `policy_version::with_read_snapshot` opens a plain `BEGIN` read transaction, and the #5084 static gate cannot see a write reached through a helper or a closure called inside it. The closure now runs under `PRAGMA query_only = ON` on both paths (the snapshot's own transaction and a transaction the caller already holds), so any write in it (rows, schema, temp tables, triggers, FTS, `user_version`, `application_id`, a cached statement) fails with `SQLITE_READONLY`, and the error carries the typed marker `ReadSnapshotGuardRefusal::WriteRefused` and the text "read-snapshot guard". The prior `query_only` value is saved and restored, never forced OFF, so a read-only pool connection and an outer scope keep ON. Setup fails closed before the closure runs. The value is restored on Ok, Err and panic; on the autocommit path the snapshot transaction ends before the restore. A failed restore is an error on Ok and an ERROR log from `Drop` otherwise, and the connection is left read-only. After the closure, a scope check refuses a closure that turned the pragma OFF or moved the change counter, a schema cookie, `user_version` or `application_id`, and on the autocommit path rolls it back. The static gate gains rule R7: source may only read `query_only` or set it ON, except the one restore function. Decision: 5-agent vote (4d3ea1c5). Known limits, each filed: on a caller-held transaction an OFF-write-ON closure is refused but its write stays in the caller's transaction (#5881); `storage::touch_many` skips its write with `Ok(0)` under `query_only` instead of refusing, and its pragma read fails open (#5882); `ATTACH` and `SAVEPOINT` are not writes to SQLite and are not refused by the pragma (`ATTACH` fails inside the snapshot transaction anyway, and a write after a `SAVEPOINT` is refused).
