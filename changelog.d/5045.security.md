### Security

- **[control-integrity] commit-signing posture gate: OpenPGP keyring + `%GF` key pin, the
  documented web-flow merge carve-out, and a non-vacuity floor**
  ([#5045](https://github.com/alphaonedev/ai-memory-mcp/issues/5045),
  [#5046](https://github.com/alphaonedev/ai-memory-mcp/issues/5046),
  [#5047](https://github.com/alphaonedev/ai-memory-mcp/issues/5047)).
  `scripts/check-commit-signing-posture.sh` (the #2486 gate) refused 75 of the 487 commits in
  a real release-branch PR range, and separately reported PASS on an empty range. Three
  defects, one file, repaired together per the crossroads verdict
  `5-agent vote (4d3ea1c5)` (ai-memory `86c7ae16-2591-461c-a797-dfd779f05edf`).
  - **#5045 — 67 legitimately-signed commits refused (`%G?=E`).** git dispatches signature
    verification on the signature type carried *in the commit object*, and `gpg.format` does
    not override that dispatch, so an OpenPGP-signed commit is verified against the OpenPGP
    keyring and never against the SSH `allowed_signers` registry. On a stock CI runner that
    keyring is empty, so every OpenPGP-signed commit reported `E` (signature present,
    unverifiable) and was refused. The gate now builds a **hermetic, job-scoped `GNUPGHOME`**
    inside the run — never the ambient runner keyring, never a live GitHub API call — from a
    second hand-enrolled registry, `scripts/qc-allowlists/enrolled-gpg-commit-signers.txt`
    plus its `.asc` public-key material, and grants ultimate ownertrust to *exactly* the
    pinned fingerprints (a bare import yields `%G?=U`, not `G`).
  - **The accept test is now `%G? == G` AND `%GF` ∈ the pinned fingerprint set**, where the
    pinned set is the union of the SSH halves' `SHA256:` fingerprints (derived from the
    existing registry with `ssh-keygen -lf`, never hand-copied) and the OpenPGP registry's
    40-hex fingerprints. Importing a key without pinning it would have been a gate that
    reports success while proving nothing: *any* trusted key in the keyring also yields `G`,
    so trust would silently have become "whatever is in the runner keyring" (the #2444
    class). `%GF` is only ever populated for a signature that actually verified. `%GK` is
    deliberately **never** pinned — it is read from the *unverified* signature packet, is
    populated even against an empty keyring and on commits whose `%GF` is empty, so a `%GK`
    pin is forgeable.
  - **#5046 — 8 web-flow merge commits refused for `unbound-committer-email`.** The gate's
    own header has always scoped the rule to the PR's source commits and never to a GitHub
    web-flow merge artifact, but that carve-out was *documented only* and never implemented;
    unimplemented documented behaviour is docs-drift, a real defect here. The range is now
    `merge-base(base,HEAD)..HEAD`, matching the shape already used by
    `check-cert-expiry.sh`, `check-shared-namespace-claims.sh` and
    `check-count-assertion-declared.sh`. All 8 of 8 refused commits are two-parent web-flow
    merges, and they are cleared **without** pinning GitHub's web-flow key: pinning a
    third-party key would extend this repo's sole-authority trust boundary to a key whose
    continued ownership no self-test can ever prove. This entry first shipped that carve-out
    as a blanket `--no-merges` on the scan, which exempted every merge — including 93 local
    two-parent merges — from both halves of the rule. **#5065, in this same branch and before
    either change lands, replaces it with the three-term exemption predicate** described in
    its own entry; read the two together, since the `--no-merges` form described here is not
    what ships. An "exclude commits already reachable
    from the protected branch" predicate was measured instead of assumed
    (`git rev-list --left-right --count` = `0 487` — it excludes *zero* commits) and
    rejected: a no-op predicate in a gate with no non-vacuity floor is how #2444 gates are
    born.
  - **#5047 — an empty range reported PASS.** Zero commits scanned is now a FAIL (exit 2)
    with a diagnostic naming the resolved base and head SHAs and whether each ref resolved,
    matching the floors already in `check-sdk-tls-scheme.sh` and `check-docs-vs-ssot.sh`. The
    exit contract is tightened and documented throughout: `0` clean, `1` a commit violated
    the rule, `2` the gate could not do its job and refuses to report PASS (usage, registry
    loss, unresolvable range, keyring-setup failure, zero commits scanned, or `PR_BASE_SHA`
    unset on a `pull_request` event — that last one previously reported `1`, misattributing a
    CI-wiring fault to the PR author as a commit violation). The gate's ENTRY POINT had no
    self-test coverage at all before this change; case (l) adds it, following the sibling
    precedent in `check-cert-expiry.sh` case (k).
  - **Self-tests: 7 shapes → 15** (→ 27 once #5065 adds the merge-evaluation cases), each
    printing its observed and expected exit code so the
    evidence is readable straight out of the CI log. New: a pinned-OpenPGP commit passing
    alongside an SSH-signed commit in one range; both failure modes of the new registry
    (missing, zero well-formed fingerprints) failing closed; an empty range failing closed;
    and a hermetic keyring built from the *shipped* registry + `.asc` so a drift between
    those two files fails the gate rather than passing silently. The load-bearing case is a
    **second ephemeral OpenPGP key in the same keyring, unpinned**: it verifies fully
    (`%G? = G`) and must still be refused as `signing-key-not-pinned`. It is the only case
    that fails if a future edit drops the `%GF` branch while keeping the keyring import —
    verified by mutation: deleting that branch turns it red and leaves the clean cases green.
  - **Measured, same two SHAs, before and after.** Under an empty keyring (the stock-runner
    condition; the host keyring masks the defect): before — exit 1, 83 violation lines across
    75 distinct commits (75 `signature-not-verified` = 67 non-merge + 8 merge, plus 8
    `unbound-committer-email`); after — exit 0 with **386 non-merge commits scanned** and
    zero refusals. The scanned count is reported on the OK line so a future vacuous pass is
    visible rather than silent. With #5065's predicate on top, the same two SHAs report
    **479 commits scanned, 93 merges evaluated, 8 merges exempted** and still zero
    refusals — the narrowed carve-out covers 93 more commits than the form described
    above (479 against 386), at zero false refusals.
  - **Scope, stated plainly.** This gate remains a declared-but-not-required status check and
    this change does not promote it (that is the operator-sequenced #3554 lockstep;
    `scripts/qc-allowlists/required-contexts-not-required.txt` is untouched). The OpenPGP
    fingerprint enrollment is an out-of-band **operator-custody** record presented for
    ratification as a reviewed diff — it does not independently prove which GitHub account
    holds that key, and the gate does not reproduce GitHub's own "Verified" badge. The
    host-`git config` half of the same defect class is still open as #5048 and is deliberately
    not touched here: one shared `.git/config` is read by ~200 concurrent worktrees.
  - The now-false sentence in `scripts/qc-allowlists/enrolled-commit-signers.txt` — that the
    registry format and the verification format "can never drift apart" with "no custom
    parser needed on either side" — is corrected in the same commit: with a second mechanism
    pinned that claim became false attested text. The header now enumerates all three
    consumers of signer data and names the self-test case that closes the drift it admits.
