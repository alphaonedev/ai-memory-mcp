**A crash after a failed audit write can no longer hide the loss (#4298).** When an audit append failed part-way, #4211 truncated the partial record before the #4086 sequence high-water recorded the lost number. A crash in between (a kill, an OOM, a power loss) left a trail ending at the previous event and a mark that did not cover the lost number, so `audit verify` read clean and a restart reused the number. The partial line that same crash used to leave had at least failed verify. The lost number is now written to the high-water and synced BEFORE any bytes are removed, and the bytes are never removed if that write fails: they stay on disk, reported as a `TornRecord`. At every crash point on this path the disk now either fails `verify` (and a restart refuses the torn tail) or reports the lost event as a gap. Found by the independent retest of #4191/#4211.
