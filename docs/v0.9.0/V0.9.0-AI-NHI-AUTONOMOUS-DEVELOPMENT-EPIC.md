**Write path — in-place by default.** Bulk/store write is an upsert: postgres `store_with_embedding` uses `ON CONFLICT (title,namespace) DO UPDATE` (`postgres.rs:11382`); sqlite goes through `ConflictMode` (`storage/mod.rs:973`) whose default arms (`Merge`) mutate in place. `ConflictMode::Version` (keeps both rows) exists but is not the default. `update`/`update_with_expected_version` (`storage/mod.rs:1731`) mutate in place. The default human/agent edit is the G6 write-side break.

**Partial supersede (exists but not append-only).** `update_with_archive_on_supersede` **archives the old row OUT** of `memories` into `archived_memories` (`archive_reason='superseded'`) and mints a new row; the supersede link is only a `metadata.superseded_id` pointer, **not** a `memory_links` RELATE row (the FK CHECK on `target_id REFERENCES memories(id)` would fail once the old row leaves `memories`, `storage/mod.rs:2216-2222`). Lineage is weak; old state is not queryable in `memories`.

**Erase path — hard-DELETE.** `storage::forget` (`storage/mod.rs:3051`) hard-`DELETE`s; `storage::delete` (`:2229`) and the SAL trait `MemoryStore::delete` (`store/mod.rs:959` — doc says "Hard-delete") both hard-delete; postgres `delete` (`postgres.rs:11854`) hard-deletes + AGE-unprojects. `autonomy::forget_if_superseded` (`autonomy.rs:483`) hard-deletes the contradicted loser via `db::delete` (`:538`), recovery only via a `RollbackEntry::Forget` snapshot (also the G7 break). Federation `apply_remote_deletion` (`store/mod.rs:1345`) + hard-delete call site at `handlers/federation_receive.rs:1184`.

**Already landed (v0.8.1 W2 / G30 — the primitive G6.2 reuses).** `forget` now calls `purge_and_tombstone_forget` (`storage/mod.rs:2921`) which writes a content-free, Ed25519-signable FORGET tombstone via `forget_tombstone_signable_bytes` (`:3016`, domain `forget-tombstone-v1`) into `forget_tombstones` (schema v71, both backends). **Test gap:** codegraph blast-radius reports "no covering tests" for `forget`, `delete`, `ConflictMode`, `ForgetMatch`, `forget_if_superseded`, `insert_if_newer`, `apply_remote_deletion`, `purge_and_tombstone_forget` — **every task must ship tests.**

## B5 — G13 signed identity lineage-DAG (key rotation/succession) (#1828)

**Issue refs:** #1828 · #1825 · #1831 · #1853 · #626 · #1709

### Current state

G13 is codegraph-confirmed: agent identity today is a flat string + single Ed25519 keypair with **no** signed lineage, **no** genesis record, **no** succession proof.

**What exists:**
- On-disk keypair is exactly the gap shape: `AgentKeypair { agent_id: String, public, private: Option<SigningKey> }` (`identity/keypair.rs:127`). Generated flat via `generate()` (`:237`); persisted as `<agent_id>.pub`/`.priv`.
- `keypair::rotate(agent_id, dir)` (`keypair.rs:361`) archives the OLD `.pub` to a timestamped sibling then **overwrites** `.pub`/`.priv` in place. **No** cryptographic link asserts the new key succeeds the old — the archived `.pub` is "the only retained trace". Rotation is not a signed succession.
- Agent registration is a single Memory row in `_agents`, id = `Uuid::new_v4()` (`storage/mod.rs:7991`). Flat UUID, not content-addressed (also G8 #1825).
- A single pubkey can be bound: `bind_agent_pubkey` (`storage/mod.rs:8107`) does `json_set($.agent_pubkey ...)` — an **unauthenticated in-place overwrite**. `agent_pubkey` (`:8139`) reads that one key; `clear_agent_pubkey` (`~8160`) stamps `pubkey_revoked_at` but records **no** successor. So a rotation/rebind clobbers the prior key with zero continuity proof.
- `reown` (`store/mod.rs:775`) is an operator bulk ownership-stamp rewrite, explicitly **not** succession.
- grep `genesis`/`succession`/`dead-man`/lineage-DAG: 0 production hits.
- **Consequence:** nothing can re-establish identity if `.priv` is lost — binding requires only the roster row, and there is no successor edge to a recovery key.

**Reusable building blocks (G13 is mostly assembly, not greenfield crypto):**
- A complete signed cert-chain primitive for federation node identity: `CertChain::verify(bundle, now, max_depth)` (`federation/identity/chain.rs:254`), `FederationCredential`/`SignedCredential` with canonical CBOR + Ed25519 sig (`credential.rs:149,216`), `FederationIssuer::issue/issue_intermediate/issue_chained` (`issuer.rs:182`), `TrustBundle` root-anchor. A working signed-lineage pattern (root → intermediate → leaf, depth-bounded) to mirror.
- Deterministic signing/verify: `identity::sign::canonical_cbor`+`sign` (RFC 8949 BTreeMap CBOR, `sign.rs:94,135`) and `identity::verify::verify`/`verify_write`/`attest_write` (strict Ed25519, #1808, `verify.rs:117,257,298`).
- Append-only Ed25519 hash chain: `signed_events` + `verify_chain` (`signed_events.rs:518`) — a genesis/succession event is a natural `signed_event` row.
- Binding surface to extend: `bind_agent_pubkey`/`agent_pubkey`/`clear_agent_pubkey`, `db::register_agent`, MCP `handle_agent_register` (`mcp/tools/agent.rs:10`).

**Critical scope nuance:** a single-key signed succession-DAG gives cryptographic **continuity** across a *voluntary* rotation (old key signs the new key) but does **not** solve "key-loss = death" — if the sole key is lost there is nothing to sign the successor. True recovery-without-the-key requires M-of-N threshold/social recovery (G17, v1.0). So v0.9 ships the DAG substrate + voluntary-handover continuity; recovery-from-loss is deferred. Per ROADMAP §26.5, "content-addressed"/"BLAKE3 identity" is **banned** until G8 ships — v0.9 must **not** claim "key-loss recovery" or "content-addressed identity".

### Scope split

**In scope (v0.9):**
- Signed lineage-DAG data model: a genesis record (self-signed by the founding key) + append-only succession records, each carrying `prev_record_hash` (DAG parent), `old_pubkey`, `new_pubkey`, `agent_id`, `seq`/`not_before`, and an Ed25519 signature made by the **predecessor** (old) key.
- Persistent storage on **both** backends, append-only (no in-place overwrite of prior keys), keyed by `agent_id` with the current HEAD pubkey resolvable.
- Lineage-DAG verification: walk a record back to genesis, verifying each succession is signed by its predecessor's pubkey under strict Ed25519 + canonical CBOR, with a max-depth guard — mirroring `CertChain::verify`.
- Rotation continuity: `keypair::rotate` and `bind_agent_pubkey` emit a signed succession record (old key signs new key) instead of clobbering; `agent_pubkey` resolves the verified lineage HEAD; revocation records a successor/tombstone, not a silent clear.
- CLI/MCP to show + verify an agent's lineage and emit a `signed_event` for genesis/succession.
- Cross-backend parity + tamper-rejection tests + a claims-discipline doc stating exactly what v0.9 delivers (continuity) vs withholds (recovery-from-loss).
- Soft coordination with G8/BLAKE3-CID (#1825): lineage records self-hash via BLAKE3 of their canonical CBOR for the `prev_record_hash` edge, sharing G8's primitive — but G13 records are self-contained and do **not** block on the G8 UUID-migration write path.

**Deferred to v1.0:**
- M-of-N threshold / social key recovery (G17, ~#1831) — the true fix for "key-loss = death" (a lost key cannot sign its own successor; inherently needs a quorum).
- Dead-man handover automation (timeout-triggered succession to a pre-designated heir) — depends on G17.
- Cross-mesh lineage gossip / propagation of succession records + divergent-branch conflict resolution (ties into #1823 tombstone propagation).
- Content-addressed identity IDs derived from genesis (full G8 UUID→BLAKE3-CID migration of the agent id) — gated behind G8 shipping.
- Quorum/threshold-based revocation + emergency identity freeze (needs G17).

### 2. Decision-Point Protocol — 2 Waves × 5 Adversarial Voters

The loop has no human in the cycle, so the **vote is the human-substitute control on irreversible commits.** It extends the operator-set single-wave 5-agent crossroads vote (canonical memory `4d3ea1c5-9017-4f97-b966-e0d41e83a801`) into 2 waves × 5 voters; the 2×5 protocol itself is recorded as `dab3276f-9de2-4766-ae13-a99a1ce8326e` and `memory_link`s to `4d3ea1c5`. **Vote BEFORE acting. Never bypass.**

#### 2.1 Trigger conditions (a vote is MANDATORY — not discretionary — when ANY Tn holds)

- **T1** Public-contract shape change with ≥2 viable forms (SAL `MemoryStore` trait signature; public struct/enum field crossing a module boundary; new MCP tool / HTTP route / CLI subcommand; wire-JSON or DB-schema/migration shape).
- **T2** A sync↔async boundary decision (`block_on` vs callback-bundle vs channel).
- **T3** A security/governance posture choice (fail-open vs fail-closed; a new or relaxed gate/auth/visibility/encryption boundary).
- **T4** A hard-to-reverse representation (on-disk format; persisted/attested/signed-bytes layout; any new back-compat obligation).
- **T5** Deviation from a written spec / acceptance criterion.

#### 2.3 Wave composition, isolation, and prompting (refute-by-default)

- Each wave = **exactly 5 concurrent isolated subagents, no cross-talk** (stays under the 7-concurrent cap; one batch per wave). The two waves run **sequentially** (Wave-2 depends on Wave-1). Record the 10 voters as *isolated*, **never** *independent* (vote-independence is perma-banned).
- **Every voter is a skeptic whose default verdict is REJECT.** The burden of proof is on the proposal: a voter casts ACCEPT **only if** the proposal affirmatively clears that lens's bar with a codegraph `file:line`/symbol anchor (CodeGraph is L1 evidence). Absent a clearing argument, the lens REJECTS.
- Each voter prompt contains: (a) the decision brief — the fork, the ≥2 enumerated options, the proposed option, the Tn(s) that fired, the acceptance criteria; (b) the explicit "you default to REJECT; only ACCEPT if the proposal proves it clears YOUR lens"; (c) the requirement to ground every claim in a codegraph anchor and to flag any §26.5 banned/grandeur term or any unshipped-gate-claimed-as-done (CLAIMED ≠ ATTESTED).
- **Distinct-lens roster (diversity is mandatory; 5 distinct lenses, no groupthink).** Wave-1 canonical: (1) Precedent/consistency; (2) Sync-async & correctness; (3) Spec-literalism & claims-discipline; (4) Testability; (5) Blast-radius & reversibility. Substitute lenses to match the firing Tn (e.g. a numeric-correctness/recall-quality lens for #1005; a cross-platform-portability lens for #1840) but keep the count at 5 and all 5 distinct.
- **Ballot schema (fixed):** `VERDICT ∈ {ACCEPT, REJECT, ACCEPT-WITH-CONDITIONS}` · `CONFIDENCE ∈ [0,1]` · `RATIONALE` · `TOP_RISK` · `KILLER_OBJECTION` · `EVIDENCE` (≥1 codegraph anchor).

#### 2.4 Per-wave tally (majority of 5, fail-closed)

Synthesis is **mechanical — count verdicts, do not re-litigate.**

- **≥3 ACCEPT ⇒ wave = ACCEPT; ≤2 ACCEPT ⇒ wave = REJECT.**
- Any ballot that is ABSTAIN, TIMED-OUT, ERRORED, or UNPARSEABLE counts as a **REJECT** — a crashed or silent voter never becomes an accept.
- `ACCEPT-WITH-CONDITIONS` counts as ACCEPT only if its condition is concrete and mergeable into the chosen pathway; if the ≥3 ACCEPTs carry mutually-incompatible conditions there is no clean majority ⇒ wave = REJECT.
- Because 5 is odd and all non-clean states resolve to REJECT, a wave verdict always resolves cleanly to ACCEPT or REJECT.

#### 2.5 Wave-2 prompting and the 2-wave reconciliation

- **Wave-2 fires after Wave-1 and is shown all 5 Wave-1 ballots verbatim, the Wave-1 verdict, and the synthesized rationale.** Its explicit task is to **red-team Wave-1** — hunt for correlated blind spots / groupthink, surface what Wave-1 missed, then independently CONFIRM or OVERTURN. Wave-2's lens roster is **rotated** relative to Wave-1 (e.g. precedent → adversary-incentive/security-attacker; testability → operability/rollback; blast-radius → data-migration/forensic-auditability) while still covering correctness, spec/claims, and reversibility. Wave-2 tallies by the same majority-of-5, same fail-closed rules.
- **Reconciliation truth table (AND-gate with asymmetric overturn).** Let (W1, W2) be the wave verdicts:

| W1 | W2 | Outcome |
|----|----|---------|
| ACCEPT | ACCEPT | **PROCEED** (double-confirmed) |
| REJECT | REJECT | **BLOCK** (double-confirmed reject) |
| ACCEPT | REJECT | **BLOCK** — Wave-2 overturns down; the conservative wave wins (record "wave-2 overturn-down" + new killer objection) |
| REJECT | ACCEPT | **PROCEED only if** Wave-2's ACCEPT is a **supermajority ≥4/5** AND at least one Wave-2 ballot names the **specific material fact** Wave-1 got wrong (a refuted Wave-1 killer objection); otherwise **BLOCK** |

> Rationale for the asymmetry: in a no-human loop, the cost of a wrong PROCEED (a shipped irreversible T3/T4 mistake) exceeds the cost of a wrong BLOCK (defer/escalate). Confirming a reject is easy; overturning a reject **up** to proceed is deliberately hard.

#### 2.6 Tie-break (single global principle)

**DEFAULT-TO-REJECT / FAIL-CLOSED WINS EVERY TIE AND EVERY AMBIGUITY.** A bare 3/2 Wave-2 ACCEPT against a Wave-1 REJECT does **not** clear the overturn-up bar ⇒ BLOCK. Any unresolved or split state that §2.4/§2.5 did not cleanly land ⇒ BLOCK. For an irreversible T4 (or combined T3+T4) decision, a tie **or any un-rebutted KILLER_OBJECTION ⇒ BLOCK + escalate**, never PROCEED. There is no coin-flip and no orchestrator deciding vote — the tie-break is purely the conservative default, preserving determinism.

#### 2.7 Record-to-memory with vote-id, and BLOCK disposition

- A **fresh per-vote id** is minted and `memory_store`'d **BEFORE any code is written.** It chains to `dab3276f` (which chains to `4d3ea1c5`). The record contains, in full: the fork; which Tn(s) fired; the ≥2 options; **all 10 ballots verbatim** (both waves, each VERDICT/CONFIDENCE/RATIONALE/TOP_RISK/KILLER_OBJECTION/EVIDENCE); both wave verdicts; the reconciliation outcome (PROCEED/BLOCK + overturn flag); the chosen pathway and why; and — non-negotiable — **the DISSENT preserved verbatim** (every minority/losing ballot retained, never discarded). Store with `kind=decision`, `tier=long` for PROCEED / `mid` for BLOCK-and-defer, high priority, tags `2x5-wave` + the issue#.
- The commit message and the issue/PR note cite `2×5-wave vote (<vote-id>)`. A Tn-matching change shipped without the citation is a self-flagged hard-block on return.
- **A BLOCK never idles the loop.** On BLOCK: record the decision + dissent; route to the next actionable task; if the blocked item is on the critical path with no alternative, **defer it to the v1.0 boundary with a recorded rationale** (the #1840 precedent). Only a release-tag-blocking, un-deferrable BLOCK is surfaced to the operator.
