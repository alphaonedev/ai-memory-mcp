## 2. §0 — strongest honest argument against each reason, and whether it survives

1. **Read fidelity (#3404).** *Argument:* the divergence is metadata on search/recall; id and content are correct; `get` is canonical and a guarded update can re-read. *Survives?* **Yes.** `recall.rs:756-757` reads `valid_from/valid_until` off the mapped row for the #2431 validity filter; the recall SELECT omits them → rows outside their validity window pass. That is a selection defect, not cosmetics; cert-void under §0.4 holds.
2. **Authorization gaps on ten MCP handlers.** *Argument:* `SECURITY.md:160` declares "MCP (stdio): trusts the parent process. No authentication needed"; the caller is `AI_MEMORY_AGENT_ID` (`identity/mod.rs:470-497`, absent → trust-all). MCP-side caller-owns gates are therefore advisory *by declared design*; the enterprise surface (HTTP) binds per-agent keys and admin-gates purge/skills/export. Astra itself wrote "neither enterprise path was demonstrated vulnerable". *Survives?* **Not as written.** What survives: F1-HTTP (pg `for_admin`), #3419/#3406, and the structural gap in §3. Reason 2 should be rewritten around the HTTP surface plus the stdio identity question; the "ten handlers" count conflates a single-trust-domain transport with a multi-principal boundary.
3. **Evidence not recomputable.** *Argument:* 35 required contexts are recomputable from any commit; dashboards are marketing. *Survives?* **Yes** — the certificate's RPO/RTO/continuity/Big-10 numbers come only from the untracked harnesses; CI green does not establish them.
4. **Release workflow.** *Argument:* supply-chain gates run in release, actions are SHA-pinned, the branch ruleset is signed-attested. *Survives?* **Yes** — no tag ruleset exists (verified), `outputs.sha` is never consumed, no qualification check.
5. **Two cert-blockers.** *Argument:* the VOID banner is honest self-declaration; #2437 is a benchmark-harness defect, not a mission-safety one. *Survives?* **#3501 yes; #2437 partially** — it blocks the G3 claim, not the safety envelope; it is a reason to withhold the *relevance* claim, not the whole decision.

## 3. Missing finding, more severe than any listed row

**stdio MCP has no principal binding.** The read-visibility and governance caller on the MCP transport is the launcher's `AI_MEMORY_AGENT_ID` env var (`src/identity/mod.rs:470-497`); when absent the ownership post-filter is skipped entirely ("trust the local caller"). There is no MCP-over-HTTP transport (`grep "/mcp"|streamable` → none) and `REQUIRE_ATTESTED_IDENTITY` exists only in `src/handlers/*` (HTTP). Consequences: (i) every MCP-side "caller-owns" gate — including all five chain-3 lanes (#3379/#3380/#3381/#3382/#3383) and #3383's `[admin].agent_ids` check — enforces against a string any agent with a shell can set; (ii) the standard's T7 principal matrix (unenrolled D, revoked key, old key) is **unsatisfiable on stdio** — there is no "unenrolled" on stdio; (iii) the `swarm(1 region, N agents, 1 data tier)` topology in §0.1 is therefore certifiable only via HTTP with per-agent keys, or with an orchestrator that provably controls child env. Neither the audit nor the standard states this. Nearest carriers: #3393 ("two client-chosen strings"), #3363 — neither is direct. Disposition needed in N11: either declare stdio NOT CERTIFIED for multi-principal use (which demotes most MCP-only rows to hygiene), or add a stdio identity binding as a GA item. This decides whether the chain-3 authority work produces a boundary or a comfort blanket.

Minor missing: A23 unlink-after-rename window (above).
