Grand-slam gate: an allowlisted resolved principal for global purge, no self-asserted escalation, preserve scoped owner purge, audit denied attempt and all-or-none effect. ## Exact authorization and deployment boundaries for #3379/#3383

Upstream MCP is not ungated as a whole. `src/mcp/mod.rs:3475-3509` refuses tools not loaded by the active profile, :3535-3555 rejects non-object arguments, and :3605-3613 applies the record-stop fence to mutating tools. Share belongs to the Power family (`src/mcp/tools/share.rs:201-203`); a profile that does not expose it cannot reach this dispatch. A stopped store can refuse either write. These controls do not evaluate whether the caller may read the particular share source or hold the admin role for global archive purge.

For #3383 specifically, `resolve_governance_subject` binds the requested actor before purge (`archive.rs:66-92`), and `Permissions::evaluate` runs for `Op::MemoryArchive` in the global namespace (:123-134), with Deny refusing and Ask returning an approval request (:135-150). The finding is **when that ordinary archive operation is permitted**, `as_admin:true` chooses every owner's rows without an additional membership check. It is not a bypass of a rule that already denies archive. The direct MCP handler is SQLite-bound; a local/shared stdio endpoint exposing this tool with multiple principals is the assessed risky shape. No claim is made that a separate tenant's unexposed MCP endpoint is reachable.

The HTTP purge twin has a materially stronger boundary: `src/handlers/archive.rs:307-314` applies enrolled/enforce identity binding, :345 calls `is_admin_caller_trusted`, and :366-369 constructs a checked admin/owner context for PostgreSQL. The SQLite HTTP branch also selects global/scoped behavior using that trusted is_admin result (:383-392). Therefore **do not project the MCP as_admin flaw onto the PostgreSQL HTTP purge route**.

The HTTP share route, in contrast, takes `_headers` unused and delegates to the same SQLite primitive (`src/handlers/share.rs:53-72`). Transport API-key/mTLS controls still govern endpoint access; the handler lacks source-caller authorization. The PostgreSQL supported-route allowlist (`src/handlers/postgres_gate.rs:105-284`) does not admit SHARE; the broad registered-route table elsewhere naming SHARE is NOT the supported-backend allowlist. A PostgreSQL HTTP deployment should refuse this unsupported operation, so this finding is not evidence of PostgreSQL cross-tenant share execution. Do not infer unsupported direct stdio/PostgreSQL wiring from the presence of the enterprise tier.
