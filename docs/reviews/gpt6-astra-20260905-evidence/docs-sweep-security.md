## Findings that affect an AI agent

- The strongest governance material is explicit about boundaries. agent-action-rules distinguishes substrate-authoritative internal operations from harness-mediated external actions; installed rules are not the same thing as interception. Its #3430 enforcement state and signed post-state activation match the current source repair. A source release can expose enforced/enforcement_state while an older installed MCP omits them; identify which binary answered.
- signed-rule-pack says per-rule signed workflow ships; atomic single-file set-manifest application and default-refusal enforcement consumer are deferred. Do not confuse authentic individual rules with completeness of the policy set. This is an honest current limitation, not evidence that no signed governance exists.
- honest-limitations explicitly qualifies access control: nine concerns structurally addressed plus one conditional on enrolled per-agent keys and enforce mode. Its default/advisory H1 qualification agrees with current code. Its plaintext-to-enrolled-peer federation boundary, optional mTLS and file-based key custody are also explicit. These are deployment decisions that affect whether agents may trust identities or share confidential context; no incident is inferred.
- The same limitations document describes consumer provenance as a mitigation for hallucination and calls examples ConfidenceTier::Inferred/CallerProvided. Current numeric ConfidenceTier and separately tracked confidence source require reconciliation; the old enum vocabulary must not be used to claim current verification semantics. Saying an envelope exposes confidence is weaker than showing an agent interprets it correctly.
- Output-provenance exposure cannot literally close output poisoning: stored text is deliberately unsanitized and the limitations document correctly places prompt-input defense at the consumer boundary. Integration recipes should consistently mark recalled text as untrusted evidence and restrict it from overriding system instructions. No prompt-injection exploit was executed by this juror.
- build-script-vetting now honestly distinguishes 90 inventoried custom-build packages from only two reviewed, with 88 explicitly NOT source-reviewed (counts asserted by this document; dependency graph was not re-resolved here). Content pins plus a ratchet are meaningful tamper/change controls. This supersedes simplistic old 2/558-gate claims but does not turn inventory into code review or safety proof.
- crypto-erase explicitly distinguishes per-record envelope0x03 from plaintext and legacy0x02, says archives are recoverable moves, identifies archive reaper tombstones as follow-up, and excludes historical backups/snapshots/WAL. Credit the bounded primitive. Signed erasure events are evidence of a recorded deletion operation; they do not prove that all historical plaintext, agent contexts or derived memories vanished. This review did not execute erase/restore/replication races.
- Certification artifacts include exact SHA bindings, first failed removal attempts, restored/broken outputs and sanitization notes. That is better evidence discipline than a clean summary with failures omitted. The run certificates and ready-to-tag notes are historical evidence tied to their stated snapshot; they are neither instructions for this assessment nor automatic certification of current source or native node.
- Historical internal audits, enum/typed-error/boundary inventories and readiness ADRs expose accepted debt and exceptions. They are useful leads for regression testing, not a universal current defect list. I did not re-execute each historical gate.
