Performance — measured, published, advisory in CI.

A bench tool with three operator-friendly flags: --baseline for regression detection (with --regression-threshold, default 10%), --history for JSONL accumulation, --json for machine-readable output. CI runs the bench on every non-docs PR and reddens the run when a p95 exceeds its budget by more than 10%. That run is advisory — it does not block a merge. The numbers in PERFORMANCE.md, single-sourced in src/bench.rs, are the public contract.

Public p95 budgets

The numbers, committed to source.

Every budget below is a target p95 on a reference machine (Apple M4, 32 GB unified memory, SQLite — per PERFORMANCE.md). The bench job runs on every non-docs PR and reddens when a measured p95 exceeds its budget by more than 10%; it is advisory and does not block the merge.

The following operations have no Operation variant in src/bench.rs, so no harness produces a number for them: memory_store with embedding, memory_get, cold/full-hybrid and neural-cross-encoder memory_recall, memory_link, memory_promote, memory_consolidate, memory_get_taxonomy, memory_archive_purge, sync_push, bulk_create, memory_check_duplicate, memory_session_start, the curator cycle and the federation ack. Where a design target is still published for those, it is marked [advisory] in PERFORMANCE.md — an operator-facing intent, never a measurement.

Reference machine: Apple M4, 32 GB unified memory, macOS, SQLite default settings, single-process daemon — the same machine PERFORMANCE.md §Hardware Baseline names for every latency budget. (The Apple M2 / 16 GB Mac mini in benchmarks/longmemeval/methodology.md is a different measurement family — retrieval quality, not latency.) On macOS the bench applies MACOS_BUDGET_MULT = 3.0, so a macOS pass bar is 3.3× the published number — recall PASSes at 165 ms against a published < 50 ms. The advisory CI run is on ubuntu-latest, where the multiplier is 1.0. Live numbers under PERFORMANCE.md.

The bench tool

Three flags that make it operator-friendly.

--baseline <path>
Compare this run against a saved baseline JSON. Flags any operation whose p95 increased by more than the configured threshold (default 10% — DEFAULT_REGRESSION_THRESHOLD_PCT in src/bench.rs) and exits non-zero. The CI workflow runs this as an advisory step at threshold 50% that swallows the exit code, so it never refuses a merge — and while the committed performance/baseline.json carries bootstrap: true it skips the comparison entirely. Blocking promotion is gated on a soak proving a <1% false-positive rate over ≥20 runs.
$ ai-memory bench --baseline ./bench/baseline-v0.6.3.json → memory_store keyword baseline 4.2ms current 4.4ms ✓ within +5% → memory_recall semantic baseline 31ms current 33ms ✓ within +6% → memory_consolidate smart baseline 1100ms current 1750ms ✗ +59% — REGRESSION Exit 1 — bench detected regressions, see report
--history <path>
Append the current run as one JSONL row to a history file. Trends over time become a one-liner — jq, awk, or any chart tool reads the JSONL directly. Used to keep a rolling p95 trend that survives across releases.
$ ai-memory bench --history ./bench/history.jsonl → Appended run 2026-04-27T05:00:00Z to history.jsonl # Each row in history.jsonl: {"timestamp":"2026-04-27T05:00:00Z", "git_sha":"d4bc4b6", "results":{ "memory_store_keyword": {"p50":3.1, "p95":4.4, "p99":5.2}, "memory_recall_semantic": {"p50":22, "p95":33, "p99":41}, … }}
--json
Emit results as machine-readable JSON instead of the human table. A saved --json payload is exactly what --baseline consumes on the next run. The baseline must be captured on the runner class it will be compared against — the regenerate-baseline workflow_dispatch job takes a median-of-3 on ubuntu-latest and uploads it for an operator to commit; a dev-machine capture compared against CI is pure hardware noise, which is why the committed bootstrap file makes the compare self-skip. PERFORMANCE.md is updated by hand from a reviewed known-good run.
$ ai-memory bench --json > ./bench/baseline-v0.7.0.json # Workflow: # 1. cut a release candidate # 2. run the regenerate-baseline workflow_dispatch job (median-of-3, ubuntu-latest) # 3. review + commit the artifact as performance/baseline.json with bootstrap:false # 4. CI feeds it back via --baseline as an ADVISORY compare on every non-docs PR # 5. update PERFORMANCE.md from the reviewed run
CI bench signal

Budget breaches turn the run red. They do not block the merge.

Every PR that touches something other than docs runs the bench job (.github/workflows/bench.yml) on ubuntu-latest. Two absolute-budget steps — the default workload and --scale 10000 — exit non-zero when a measured p95 exceeds its budget by more than 10%, which fails the job.

The workflow is advisory. Its own header states it verbatim — "Bench is advisory (not in required-status-checks)" — and it appears zero times in scripts/qc-allowlists/required-contexts-release.txt, the mirror of the required-status-check set on the release branch. A red Bench run is a loud signal to a reviewer; branch protection does not act on it. Both triggers also carry paths-ignore: ['docs/**', '**/*.md'], so a docs-only PR never runs it.

The baseline compare is a third, separately advisory step. It does not pull from a release tag: the baseline is a committed file, performance/baseline.json. That file currently ships as a dev-machine bootstrap: true capture, which makes the step skip the comparison entirely. Capturing a real one is the regenerate-baseline workflow_dispatch job.

# .github/workflows/bench.yml — real shape (abridged) on: pull_request: branches: [main, develop, "release/**"] paths-ignore: ['docs/**', '**/*.md'] # docs-only PRs never run the bench jobs: bench: name: ai-memory bench (ubuntu-latest) # NOT a required status check runs-on: ubuntu-latest steps: - name: Run bench (gate) # exit != 0 on >10% over budget - name: Run bench at 10k scale (gate) # same, against the [scale] budgets - name: Baseline regression (advisory, #1987) # reads the COMMITTED performance/baseline.json; # self-skips while bootstrap:true; `exit 0` unconditionally - name: Upload bench artifact uses: actions/upload-artifact@v5

Turning this into a real merge gate is one line in required-contexts-release.txt plus the matching branch-protection entry. Until that lands, the budgets are enforced by review and by an unmissable red run — and this page says so rather than implying otherwise.

Tracing — span-level attribution

Why was that one slow?

Every MCP tool dispatch is wrapped in a tracing::info_span!("mcp_tool_call") with attributes including tool, elapsed_ms, outcome. Operators can chart per-tool p95/p99 against the public budgets — and when a single call regresses, the trace tree shows which sub-operation took the time (see the tracing atlas for the full target list).

# Example — find recall calls slower than 100ms in the last hour $ grep "mcp_tool_call" daemon.log | jq 'select(.tool=="memory_recall" and .elapsed_ms > 100)' {"timestamp":"…", "tool":"memory_recall", "elapsed_ms":142, "outcome":"ok", "namespace":"alphaone/eng/platform/team-a", "limit":50, "reranker_used":true}
Scaling envelope

When the numbers stop holding.

Small corpora (the default bench never grows past ~500 rows) — the p95 budgets above are calibrated here, and at ai-memory bench --scale 10000 the measured release-build numbers still sit well inside the per-scale budgets: memory_store 0.45 ms, FTS5 memory_search 1.42 ms, hot keyword memory_recall 15.44 ms (PERFORMANCE.md §Corpus-scale budgets, gated against the [scale] table, not the default budgets).
~100k rows on SQLite — the default budgets stop holding, and the doc says so. The #1579 P1 audit measured memory_recall p95 at 361 ms against the 50 ms default budget on a 100k-row corpus while the ~500-row default bench stayed green — a corpus-scale regression the default workload cannot see. Closing that blind spot is exactly why ai-memory bench --scale <rows> and the separate per-scale budget table exist. FTS5 and the HNSW index remain the fast primitives, but the small-corpus numbers above are not a claim about a 100k-row store — treat the --scale table as the contract there. Past ~1M rows, move to the Postgres SAL adapter (--features sal).
1M+ on Postgres — supported via SAL. Bench numbers shift; v0.7 Apache AGE wraps the KG schema for graph-query speedup at this scale. The two backends are NOT one identical API: of the 80 unique production HTTP paths, 59 are served on PostgreSQL and 21 fail closed with a uniform 501 NOT IMPLEMENTED (the Agent Skills surface, /api/v1/share, the legacy /api/v1/find_paths alias, and the memory_* parity routes with no pg SAL trait method yet) — pinned by tests/pg_supported_route_inventory_gate_2799.rs. MCP stdio is structurally SQLite-only; postgres deployments serve MCP clients through the HTTP daemon. Where a path IS pg-supported, the shared SAL trait keeps its behaviour equal across backends.
Federation soak — 5+ peers, sustained burst writes — v0.6.3 W12 hardening + S40 catchup batch close the gap from v0.6.2 (which dropped 1/500 rows under sustained mTLS load). The certification matrix on release-pipeline.html shows v0.6.2's a2a-gate certification streak; v0.6.3 builds on that with an additional 3.05% coverage gain across federation paths.
