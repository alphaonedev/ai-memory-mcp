# THREE RULES (Conductor, 2026-09-13; the gate enforces them, this file respects them):
#   1. DIRECTION, not convenience. A value crossing to a CALLER is never allowlisted as passing —
#      it is `pending` under an issue until the render is routed through a typed mapper or dropped.
#      An operator LOG is a different audience (TIER 2) and is never a finding. Only an ECHO of the
#      caller's own input is a genuine acknowledgement; the gate already clears the validator echoes
#      by provenance, so an `echo:` line here needs a reason the walk could not see. There are NONE
#      today: every entry below is a live foreign render, tracked.
#   2. No entry may name a masker (redact_* / mask_* / scrub_*). The gate FAILS such an entry.
#   3. The gate reports LIVE instances separately from ledgered ones (its summary's "LIVE foreign
#      renders reaching a caller" line); a ledger that turns findings into silence is the same defect
#      as a gate that certifies nothing. A `pending` entry keeps the finding visible as INFO with its
#      issue; a stale entry (site fixed or moved) is a NOTICE.
#
# A key is re-derived on every run from PROVENANCE, not from a binding name. Moving a render from a
# helper (`signal_insert_error`) into its caller re-keys the finding and UN-LEDGERS it — that is a
# new finding, not a fixed one: the gate goes RED and the issue owner adds the new key. A site that
# renders several foreign values keys on the first identifier by name (deterministic tie-break), so
# one key can stand for two taints (forward_to_http: the peer body `e` and the URL `url`).
